# chizu 設計（最初の版）

この文書は、[要件定義](requirements.md)の「最初の版（MVP）」を実装するための設計をまとめる。外部の資料から得た事実は末尾の「参考にした事実」に出典とともに並べ、本文で使うときは「（事実 F1）」のように番号で示す。番号のない記述は、この設計での判断である。

## 全体の形

```text
┌─ メインスレッド（TypeScript）──────────┐      ┌─ Web Worker ─────────────────────────┐
│ 描画（WebGL2）  操作の受け付け         │      │ chizu-wasm（受け渡しの薄い層）       │
│   ▲ 毎フレーム読む    │ コマンド       │      │   └ chizu-core（決定論の中核）       │
│   │                   ▼ postMessage    │ ───▶ │       └ rayon のスレッドプール       │
│ SharedArrayBuffer の描画用スナップショット ◀──│  1 tick ごとに書く                   │
│ チャンク単位の静的データ（版番号つき）◀───────│  変わったチャンクだけ送る            │
└────────────────────────────────────────┘      └──────────────────────────────────────┘
```

- 中核 `chizu-core` は描画・通信・実時間の時計を知らない。入力は「種」と「コマンドの列」だけで、出力は状態と状態ハッシュである。
- 中核の中では浮動小数点を使わない。描画用の座標を `f32` に直すのは `chizu-wasm` の仕事で、その値は中核に戻らない。

## 時間の単位

中核の時間は整数の tick で数える。

| 量 | 値 | 理由 |
|---|---|---|
| 1 日 | 7,200 tick | 等速 5 tick/秒 × 1,440 秒（1 日約 24 分） |
| 時計の進み | 1 tick = ゲーム内 12 秒 | 86,400 秒 ÷ 7,200 |
| 移動の進み | 1 tick = 移動の 1 秒 | 車の追従を 1 秒刻みで解く（事実 F5 と同じ刻み） |
| 最高速 | 1,440 tick/秒（1 日 5 秒）〜 720 tick/秒（10 秒） | 要件の 144〜288 倍速 |

時計と移動の尺度をそろえると、等速でも車が 1 tick に 160m 以上進んでしまい、追従も信号も解けない。そこで、移動は時計より 12 倍遅い尺度で進める。時速 50km の車は 1 tick に約 14m 進み、5km の通勤は 357 tick（等速で約 71 秒、ゲーム内で約 71 分）かかる。等速の画面では、移動は現実の 5 倍ほどの速さに見える。

所要時間は、時計の時間ではなく移動の時間（1 tick を 1 秒として数えた時間）で測る。通勤・通学の幸福度はこの値で計算し、画面に通勤時間を出すときもこの値で出す。上の 5km の通勤なら、幸福度の計算でも画面の表示でも約 6 分（357 秒）になる。

描画は 60fps で、前後 2 つの tick のあいだを補間して滑らかに見せる。等速では 1 tick が実時間の 200ms で、12 フレームに 1 回 tick が進む。

画面の速さの段は、1 倍（5 tick/秒、1 日 24 分）、6 倍（30 tick/秒、4 分）、48 倍（240 tick/秒、30 秒）、288 倍（1,440 tick/秒、5 秒）の 4 つにする。上の帯には 1、6、48 倍と一時停止を出し、CS2 と同じく 3 段にする。288 倍は詳細の欄に置く。眺める、ふつうに遊ぶ、早送り、最高速の 4 つの使い方に 1 つずつ当て、細かい計算、区間の計算、一括の計算（3.1）のどれにも段が入るようにした。段にない速さの記録（前の帯の 4 倍や 16 倍など）を読み込んだときは、画面が最初の枠で、1 秒あたりの tick 数の比がいちばん近い段へ `SetSimSpeed` でそろえる。

## 1. 中核のデータ構造

### 1.1 単位と座標

固定小数点の汎用ライブラリ（`fixed` クレートなど）は使わず、意味ごとに整数の新しい型を作る。単位を型で分けておくと、長さと時間を取り違える誤りをコンパイル時に防げる。

```rust
pub struct Mm(pub i64);          // 長さ。ワールド座標は mm 単位の i64（要件の 64 ビット）
pub struct WorldPos { pub x: Mm, pub y: Mm }
pub struct Tick(pub u64);
pub struct MmPerTick(pub i32);   // 速さ
pub struct LaneOffset(pub u32);  // 車線の始点からの距離（mm）。1 本は 4,000km まで
```

- 移動体の位置は「車線 ID ＋車線上の距離」で持ち、ワールド座標は描画のときだけ求める。毎 tick 触るデータを 32 ビットに収めるためである。
- 符号つきの整数の割り算と剰余は、丸め方を名前に入れた関数（`div_round_half_even` など）だけで行う。符号なしの整数の `/` と `%` はそのまま使ってよい。
- `chizu-core` では、浮動小数点の混入を 2 段で止める（事実 F7）。clippy の `disallowed_types` で `f32` と `f64` を禁じ、`float_arithmetic` も deny にする。ただし、どちらも型を推論させた浮動小数点（`let a = 0.5;` や `2.5_f64.floor()`）は拾わない。そこで `scripts/check-no-float.sh` が、ソースから `f32`、`f64` と浮動小数点のリテラルを探して、見つかったら `lint:rust` を落とす。

### 1.2 チャンクと層

```rust
pub struct ChunkCoord { pub cx: i32, pub cy: i32 }   // 1 チャンク 64×64 マス = 512m
pub enum Layer { Ground = 0, Elevated = 1, Underground = 2 }

pub struct Chunk {
    pub coord: ChunkCoord,
    pub owned: bool,
    pub version: u32,                   // 中身が変わるたびに増やす。描画側のキャッシュの鍵
    pub terrain: TerrainTiles,          // 標高 u16 と水の有無。MVP は標高 0 固定
    pub layers: [Option<Box<LayerTiles>>; 3],
}
pub struct LayerTiles {
    pub occupancy: [TileUse; 4096],     // 何がそのマスを使っているか（道路、建物、空き）
    pub zone: [ZoneKind; 4096],         // 地上だけが意味を持つ
}
```

- チャンクは `BTreeMap<ChunkCoord, Chunk>` で持つ。反復の順番が座標順に決まるので、決定論を崩さない。
- メモリに置くのは、買った土地、道路や幹線が通るチャンク、画面に入ったチャンクだけである。地形は `terrain(seed, coord)` という純関数で作るので、捨てても作り直せる。
- 層は配列の添え字で持つ。MVP は `layers[Ground]` しか作らないが、高架や地下を足すときは `Some` を入れるだけで済む。
- チャンク座標を i32 で持っても、表せる広さは 10^12 m を超える。ワールド座標を i64 で持つ要件とは矛盾しない。

### 1.3 道路と歩道の網

網はチャンクに分けず、街全体で 1 つのグラフとして持つ。チャンクには「このチャンクにかかる区間の ID 一覧」だけを空間索引として持たせる。

```rust
pub struct Node    { pub pos: WorldPos, pub layer: Layer, pub control: NodeControl }
pub struct Segment { pub a: NodeId, pub b: NodeId, pub kind: RoadKind, pub lanes: SmallVec<[LaneId; 8]> }
pub struct Lane    { pub segment: SegmentId, pub dir: Dir, pub mode: LaneMode, pub length: Mm }
pub struct Connector { pub from: LaneId, pub to: LaneId, pub node: NodeId, pub signal_group: u8 }
pub enum LaneMode { Car, Sidewalk }
pub enum NodeControl { None, Signal(SignalPlan) }
```

- 区間は 8 方向（縦横と 45 度）の直線に限る。曲線は MVP では入れない。
- 区間の片側の車線をまとめた「向きつき区間」を **リンク** と呼び、経路探索と粗い計算の単位にする。リンク ID は `(SegmentId, Dir, LaneMode)` から決まる。
- 層をまたぐ移動（高架の上り口、駅の階段）は、層の違うノードを結ぶ普通の区間として表す。経路探索は層を区別しないので、高架や地下を足しても探索の処理は変わらない。
- 横断歩道は区間として持たない。3 本以上の区間が集まる交差点の、高速道路でないどの腕にも自動で付く「渡る所」とする。車線との交差は、あとで述べる衝突区間として持つ。
- ID は世代つきの添え字（`u32` の添え字＋ `u16` の世代）にする。空き番号は後入れ先出しで使い回し、使い回しの順番も決定論に従う。
- 外部接続の高速道路は、種から作る幹線として普通の区間で持ち、端に「外の世界」ノードを置く。移住者と外から来る車はここで生まれ、ここで消える。

### 1.4 区画と建物

区画は CS2 にならい、道路沿いのマスに塗る（事実 F2）。マスごとの `ZoneKind`（住宅・商業・工業・オフィス）を `LayerTiles.zone` に持つ。

建物は表 `Buildings` に入れる。持つのは、占めるマスの範囲、種類と段階、世帯数や職場数の上限、出入口（歩道のリンクと位置）、駐車場の台数、電気と水道が届いているかである。

電気と水道は、発電所・浄水場から道路網づたいにつながっている建物に、施設の入口から道のりの近い順に、供給量が尽きるまで届ける。供給が需要に足りないと、施設から遠い建物から届かなくなる。判定は差し替えやすい関数 1 つ（`service::evaluate_supply`）に閉じ込める。

新しい建物は、その道路網の電気と水道に余りがあるときだけ建つ。施設のない網には、小さな家が数軒建つ程度の余地（`service::UNSUPPLIED_ALLOWANCE`）しかない。

余りは道路網をまたいで足さず、主の網（需要がいちばん大きい網）の値で見る。次のどちらかに当たる施設は、孤立した施設として読み取れる（`World::isolated_facilities`）。面した道路が消えて入口がない施設と、主の網ではない網にあって余りが正なのに、主の網の余りが少ないか足りない施設である。主の網に十分な余りがあるあいだは、ほかの網に施設があっても数えない。別の町を作る遊び方で、誤った知らせを出さないためである。状態ハッシュと記録には入れない。

### 1.5 住民データの並べ方

ECS ライブラリは使わず、自前の SoA（列ごとの `Vec`）で持つ。

| 案 | 良い点 | 困る点 |
|---|---|---|
| bevy_ecs | スケジューラと変更検知がある | WASM では並列に動かない（事実 F10）。反復の順番が内部の配置に依存する。依存が大きい |
| hecs | 軽い | 部品を足し引きすると実体の並びが変わり、順番を自分で管理する必要がある。並列化の仕組みはない |
| 自前の SoA | 反復の順番が ID 順に決まる。rayon で区切って並列に回しやすい。保存と状態ハッシュも列をなめるだけで済む | 表ごとに追加・削除の処理を書く |

住民は種類の少ない固定の表なので、ECS の柔軟さはあまり効かない。決定論と保存のしやすさを優先した。

```rust
pub struct Citizens {            // 住民データ層。全員分
    pub household: Vec<HouseholdId>,
    pub age: Vec<u8>,
    pub workplace: Vec<Option<BuildingId>>,   // 職場または学校
    pub schedule: Vec<ScheduleState>,         // 次の予定と出発予定の tick
    pub happiness: Vec<HappinessParts>,       // 通勤・生活サービス・暮らし向きの 3 つ
    pub trip: Vec<Option<TripId>>,            // 移動中なら移動の ID
}
pub struct Households { pub home: Vec<BuildingId>, pub money: Vec<i64>, pub members: Vec<SmallVec<[CitizenId; 4]>> }
```

- 「ゲーム内の十数分に 1 回まとめて更新」は、住民を ID で 64 組に分け、毎 tick 1 組ずつ更新して実現する。1 人あたりゲーム内の約 13 分（64 tick）に 1 回になる。tick を基準にするので、速度を変えてもゲーム内の時間あたりの更新回数は変わらない。
- 出発は優先度つき待ち行列 `(出発 tick, CitizenId)` に積む。同じ tick の出発は ID 順に処理する。
- 移動層は別の表 `Trips` と、車線ごとの移動体の列に持つ（3 章）。

## 2. 中核と画面の受け渡し

### 2.1 中核から画面へ

| 中身 | 頻度 | 渡し方 |
|---|---|---|
| 画面内の移動体（位置、向き、種類） | 毎 tick、ただし最大 60 回/秒。最高速では送らない | SharedArrayBuffer の三重バッファ |
| 時計、お金、人口、速度 | 同上 | 同じバッファの先頭に置く |
| チャンクの静的データ（道路、建物、区画） | 変わったときだけ | `postMessage` で ArrayBuffer を移譲（transfer）する |
| データレイヤーの値 | 画面に出しているレイヤーだけ、数秒に 1 回 | 同上。チャンクごとの 64×64 の配列 |

- 三重バッファは、書き込み中・最新・読み込み中の 3 枠を `Atomics` で入れ替える。中核は待たず、描画は常に最新の完成した枠を読む。
- 移動体 1 体は 16 バイト（チャンク原点からの x・y を `f32`、向きを `u16`、種類と色を `u16`、ID を `u32`）にする。2 万体で 320KB なので、毎 tick 書いても負担にならない。
- 静的データは、チャンクの `version` が描画側の手元と違うときだけ送る。描画側は「いま見えているチャンクと手元の版番号」を Worker に伝え、Worker は差分だけ返す。
- 画面の範囲は、描画側と Worker のあいだだけで受け渡す。Worker は、中核の読み取り専用の問い合わせ `World::movers_in(rect)` で、その範囲の移動体の位置を受け取る。中核は問い合わせで状態を変えないので、画面の範囲は状態にもハッシュにも影響しない。
- 中速では中核に移動体がない。`movers_in` は、区間の計算の主体の（リンク、入った tick、出る tick）から位置を補間して、描画用の移動体をその場で作って返す（3.2）。
- SharedArrayBuffer を使うので、ページは COOP/COEP ヘッダーつきで配信する必要がある。開発サーバー（Vite）がこのヘッダーを出す前提で作り、公開先は公開する段階で決める。SharedArrayBuffer がない環境の代わりの経路は作らない。

### 2.2 画面から中核へ

プレイヤーの操作はすべて `Command` に直して中核へ渡す。

```rust
pub enum Command {
    BuildRoad { from: TilePos, to: TilePos, kind: RoadKind },
    UpgradeRoad { from: TilePos, to: TilePos, kind: RoadKind },  // 直線が通る既存の区間の種類を、区間ごと変える
    Bulldoze { area: TileRect },
    PaintZone { area: TileRect, zone: Option<ZoneKind> },   // None で区画を消す
    PlaceBuilding { kind: ServiceKind, at: TilePos, rotation: u8 },
    SetSignal { node: NodeId, on: bool },
    BuyChunk { coord: ChunkCoord },
    SetTaxRate { zone: ZoneKind, permille: u16 },
    SetSimSpeed { speed: SimSpeed },
}
```

- 画面は JSON に近いオブジェクトで送り、`chizu-wasm` が `Command` に直す。値の範囲の検証は中核の `Command::validate` が行い、`chizu-wasm` はそれを呼んで不正なコマンドを捨てる。記録も同じ検証を通すので、記録に入ったコマンドは必ず読み戻せる。
- Worker は受け取った順に番号を振り、まだ step していないいまの tick に `(tick, 番号, Command)` として記録し、その場で適用する。tick T の状態は「tick が T 以下のコマンドを番号順に適用し、step を T 回済ませたもの」と決める。再生（`replay`）で T tick 進めると、最後の step のあとで tick T のコマンドまで適用して終えるので、受けてすぐ適用した状態と一致する。一時停止中も同じで、止めたまま建てられる。`World` は適用済みの記録の次の番号を状態に持ち、途中の状態から続きを再生するときは、その番号より後の記録だけを適用する。再現に必要なのは、種とこの記録だけである。
- `UpgradeRoad` は CS2 のアップグレードの道具にならい、形とノードを変えずに種類だけを変える。費用は建設費の差額で、下げても払い戻さない。区間は作り直すので ID が変わり、建物の出入口は付け直し、走っている移動は区間が分かれたときと同じく、いまの位置から経路を探し直す。車線が減って重なる車は、空くまで出発を待つ車にする。
- 計算の細かさは速度で変わり、結果も少し変わる。そのため速度の変更（`SetSimSpeed`）もコマンドとして記録する。
- 画面の範囲はコマンドにしない。見ている人ごとに範囲が違っても、同じ記録から同じ街を再現できるようにするためである。
- 一時停止は tick を進めないだけなので、記録しない。

## 3. 速度に応じた移動計算の切り替え

### 3.1 3 つの計算

| 名前 | 使う場面 | 中身 |
|---|---|---|
| 細かい計算 | 120 tick/秒まで（等速〜24 倍、1 日 1 分まで） | 移動体が車線を走る。追従、信号、横断歩道、渋滞を 1 tick ごとに解く |
| 区間の計算 | 中速（120 tick/秒を超え 360 tick/秒まで、1 日 20 秒まで） | 移動体を作らない。移動の主体はリンクの待ち行列に入り、見積もった所要時間が過ぎたら次のリンクへ移る |
| 一括の計算 | 最高速（360 tick/秒を超える速度） | 出発の時点で経路の各リンクの所要時間を足し、到着 tick を決める |

区間の計算は、リンクを待ち行列とみなす MATSim の手法にならう（事実 F3）。リンクには流せる台数（1 tick あたり）と溜められる台数を持たせ、溜まりきったら手前のリンクで待たせる。これで、渋滞が手前へ伸びる様子を粗い計算でも再現する。

速度の境目は、倍率ではなく 1 秒あたりの tick 数（120 tick/秒と 360 tick/秒）で決める。重さは 1 秒に解く tick の数で決まるので、等速の tick 数を変えても境目は動かさずに済む。境目は定数にし、ベンチマークを見て決め直す。

### 3.2 計算の選び方と中速の描画

どの計算で回すかは速度だけで決め、街全体に同じ計算を使う。画面の範囲は計算の選び方に関わらない。

移動の主体（`Trip`）は、いまどの計算で動いているかを持つ。

```rust
pub enum TripState {
    Micro { lane: LaneId, offset: LaneOffset, speed: MmPerTick, entered_at: Tick },
    Queued { link: LinkId, entered_at: Tick, exit_at: Tick },        // 区間の計算
    Scheduled { arrive_at: Tick, entered: Vec<(LinkId, Tick)> },     // 一括の計算
}
```

中速の画面に映る移動体は、`Queued` の主体から描画のためだけに作る。リンク上の位置は `(いまの tick − entered_at) ÷ (exit_at − entered_at)` でリンクの長さを按分して求める。出る tick を過ぎても先のリンクが詰まって待っている主体は、リンクの終わりから待ち行列の順に車 1 台ぶんずつ下げて並べる。どの車線に描くかは `TripId` から決める。この移動体は中核の状態に入らず、状態ハッシュにも影響しない。

### 3.3 速度の境目をまたぐときの移り変わり

- 細かい → 区間：移動体をすべて消し、いまのリンクで `Queued` にする。`entered_at` はそのリンクに実際に入った tick を引き継ぎ、`exit_at` は「いまの tick ＋残りの距離 ÷ そのリンクの平均の速さ」とする。
- 区間 → 細かい：`Queued` の主体を、3.2 と同じ按分で求めた位置に移動体として置く。前の車と重なるときは、前の車の後ろの空いた位置まで下げる。リンクの始点まで下げても空きがなければ、空きができるまで `Queued` のまま待たせる。
- 区間 → 一括：`Queued` の主体を、残りの経路について一括で見積もり直し、`Scheduled` にする。
- 一括 → 区間：`entered` から、いまいるはずのリンクと入った tick を求めて `Queued` に戻す。
- 細かい計算と一括の計算のあいだを 1 度に飛ぶときは、同じ tick の中で区間の計算を経由する。
- 移り変わりはすべて tick の頭で、`TripId` の順に処理する。

### 3.4 数字をずらさないための所要時間の表

3 つの計算は、所要時間を **リンクごとの表 `LinkStats` 1 つ** から読む。細かい計算が測った値を書き、粗い計算はそれを読むだけにする。

- 1 日を 96 の時間帯（ゲーム内 15 分、75 tick）に分け、リンク × 時間帯ごとに「測った平均の所要時間 T」と「そのときの交通量 V」を持つ。
- 細かい計算でリンクを通り抜けた移動体は、入った tick と出た tick を記録する。時間帯の終わりに集計し、過去の値と指数移動平均で混ぜる（重みは 1/4）。中速と最高速では測らないので、最後に細かい計算で測った値をそのまま使う。
- 粗い計算での見積もりは、BPR 関数（事実 F6）の比で補正する。

  ```text
  見積もり = T × BPR(いまの交通量) ÷ BPR(V)     ※測った値がないリンクは自由走行の時間 × BPR(いまの交通量)
  BPR(v) = 1 + 0.15 × (v / 容量)^4              ※整数の表引きで計算する
  ```

- 見積もりは自由走行の時間の 1〜10 倍に収める。信号の待ち時間は、測った値がないうちは周期の赤の割合 × 周期 ÷ 2 を足す。
- 区間の計算と一括の計算も、リンクに入った台数を「いまの交通量」として数える。こうすると、最高速で回しているあいだも渋滞の度合いが所要時間に反映される。
- ずれていないかは、同じ街を 3 つの計算でそれぞれ数日回し、平均の通勤時間、リンクの交通量、収入を比べるテストで確かめる（8 章）。

### 3.5 細かい計算の中身

- 車線ごとに移動体を前から順に並べた配列を持つ。追従は SUMO の既定と同じ Krauss 型の安全速度（事実 F5）を整数で解く。
- 車線の選び方は、リンクに入るときに次の曲がり方から決める。MVP では追い越しをしない。
- 1 tick の更新は 2 段に分ける。
  1. 車線ごとに、前の tick の状態だけを読んで新しい位置を求める（rayon で並列）。
  2. ノードをまたぐ移動を、ノード ID の順に 1 つずつ確定する。行き先の車線に空きがなければ止める。
- 3 本以上の区間が集まるノード（交差点）では、1. の前に、前の tick の状態だけを読んで、ノードの手前で止める車をノード ID の順に決める。交差点の手前まで来た車線の先頭の車を優先の順に見て、交差点の中の車や先に通すと決めた車と道筋が交わるか、同じリンクへ合流するなら止める。優先の順は、止まりきれない車、長く待ちすぎた車、格の高い道路の車、右折より直進と左折、待った長さの順とする。全順序なので、譲り合って誰も動かない行き詰まりは起きない。交差点の中で止まる車を出さないよう、出ていく車線に交差点を抜けきるだけの空きがなければノードをまたがせない。出ていく車線の詰まりが輪になって誰も動けなくなったときは、交差点の手前で 300 tick より長く待った車を行き先に着いたことにして、輪をほどく。
- 建物の前の路肩から出る車は、空いた車線に置く。前の車と重なるなら、その後ろの空いた位置まで下げる。ただし、交差点の手前まで来た車線の先頭の車が交差点の先で入りうる車線では、自分の位置から車 2 台ぶんより後ろへは下げず、空くまで路肩で待つ。後ろへ下げて入れると、列が進んでリンクの入口にできた空きを路肩の車が先に取り、交差点の先頭の車が空きを待ち続けて、詰まりの輪ができるためである。先頭の車は先の車線のうち車の少ない車線を選ぶので、路肩の車を置くと選ぶ車線が変わりうる。そのため、選ぶ 1 本だけでなく、選びうる車線をすべて守る。
- 横断歩道と、道路を勝手に横切る歩行者は **衝突区間** で表す。衝突区間は毎 tick、歩行者の位置から作り直し、状態には持たない。
  - 歩行者は、どちらの向きに歩いても建物の側の歩道を歩く。交差点で側を変えるときは、交差点のまわりを渡る腕の少ない向きに回り、通る腕の横断歩道を順に渡る。高速道路の腕は渡らずに回る。
  - プレイヤーは、交差点の腕ごとに横断歩道を外せる。外した腕は、腕の向きの印としてノードに持つので、区間を分けても種類を変えても残り、腕を取り壊すと消える。歩行者は、外した腕も高速道路の腕と同じく渡らずに回り、次の交差点で外した腕を避けられる側へ先に移っておく。どちらに回っても越えるときだけ、横断歩道があるときと同じく車を止めて渡る。高速道路の腕を車を止めずに越えるのは、外した腕を渡っても回れないときだけである。交差点で渡り始めた人の道のりは、渡り終えるまで変えない。経路を選ぶときは、そうして越える腕 1 本ごとに 100m の固定の費用を足すので、ほかの交差点を回る遠回りがそれより短ければその交差点を避ける。外した腕を渡るのは回れない人だけになるので、そこを通る車は、ほとんど止まらなくなる。
  - 車は、交差点で入る腕か出る腕の横断歩道に人がいれば、ノードの手前で止まる。区間の途中の衝突区間では、その手前で止まる。止まりきれない車は止まらない。
  - 歩行者は、止まりきれない車が来ているあいだと、交差点の中に車がいるあいだは渡り始めない。信号のない交差点では、手前まで来た車を先に通す。信号のある交差点では、歩行者も信号に従う。
  - 人と車は、待った長さで順番を回す。渡り始めるのを 40 tick より長く待った歩行者がいる横断歩道では、止まりきれる車を止め、待っていた歩行者をまとめて渡らせる。ただし、横断歩道の人に譲ってその歩行者より長く待った車がいれば、その車を先に通す。交差点の中で止まった車がいるあいだは歩行者が渡れないので、手前の車を止めない。止めると、先の詰まりと輪になりうる。車の待ちは、横断歩道の人だけのために続けて止まった tick 数で数え、ほかの車や先の車線の空きを待つ車は歩行者を止めない。こうして、車が途切れない交差点でも歩行者はいつか渡れ、歩行者が途切れない交差点でも車はいつか進める。
  - 区間の途中で横切る歩行者も、40 tick より長く待てば、止まっている車のすぐ前を横切る。横切る所に車がかかっていなければ、止まりきれる車にその前を空けさせる。かかっている所で空けさせないのは、空けさせた所どうしが互いを待ち続けないためである。
  - 区間の途中で横切るのは、出発と行き先が同じリンクの上にあり、建物が道路の反対の側どうしのときだけである。経路を選ぶときは横切りに 100m の固定の費用を足すので、近くの横断歩道までの遠回りがそれより短ければ横断歩道を使う。
- 信号は感応式とする。骨組みは固定の周期で、どの軸の段階にいるかは `(tick + ノードごとのずらし) mod 周期` で決める。そのうえで、tick を進める前の車と歩く人の位置から、青を渡す先を決める。段階の軸の手前に車が来ていなければ、車の来ている次の軸へ青を渡すので、段階の青の長さ（30 tick）は上限になる。ほかの軸の腕を渡ろうと待つ人がいるあいだは渡さない。止まりきれない車のいる軸は、どの段階でもその tick は黄にし、青はその車が抜けてからほかの軸へ移す。信号は状態を持たず、灯火はいまの tick と移動の主体の位置だけで決まる。画面に出す灯火は、移動の主体の表が控えた、直前の tick に効いた様子から求める。
- 駐車は、建物の駐車場の台数だけを持つ。満車なら近くの別の建物の駐車場へ回り、そこから歩く。路上駐車は MVP では入れない。

## 4. 決定論の守り方

| 項目 | 方法 |
|---|---|
| 数値 | 1.1 の整数の型だけを使う。`f32` と `f64` を `disallowed_types` で禁じ、浮動小数点のリテラルも `scripts/check-no-float.sh` で禁じる |
| 乱数 | 自前の小さな生成器（SplitMix64 で種を混ぜ、PCG32 で引く）。外部クレートを使わないのは、版が上がって乱数の列が変わるのを避けるため |
| 乱数の流れ | 共有の生成器を持たない。`rng(seed, 用途, 対象の ID, tick)` で毎回その場で作る。並列に回しても引く順番に左右されない |
| 集合 | `HashMap` と `HashSet` を clippy の `disallowed_types` で禁じる。`BTreeMap`、ID で引く `Vec`、挿入順を保つ表のどれかを使う |
| 並列 | rayon で並列に回すのは「入力を読み、出力を自分の枠に書く」処理だけにする。添え字つきの並列反復を `collect` すれば元の順番が保たれる（事実 F8）。他の表への書き込みは、命令の列として集め、ID 順に並べてから 1 本のスレッドで適用する |
| 集計 | 整数の足し算だけで行う。足す順番が変わっても結果は変わらない |
| 経路探索 | 時間帯の初めに重みの写しを作り、その時間帯の探索はすべて写しを読む。結果は依頼の順に並べて適用する |
| 状態ハッシュ | `World::state_hash()` が、表を ID 順になめて決まった順番でバイト列を作り、xxh3 にかける。`std::hash::Hash` の既定の仕組みは使わない |

## 5. 経路探索

### 5.1 グラフ

- 車のグラフは、リンクを頂点、ノードでの曲がり方（`Connector` をリンク単位にまとめたもの）を辺にする。曲がり方を辺にすると、右折禁止や信号の待ちを辺の重みに乗せられる。
- 歩行者のグラフは、歩道のリンクを頂点にし、ノードでのつながりを辺にする。歩道のリンクは歩く向きを表し、どちらの側の歩道を歩くかは移動の主体が持つ（3.5 節）。横断歩道を渡る時間は経路の費用に入れない。区間の途中での横切りの費用（100m の固定）は、グラフの辺ではなく、出発と行き先の組を選ぶときに足す。
- 自家用車の移動は「歩く → 車 → 歩く」の 3 区切りで探す。家の駐車場から車に乗り、行き先の建物の駐車場（満車の見込みなら近くの駐車場）で降りる。
- 費用は、所要時間に、燃料代と駐車料をお金の重みで換算して足したものにする。CS2 の時間・快適さ・お金・振る舞いの 4 つ（事実 F1）のうち、MVP は時間とお金だけを入れる。
- 住民は家を出るときに、徒歩と自家用車の両方の費用を比べて安いほうを選ぶ。

### 5.2 10 万人規模で回すための方式

10 万人が 1 日に約 2.5 回移動すると、1 日に 25 万回の探索が要る。最高速で 1 日 5 秒なら、毎秒 5 万回になる。素朴な A* で 1 回に数 ms かかると、4 スレッドでも間に合わない。

段階を踏んで速くする。

1. **A* ＋結果の再利用（最初の実装）**：`(出発のリンク, 着くリンク, 手段, 時間帯)` を鍵にして結果を覚えておく。網か時間帯の重みが変わったら捨てる。住民の行き先は職場や店に集まるので、覚えた結果を使い回せる場面が多いと見込んでいる。
2. **出発地の束ね**：同じ tick に同じ建物群から出る探索を、1 回の一対多の探索にまとめる。
3. **CCH（必要になったら）**：Customizable Contraction Hierarchies は、網の形だけを使う重い前処理と、重みを入れる軽い処理を分ける手法である（事実 F9）。時間帯ごとに重みだけを入れ直せばよく、渋滞の反映と相性が良い。道路を引くたびに前処理をやり直すので、建設中は 1. に戻すといった工夫が要る。既存の RoutingKit は C++ なので、使うなら Rust で書き直す。

探索は `Router` という trait の裏に隠し、1.〜3. を差し替えられるようにする。探索の依頼は tick ごとに集めて rayon で並列に解き、依頼の順に適用する。

### 5.3 渋滞の反映と経路の見直し

辺の重みには、3.4 の `LinkStats` の見積もりを時間帯の初めに写したものを使う。所要時間の情報源を 1 つにすることで、細かい計算と粗い計算で経路の選び方がずれない。

いまは `LinkStats` を入れる前の仮の形として、車線に並んでいる車の台数から遅れを見積もる。

- 時間帯（75 tick）ごとに 1 回、職場の割り当てなどの重い処理と重ならない時間帯の真ん中の tick に、時速 7.2km より遅い車をリンクごとに数え、1 台あたり 4 秒をリンクの車線の数で割った長さを遅れにする。交差する流れのある交差点や信号では、車線の先頭から 4 tick に 1 台ほど抜けるためである。
- 車のリンクの費用は、自由に走れたときの所要時間にこの遅れを足したものにする。次に見積もるまでの探索はすべて同じ遅れを読む。遅れが変わったら、覚えた車の経路を捨てる。
- 時間帯の途中で書き出した街を読み戻しても同じ経路を選ぶよう、遅れは街の状態に入れる。
- 費用の同じ経路が並ぶ碁盤の目でも、混んだ道を避けて並行の道へ分かれる。

碁盤の目には、費用の同じ最短経路がたくさんある。1 つの決まりで 1 本を選ぶと、遅れが見積もられるまで、同じ向きの車がみな同じ道に集まる。そこで、費用の同じ経路を次のように散らす。

- 車の経路は、1 回の探索から、費用の同じ経路を 8 本の候補として取り出す。候補 k では、出発のリンクから進むたびに、最短経路を続けられる辺のうち、行き先のリンクの順がいちばん小さいものを選ぶ。順は、候補の番号と、リンクの通る直線（向きと位置）を混ぜた値である。同じ直線の上では順が変わらないので、まっすぐ進む経路が選ばれやすい。
- どの候補を使うかは、出発と行き先の位置を混ぜた値で決める。同じ 2 点のあいだはいつも同じ経路を通り、同じ道に面した隣の家からは別の経路に分かれる。
- 費用は変えないので、ヒューリスティックは下限のままである。結果は `(出発のリンク, 着くリンク, 手段, 時間帯)` ごとに 8 本の候補をまとめて覚えるので、探す回数は変わらない。鍵あたりの大きさが鍵によって大きく違うので、覚える量の上限は鍵の数ではなく、持っている経路のリンクの数の和で決める。
- 歩く経路は散らさない。

経路は出発のときに決め、途中では変えない。ただし、通る予定の区間が消されたときと、細かい計算で同じ場所に一定の時間以上止まったときだけ、いまの位置から探し直す。

## 6. 性能の目標と測り方

### 6.1 目標

| 場面 | 規模 | 目標 |
|---|---|---|
| 細かい計算（6 倍、30 tick/秒） | 人口 10 万、移動体 2 万 | 1 tick の計算が 10ms 以内（30 tick/秒に対して 3 割の余裕）。描画は 60fps |
| 中速（48 倍、240 tick/秒） | 人口 10 万、街全体を区間の計算で回し、画面内の約 2 千体を補間して描く | 240 tick/秒を保つ |
| 最高速 | 人口 10 万 | 1 日（7,200 tick）を 5〜10 秒で回す |
| 将来 | 人口 100 万 | 最高速で 1 日 60 秒以内。表の作りを変えずに届くかを見るためだけに測る |

すべて 4 スレッドの WASM（Chrome、M1 程度の機械）を基準にする。ネイティブの値は参考にとどめる。

### 6.2 測り方

- `chizu-scenario` クレートに、種から格子状の街を決定論的に作る関数を置く。住民の表は `synthetic_population`、道路の格子は `grid_network` と `city_grid_100k`、区画を塗って建物が建つ街は `zoned_grid_city`、通勤の依頼は `commute_requests` で作る。テストとベンチマークはこれを共有する。
- ネイティブのベンチマークは `crates/chizu-scenario/benches/` に置き、`mise run bench` で回す。
  - `citizen_bucket`：住民の表の 1 組の更新（10 万人と 100 万人）
  - `route_batch`：経路の一括探索（1,000 件と 10 万件、束ねるかどうか、職場の集まり方）
  - `growth`：建物が建つ街の 1 日と、最悪の 1 tick
- ブラウザとネイティブを同じ条件で並べる測定は `chizu-scenario` の `perf` モジュールにまとめ、`mise run bench:wasm` で回す。
  - 1 tick は、`zoned_grid_city` の `World::step` と、住民の表の 1 組の更新である。住民の処理には、乱数を引いて幸福度と出発の予定を書き戻す仮の中身（`perf::rng_write`）を使う。住民の表は `World` の外に持つ。
  - `day_100k` と `day_1m`：住民 10 万人で 1 日（7,200 tick）、100 万人で 1/10 日を回し、1 tick の平均と最悪を出す。`day_ns` は 1 tick の平均から見積もった 1 日の時間である。道路を引いたあとの最初の `World::step` は経路のグラフを作り直すので、1 回進めてから測る。
  - `movers_20k`：`city_grid_100k` で、歩く人と車を 1 万ずつ出して 300 tick 進め、1 tick の平均と最悪を出す。6.1 の細かい計算の場面の目安である。
  - `route_batch_1k` と `route_batch_100k`：`city_grid_100k` で、職場が車のリンクの約 1/100 に集まった通勤を、覚えた結果がない状態から解く。
  - `memory_bytes`：始めたとき、`day_100k` のあと、`day_1m` のあとの WASM の線形メモリの大きさ。線形メモリは縮まないので、それまでで最も大きかったときの値になる。
  - 測る前に、どの項目も小さい規模で一度ずつ回す（`perf::warm_up`）。V8 は WASM をまず Liftoff で動かし、よく呼ぶ関数を TurboFan でコンパイルし直すので、その時間を測った値に入れないためである。ネイティブでも同じように回す。
- WASM の側は `chizu-bench-wasm` クレートから `perf` を呼ぶ。画面のアプリの WASM には入れず、`build:bench-wasm` で `build:wasm` と同じ rustflags とプロファイル（`wasm-release`）でビルドする。
  - `bench:wasm` は、COOP/COEP のヘッダーをつけて配る小さなサーバーを立て、ヘッドレスの Chrome で開いた Worker から呼ぶ。
  - rayon のスレッドは 1、4、`navigator.hardwareConcurrency` 本の 3 通りにする。スレッドプールは 1 つのインスタンスで 1 度しか作れないので、スレッド数ごとに Worker を作り直す。
  - 同じ項目を、ネイティブでも同じスレッド数で回す（`CHIZU_PERF_THREADS=4 cargo bench -p chizu-scenario --bench perf`）。WASM がネイティブの何倍かかったかを `ratio` に出す。`CHIZU_PERF_THREADS` がないときは何もしないので、`mise run bench` では回らない。
  - どちらも、測る処理全体を rayon のプールのスレッドの上で回す。ネイティブは `ThreadPool::install` を使い、WASM はプールに `rayon::spawn` で渡して終わるのを待つ。
  - 結果は、標準出力と `target/bench-wasm.json` に JSON で書く。`mise run bench:wasm -- --wasm-only` ならネイティブは回さない。
- 粗い計算が入ったら、6.1 の中速と最高速の場面に合わせて `perf` に項目を足す。
- 共有の CI の機械は速さがぶれるので、CI ではベンチマークをビルドするだけにする。`chizu-bench-wasm` は `lint:wasm` で wasm32 に clippy をかけ、壊れたら落ちるようにする。数字は手元で測り、大きな変更の PR には前後の値を書く。

## 7. リポジトリの構成

```text
Cargo.toml                 # workspace
rust-toolchain.toml        # 日付で固定した nightly、rust-src、clippy、rustfmt、wasm32 のターゲット
crates/
  chizu-core/              # 中核。依存は rayon（feature "parallel"）、smallvec、xxhash-rust だけ
  chizu-scenario/          # テストとベンチマーク用の街の生成
  chizu-wasm/              # wasm-bindgen の受け渡し、スナップショットの書き込み、コマンドの検証
  chizu-cli/               # ネイティブで操作の記録を再生し、状態ハッシュを出す
web/
  package.json  vite.config.ts  tsconfig.json  biome.json
  src/  main.ts  worker.ts  protocol/  render/  ui/
```

中核をさらに網・住民・交通のクレートに分けるのは、ビルド時間が気になってからにする。最初は `chizu-core` の中のモジュールで分ける。

WASM でスレッドを使うには、nightly と `build-std` と `+atomics` が要る（事実 F4）。nightly は `rust-toolchain.toml` で日付ごと固定し、ネイティブのビルドも同じものを使う。stable と nightly を混ぜると、clippy やテストを 2 つのツールチェーンで回すことになるためである。

WASM は `cargo build` のあと `wasm-bindgen --target web` で JS 側のつなぎのコードを作る。wasm-pack は使わない。`wasm-bindgen-cli` は、クレートの wasm-bindgen と同じ版を mise の tools で入れる。

TypeScript 側は Vite でビルドする。wasm-bindgen-rayon は Rollup 系では Vite を勧めている（事実 F4）。Worker の扱いと開発サーバーの COOP/COEP ヘッダーも、Vite なら設定だけで済む。パッケージ管理は pnpm、テストは Vitest、lint と整形は Biome、型の検査は `tsc --noEmit` にする。描画はライブラリを使わず、WebGL2 のインスタンス描画で書く。

node、pnpm、biome は mise の tools で入れる。Vite などの開発用の依存は `package.json` に書き、`pnpm install --frozen-lockfile` で入れる。

### 7.1 mise のタスク

既存の `test` と `lint` を、チェックごとのタスクに分けて束ねる形に変える。

```toml
[tasks."lint:md"]      # 既存
run = "rumdl check ."
[tasks."lint:actions"] # 既存
run = "jactionlint"
[tasks."lint:rust"]
run = ["cargo fmt --all --check", "cargo clippy --workspace --all-targets -- -D warnings"]
[tasks."lint:web"]
dir = "web"
run = ["biome check .", "pnpm exec tsc --noEmit"]
[tasks.lint]
depends = ["lint:md", "lint:actions", "lint:rust", "lint:web"]

[tasks."test:rust"]
run = "cargo test --workspace"
[tasks."test:wasm"]    # WASM で決まった状態ハッシュが出るか
run = "..."
[tasks."test:web"]
dir = "web"
run = "pnpm exec vitest run"
[tasks.test]
depends = ["test:rust", "test:wasm", "test:web"]
```

ほかに `build`（WASM と Web）、`dev`（Vite の開発サーバー）、`bench`、`bench:wasm` を置く。

### 7.2 CI

### 7.3 WASM のビルドの設定

設定は `bench:wasm` の数字を見て決めた。比べるときは、設定ごとにビルドした WASM を順番を入れ替えながら交互に測り、中央値で比べる。

- `--max-memory` は 2GiB にする。100 万人の街を作ったときの線形メモリは約 140〜160MiB で、これで足りる。
  - 共有メモリは、上限の大きさの仮想アドレスを最初に確保する。
  - iOS の Safari では、上限の大きい共有メモリで `WebAssembly.Memory` が作れなかったという報告がある（WebKit の Bug 255103）。そのため、wasm32 で指せる最大の 4GiB にはしない。報告は上限 2GiB のときのものなので、iOS で動かすときに確かめ、だめなら下げる。
- `target-feature` に `+simd128` を足す。WASM のビルドには専用のプロファイル `wasm-release`（`release` を引き継ぎ、`lto = "fat"` と `codegen-units = 1`）を使い、`build:wasm` と `build:bench-wasm` だけがこれでビルドする。ネイティブの `release` と `bench` は、ビルドが遅くならないように LTO を入れない。`opt-level` は既定の 3 のままにする。
  - 負荷の低いときに測ると、両方を入れた WASM は、どちらも入れないものに比べて 1 tick が 1〜3 割速く、大きさが約 2 割小さかった。経路の一括探索は、4 スレッドでは変わらなかった。
  - simd128 は、主要なブラウザがすべて対応している（Chrome 91、Firefox 89、Safari 16.4 から）。対応していないブラウザでは WASM を読み込めない。スレッドに要る共有メモリは Safari 15.2 から使えるので、Safari 15.2〜16.3 が新たに外れる。

## 8. テストの方針

### 8.1 決定論のテスト

- **再生**：`chizu-scenario` の街に決まった操作の列を与えて N tick 回し、状態ハッシュが記録した値（`tests/golden/*.hash`）と一致するかを見る。シミュレーションを意図して変えたときは、記録した値を同じ PR で更新する。
- **スレッド数**：同じ入力を、rayon のスレッド 1 本と 8 本で回してハッシュを比べる。
- **画面の範囲**：同じ記録を、途中で `movers_in` を違う範囲で呼びながら回し、呼ばない場合とハッシュが同じかを見る。
- **環境**：同じ入力を、ネイティブと WASM（Node で動かす単一スレッド版）で回してハッシュを比べる。
- **保存**：途中で保存して読み直し、続きを回した結果が、通しで回した結果と同じハッシュになるかを見る。
- **計算の切り替え**：速度を変えるコマンドを途中に挟んだ記録を、2 回再生して同じハッシュになるかを見る。

### 8.2 計算の細かさのあいだのずれ

同じ街を、細かい計算だけ、区間の計算だけ、一括の計算だけでそれぞれ 3 日回す。そして、3 日目の平均の通勤時間、交通量の多い上位 50 リンクの交通量、税収を比べる。ずれは細かい計算に対して ±10% 以内を合格とする。この幅は、ベンチマークの街で実際に測ってから見直す。

### 8.3 単体テスト

- 単位の型と丸め、BPR の表引き、乱数の列は、表で値を固定したテストと proptest を使う。
- 網の編集（道路を引く、交差させる、消す）は、ノードと区間とリンクの整合が保たれるかを proptest で確かめる。
- 追従、信号、衝突区間は、車線 1〜2 本の小さな場面を作って、止まる位置や通過の台数を確かめる。
- TypeScript 側は、受け渡しの符号化と、三重バッファの入れ替えを Vitest で確かめる。
