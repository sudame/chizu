# chizu 設計（最初の版）

この文書は、[要件定義](requirements.md)の「最初の版（MVP）」を実装するための設計をまとめる。外部の資料から得た事実は末尾の「参考にした事実」に出典とともに並べ、本文で使うときは「（事実 F1）」のように番号で示す。番号のない記述は、この設計での判断である。

## 全体の形

```text
┌─ メインスレッド（TypeScript）──────────┐      ┌─ Web Worker ─────────────────────────┐
│ 描画（WebGL2）  操作の受け付け         │      │ chizu-wasm（受け渡しの薄い層）       │
│   ▲ 毎フレーム読む    │ コマンド       │      │   └ chizu-core（決定論の中核）       │
│   │                   ▼ postMessage    │ ───▶ │       └ rayon のスレッドプール       │
│ SharedArrayBuffer の描画用スナップショット ◀──│  1 tick ごとに書く                   │
│ チャンク単位の静的データ（版番号つき）◀───────│  変わったチャンクだけ送る            │
└────────────────────────────────────────┘      └──────────────────────────────────────┘
```

- 中核 `chizu-core` は描画・通信・実時間の時計を知らない。入力は「種」と「コマンドの列」だけで、出力は状態と状態ハッシュである。
- 中核の中では浮動小数点を使わない。描画用の座標を `f32` に直すのは `chizu-wasm` の仕事で、その値は中核に戻らない。

## 時間の単位

中核の時間は整数の tick で数える。

| 量 | 値 | 理由 |
|---|---|---|
| 1 日 | 7,200 tick | 等速 5 tick/秒 × 1,440 秒（1 日約 24 分） |
| 時計の進み | 1 tick = ゲーム内 12 秒 | 86,400 秒 ÷ 7,200 |
| 移動の進み | 1 tick = 移動の 1 秒 | 車の追従を 1 秒刻みで解く（事実 F5 と同じ刻み） |
| 最高速 | 1,440 tick/秒（1 日 5 秒）〜 720 tick/秒（10 秒） | 要件の 144〜288 倍速 |

時計と移動の尺度をそろえると、等速でも車が 1 tick に 160m 以上進んでしまい、追従も信号も解けない。そこで、移動は時計より 12 倍遅い尺度で進める。時速 50km の車は 1 tick に約 14m 進み、5km の通勤は 357 tick（等速で約 71 秒、ゲーム内で約 71 分）かかる。等速の画面では、移動は現実の 5 倍ほどの速さに見える。

所要時間は、時計の時間ではなく移動の時間（1 tick を 1 秒として数えた時間）で測る。通勤・通学の幸福度はこの値で計算し、画面に通勤時間を出すときもこの値で出す。上の 5km の通勤なら、幸福度の計算でも画面の表示でも約 6 分（357 秒）になる。

描画は 60fps で、前後 2 つの tick のあいだを補間して滑らかに見せる。等速では 1 tick が実時間の 200ms で、12 フレームに 1 回 tick が進む。

画面の速さの段は、1 倍（5 tick/秒、1 日 24 分）、6 倍（30 tick/秒、4 分）、48 倍（240 tick/秒、30 秒）、288 倍（1,440 tick/秒、5 秒）の 4 つにする。上の帯には 1、6、48 倍と一時停止を出し、CS2 と同じく 3 段にする。288 倍は詳細の欄に置く。眺める、ふつうに遊ぶ、早送り、最高速の 4 つの使い方に 1 つずつ当て、細かい計算、区間の計算、一括の計算（3.1）のどれにも段が入るようにした。段にない速さの記録（前の帯の 4 倍や 16 倍など）を読み込んだときは、画面が最初の枠で、1 秒あたりの tick 数の比がいちばん近い段へ `SetSimSpeed` でそろえる。

## 1. 中核のデータ構造

### 1.1 単位と座標

固定小数点の汎用ライブラリ（`fixed` クレートなど）は使わず、意味ごとに整数の新しい型を作る。単位を型で分けておくと、長さと時間を取り違える誤りをコンパイル時に防げる。

```rust
pub struct Mm(pub i64);          // 長さ。ワールド座標は mm 単位の i64（要件の 64 ビット）
pub struct WorldPos { pub x: Mm, pub y: Mm }
pub struct Tick(pub u64);
pub struct MmPerTick(pub i32);   // 速さ
pub struct LaneOffset(pub u32);  // 車線の始点からの距離（mm）。1 本は 4,000km まで
```

- 移動体の位置は「車線 ID ＋車線上の距離」で持ち、ワールド座標は描画のときだけ求める。毎 tick 触るデータを 32 ビットに収めるためである。
- 符号つきの整数の割り算と剰余は、丸め方を名前に入れた関数（`div_round_half_even` など）だけで行う。符号なしの整数の `/` と `%` はそのまま使ってよい。
- `chizu-core` では、浮動小数点の混入を 2 段で止める（事実 F7）。clippy の `disallowed_types` で `f32` と `f64` を禁じ、`float_arithmetic` も deny にする。ただし、どちらも型を推論させた浮動小数点（`let a = 0.5;` や `2.5_f64.floor()`）は拾わない。そこで `scripts/check-no-float.sh` が、ソースから `f32`、`f64` と浮動小数点のリテラルを探して、見つかったら `lint:rust` を落とす。

### 1.2 チャンクと層

```rust
pub struct ChunkCoord { pub cx: i32, pub cy: i32 }   // 1 チャンク 64×64 マス = 512m
pub enum Layer { Ground = 0, Elevated = 1, Underground = 2 }

pub struct Chunk {
    pub coord: ChunkCoord,
    pub owned: bool,
    pub version: u32,                   // 中身が変わるたびに増やす。描画側のキャッシュの鍵
    pub terrain: TerrainTiles,          // 標高 u16 と水の有無。MVP は標高 0 固定
    pub layers: [Option<Box<LayerTiles>>; 3],
}
pub struct LayerTiles {
    pub occupancy: [TileUse; 4096],     // 何がそのマスを使っているか（道路、建物、空き）
    pub zone: [ZoneKind; 4096],         // 地上だけが意味を持つ
}
```

- チャンクは `BTreeMap<ChunkCoord, Chunk>` で持つ。反復の順番が座標順に決まるので、決定論を崩さない。
- メモリに置くのは、買った土地、道路や幹線が通るチャンク、画面に入ったチャンクだけである。地形は `terrain(seed, coord)` という純関数で作るので、捨てても作り直せる。
- 層は配列の添え字で持つ。MVP は `layers[Ground]` しか作らないが、高架や地下を足すときは `Some` を入れるだけで済む。
- チャンク座標を i32 で持っても、表せる広さは 10^12 m を超える。ワールド座標を i64 で持つ要件とは矛盾しない。

### 1.3 道路と歩道の網

網はチャンクに分けず、街全体で 1 つのグラフとして持つ。チャンクには「このチャンクにかかる区間の ID 一覧」だけを空間索引として持たせる。

```rust
pub struct Node    { pub pos: WorldPos, pub layer: Layer, pub control: NodeControl }
pub struct Segment { pub a: NodeId, pub b: NodeId, pub kind: RoadKind, pub lanes: SmallVec<[LaneId; 8]> }
pub struct Lane    { pub segment: SegmentId, pub dir: Dir, pub mode: LaneMode, pub length: Mm }
pub struct Connector { pub from: LaneId, pub to: LaneId, pub node: NodeId, pub signal_group: u8 }
pub enum LaneMode { Car, Sidewalk }
pub enum NodeControl { None, Signal(SignalPlan) }
```

- 区間は 8 方向（縦横と 45 度）の直線に限る。曲線は MVP では入れない。
- 区間の片側の車線をまとめた「向きつき区間」を **リンク** と呼び、経路探索と粗い計算の単位にする。リンク ID は `(SegmentId, Dir, LaneMode)` から決まる。
- 層をまたぐ移動（高架の上り口、駅の階段）は、層の違うノードを結ぶ普通の区間として表す。経路探索は層を区別しないので、高架や地下を足しても探索の処理は変わらない。
- 横断歩道は区間として持たない。3 本以上の区間が集まる交差点の、高速道路でないどの腕にも自動で付く「渡る所」とする。車線との交差は、あとで述べる衝突区間として持つ。
- ID は世代つきの添え字（`u32` の添え字＋ `u16` の世代）にする。空き番号は後入れ先出しで使い回し、使い回しの順番も決定論に従う。
- 外部接続の高速道路は、種から作る幹線として普通の区間で持ち、端に「外の世界」ノードを置く。移住者と外から来る車はここで生まれ、ここで消える。

### 1.4 区画と建物

区画は CS2 にならい、道路沿いのマスに塗る（事実 F2）。塗れるのは、建物が建ちうるマスだけである。つまり、道路に面した間口のマスと、そこから道路と反対の向きへ、塗れるマスが途切れずに続くマスである（縦横の道路なら奥へ `ZONE_DEPTH` マスまでの 1 列、斜めの道路なら間口を角にした `DIAGONAL_LOT_SIDE` マス四方）。道路から `ZONE_DEPTH` マス以内でも、道路との間に塗れないマスや別の種類の区画を挟んで切れたマスは塗れない。ここでの「塗れるマス」は、同じ塗りの範囲の中の空きマスか、範囲の外ですでに同じ種類を塗ったマスである。塗る範囲に、塗れないマスが 1 つでも混ざるときは（奥行きの外、買っていない土地、道路に面していない、建物があるなど、理由は問わない）、塗れるマスだけを塗り、結果を `AppliedPartly` で返す。道路のマスは塗る所ではないので、塗れなかったマスに数えない。1 マスも新しく塗れないときは断る。塗れなかったマスの理由が、建物か施設のあるマスのほうが多ければ `Occupied`、そうでなければ `NoZonableTile` である。chizu-cli は、買った土地や道路、建物と照らして、塗れたマスの数と塗れなかったマスの数を理由ごとに結果へ付ける。すでに塗ってある区画が、道路を消すなどで道路から切れた場合は、この判定では消さない。マスごとの `ZoneKind`（住宅・商業・工業・オフィス）を `LayerTiles.zone` に持つ。住宅を低密度と高密度に分ける持ち方は 3.9 にある。

建物は表 `Buildings` に入れる。持つのは、占めるマスの範囲、種類と段階、世帯数や職場数の上限、出入口（歩道のリンクと位置）、駐車場の台数、電気と水道が届いているかである。

電気と水道は、発電所・浄水場から道路網づたいにつながっている建物に、施設の入口から道のりの近い順に、供給量が尽きるまで届ける。供給が需要に足りないと、施設から遠い建物から届かなくなる。判定は差し替えやすい関数 1 つ（`service::evaluate_supply`）に閉じ込める。

新しい建物は、その道路網の電気と水道に余りがあるときだけ建つ。施設のない網には、小さな家が数軒建つ程度の余地（`service::UNSUPPLIED_ALLOWANCE`）しかない。

余りは道路網をまたいで足さず、主の網（需要がいちばん大きい網）の値で見る。次のどちらかに当たる施設は、孤立した施設として読み取れる（`World::isolated_facilities`）。面した道路が消えて入口がない施設と、主の網ではない網にあって余りが正なのに、主の網の余りが少ないか足りない施設である。主の網に十分な余りがあるあいだは、ほかの網に施設があっても数えない。別の町を作る遊び方で、誤った知らせを出さないためである。状態ハッシュと記録には入れない。

### 1.5 住民データの並べ方

ECS ライブラリは使わず、自前の SoA（列ごとの `Vec`）で持つ。

| 案 | 良い点 | 困る点 |
|---|---|---|
| bevy_ecs | スケジューラと変更検知がある | WASM では並列に動かない（事実 F10）。反復の順番が内部の配置に依存する。依存が大きい |
| hecs | 軽い | 部品を足し引きすると実体の並びが変わり、順番を自分で管理する必要がある。並列化の仕組みはない |
| 自前の SoA | 反復の順番が ID 順に決まる。rayon で区切って並列に回しやすい。保存と状態ハッシュも列をなめるだけで済む | 表ごとに追加・削除の処理を書く |

住民は種類の少ない固定の表なので、ECS の柔軟さはあまり効かない。決定論と保存のしやすさを優先した。

```rust
pub struct Citizens {            // 住民データ層。全員分
    pub household: Vec<HouseholdId>,
    pub age: Vec<u8>,
    pub workplace: Vec<Option<BuildingId>>,   // 職場または学校
    pub schedule: Vec<ScheduleState>,         // 次の予定と出発予定の tick
    pub happiness: Vec<HappinessParts>,       // 通勤・生活サービス・暮らし向きの 3 つ
    pub trip: Vec<Option<TripId>>,            // 移動中なら移動の ID
    pub commute: Vec<Option<u32>>,            // 通勤にかかった時間（移動の秒）を均した値
}
pub struct Households { pub home: Vec<BuildingId>, pub money: Vec<i64>, pub members: Vec<SmallVec<[CitizenId; 4]>> }
```

- 「ゲーム内の十数分に 1 回まとめて更新」は、住民を ID で 64 組に分け、毎 tick 1 組ずつ更新して実現する。1 人あたりゲーム内の約 13 分（64 tick）に 1 回になる。tick を基準にするので、速度を変えてもゲーム内の時間あたりの更新回数は変わらない。
- 出発は優先度つき待ち行列 `(出発 tick, CitizenId)` に積む。同じ tick の出発は ID 順に処理する。
- 移動層は別の表 `Trips` と、車線ごとの移動体の列に持つ（3 章）。

### 1.6 幸福度の通勤の点

通勤の点は、住民が実際に通勤にかかった時間で決める。渋滞を直すと点が上がり、遊ぶ人が手を打つ理由になるようにするためである。

- 測るのは、家を出てから職場に着くまでの時間である。移動を作った tick から、最後の歩く区切りを終えた tick までを数える。歩きも車も同じ物差しで、駐車場で車線に出るのを待つ時間や渋滞も含む。単位は移動の秒（tick）である。
- 住民ごとに `Citizens::commute`（`Option<u32>`）に持つ。職場に着くたびに、新しい 1 回を 1/4 の重みで混ぜる（`COMMUTE_SMOOTHING`）。通勤は 1 日に 1 回なので、直近の数日の様子になり、1 日だけの渋滞で幸福度は跳ねない。整数で丸め、状態ハッシュとスナップショットに入れる。
- 職場か家が変わったら、測った値を捨てる。まだ測っていない住民（越してきたばかり、職を変えたばかり）は、直線距離からの見積もり（`commute_seconds`）を使う。職のない住民は通勤の点を満点とする（前と同じ）。
- 見積もりは、家と職場の出入口の直線距離を 1,000 mm/秒（`STRAIGHT_LINE_MM_PER_SECOND`）で割る。前の 6,000 mm/秒では、ほぼ全員が満点になり、越してきたばかりの人の多い街で点が高いほうへ偏っていた。測った街で、住民ごとに「直線距離 ÷ 測った通勤の時間」を求めた中央値は、729〜1,205 mm/秒（種 512 が 1,106、第 13 回 b が 1,205、種 101 が 870、第 13 回 s が 993、種 0 が 1,011、種 311 が 862、city.rec が 729、第 13 回 b の続きが 989）で、街どうしの中央値をとると約 990 になる。これを丸めて 1,000 にした。
- 途中で消えた移動と、経路がなくその場で着いたことにした住民は、測った値を変えない。
- 歩きに切り替えた移動と、近くのほかの駐車場に回った移動は、最初の区切りの出発の tick を引き継ぐので、家を出たときから数える。
- 止まったままの車を救済で行き先に着いたことにすると、残りの走る時間は数えない。救済は 301 秒止まってからなので、測る値は少なくとも 301 秒あり、満点の境目（300 秒）をすでに越えている。そのため、この簡略は残す。
- 点は、時計で 60 分（300 秒）までは満点で、時計で 3 時間（900 秒）で 0 点になるまで一様に下がる。2 時間で 50 点である。重み（通勤 1、生活サービス 1、暮らし向き 3）は変えていないので、通勤だけで幸福度は最大 20 点下がる。のちに駐車場の点（3.7 の 4）を重み 1 で足し、暮らし向きの重みを 4 にしたので、いまは最大で 7 分の 1（約 14 点）である。

#### 境目の決め方

時計と移動の尺度（1 tick が時計で 12 秒、移動で 1 秒）は変えないので、通勤は時計の上で長く見える。そこで、境目は今の街で測った通勤の分布から決めた。
職のある住民ごとに、職場に着いた通勤の時間を平均し、その中央値と上位 10% の境目を見た（移動の秒。括弧は時計の分）。

| 街 | 中央値 | 上位 10% | 全部の移動の平均（時計の分） |
|---|---|---|---|
| 種 512 | 265（53） | 519（104） | 45 |
| 第 13 回 b（入口 2 つ） | 356（71） | 716（143） | 59 |
| 種 101 | 467（93） | 984（197） | 72 |
| 第 13 回 s（入口 1 つ） | 527（105） | 988（198） | 80 |
| 種 0 | 570（114） | 901（180） | 88 |
| 種 311 | 609（122） | 907（181） | 98 |
| city.rec | 787（157） | 1187（237） | 123 |

- 混んでいない街（種 512）の中央値が 300 秒の近くにあるので、満点の境目を 300 秒（時計で 60 分）にした。
- 0 点は 900 秒（時計で 3 時間）にした。混んだ街の上位 10% がこのあたりにある。1,200 秒（4 時間）も試したが、入口を足して通勤を直したときの通勤の点の上がりが 7.6 点と小さく、混んだ街との差も小さかった。

#### 前後の比べ方と結果

各街を、着く判定を数 mm ずらした版 5 本で回し、最後の 3〜5 日の日ごとの値を平均した。記録は前の版で遊んだものなので、所持金が少し違うだけで建てる操作が断られ、街が別物になる。前後で同じ操作が通るよう、どちらにも始めの所持金を同じだけ足した。

| 街 | 幸福度 | 通勤の点 | 人口 | 税収/日 |
|---|---|---|---|---|
| 種 512 | 84.0 → 83.0 | 100 → 94.0 | 8,780 → 8,793 | 132,795 → 132,957 |
| 種 101 | 73.6 → 70.2 | 100 → 82.2 | 9,895 → 9,910 | 152,852 → 152,624 |
| 種 311 | 83.3 → 78.7 | 100 → 76.5 | 6,063 → 6,072 | 82,936 → 82,829 |
| 種 0 | 92.5 → 87.2 | 100 → 73.0 | 8,289 → 8,260 | 42,651 → 42,546 |
| city.rec | 84.0 → 76.0 | 100 → 58.6 | 5,145 → 5,127 | 66,090 → 65,962 |
| 第 13 回 b（入口 2 つ） | 83.0 → 81.0 | 100 → 88.5 | 7,326 → 7,344 | 103,393 → 103,281 |
| 第 13 回 s（入口 1 つ） | 83.0 → 79.0 | 100 → 78.9 | 7,340 → 7,343 | 103,540 → 103,722 |

- 前は、どの街も通勤の点が 100 のままで、入口を足しても幸福度は変わらなかった。後は、入口を 1 本足すと（s → b）通勤の点が 78.9 から 88.5 に、幸福度が 79.0 から 81.0 に上がる。
- 普通の街の下がりは 1〜3 点、詰まった街（city.rec、通勤の中央値が時計で 2.5 時間）は 8 点である。人口の違いは 1% 未満で、街は崩れない。
- 移動の平均、通勤の中央値、税収は前後でほぼ変わらない。人口と職場の数がほぼ同じためである。需要もゆらぎの幅の中で動く。
- 通勤が長いだけでは、職のある世帯は出ていかない。職があり税が基準の世帯は、通勤の点が 0 でも幸福度が 56 以上あり、出ていく境目（52）を下回らないためである。駐車場の点を足した後（3.7 の 4）も、同じ世帯は自宅の枠があれば 62、車を持てなくても 52 あり、境目を下回らない。転出が増えるのは、蓄えが少ない、税が高いなど、ほかの要素と重なったときである。

## 2. 中核と画面の受け渡し

### 2.1 中核から画面へ

| 中身 | 頻度 | 渡し方 |
|---|---|---|
| 画面内の移動体（位置、向き、種類） | 毎 tick、ただし最大 60 回/秒。最高速では送らない | SharedArrayBuffer の三重バッファ |
| 時計、お金、人口、速度 | 同上 | 同じバッファの先頭に置く |
| チャンクの静的データ（道路、建物、区画） | 変わったときだけ | `postMessage` で ArrayBuffer を移譲（transfer）する |
| データレイヤーの値 | 画面に出しているレイヤーだけ、数秒に 1 回 | 同上。チャンクごとの 64×64 の配列 |

- 三重バッファは、書き込み中・最新・読み込み中の 3 枠を `Atomics` で入れ替える。中核は待たず、描画は常に最新の完成した枠を読む。
- 移動体 1 体は 16 バイト（チャンク原点からの x・y を `f32`、向きを `u16`、種類と色を `u16`、ID を `u32`）にする。2 万体で 320KB なので、毎 tick 書いても負担にならない。
- 静的データは、チャンクの `version` が描画側の手元と違うときだけ送る。描画側は「いま見えているチャンクと手元の版番号」を Worker に伝え、Worker は差分だけ返す。
- 画面の範囲は、描画側と Worker のあいだだけで受け渡す。Worker は、中核の読み取り専用の問い合わせ `World::movers_in(rect)` で、その範囲の移動体の位置を受け取る。中核は問い合わせで状態を変えないので、画面の範囲は状態にもハッシュにも影響しない。
- 中速では中核に移動体がない。`movers_in` は、区間の計算の主体の（リンク、入った tick、出る tick）から位置を補間して、描画用の移動体をその場で作って返す（3.2）。
- SharedArrayBuffer を使うので、ページは COOP/COEP ヘッダーつきで配信する必要がある。開発サーバー（Vite）がこのヘッダーを出す前提で作り、公開先は公開する段階で決める。SharedArrayBuffer がない環境の代わりの経路は作らない。

### 2.2 画面から中核へ

プレイヤーの操作はすべて `Command` に直して中核へ渡す。

```rust
pub enum Command {
    BuildRoad { from: TilePos, to: TilePos, kind: RoadKind },
    UpgradeRoad { from: TilePos, to: TilePos, kind: RoadKind },  // 直線が通る既存の区間の種類を、区間ごと変える
    Bulldoze { area: TileRect },
    PaintZone { area: TileRect, zone: Option<ZoneKind> },   // None で区画を消す
    PlaceBuilding { kind: ServiceKind, at: TilePos, rotation: u8 },
    SetSignal { node: NodeId, on: bool },
    BuyChunk { coord: ChunkCoord },
    SetTaxRate { zone: ZoneKind, permille: u16 },
    SetSimSpeed { speed: SimSpeed },
}
```

- 画面は JSON に近いオブジェクトで送り、`chizu-wasm` が `Command` に直す。値の範囲の検証は中核の `Command::validate` が行い、`chizu-wasm` はそれを呼んで不正なコマンドを捨てる。記録も同じ検証を通すので、記録に入ったコマンドは必ず読み戻せる。
- Worker は受け取った順に番号を振り、まだ step していないいまの tick に `(tick, 番号, Command)` として記録し、その場で適用する。tick T の状態は「tick が T 以下のコマンドを番号順に適用し、step を T 回済ませたもの」と決める。再生（`replay`）で T tick 進めると、最後の step のあとで tick T のコマンドまで適用して終えるので、受けてすぐ適用した状態と一致する。一時停止中も同じで、止めたまま建てられる。`World` は適用済みの記録の次の番号を状態に持ち、途中の状態から続きを再生するときは、その番号より後の記録だけを適用する。再現に必要なのは、種とこの記録だけである。
- `UpgradeRoad` は CS2 のアップグレードの道具にならい、形とノードを変えずに種類だけを変える。費用は建設費の差額で、下げても払い戻さない。区間は作り直すので ID が変わり、建物の出入口は付け直し、走っている移動は区間が分かれたときと同じく、いまの位置から経路を探し直す。車線が減って重なる車は、空くまで出発を待つ車にする。
- 計算の細かさは速度で変わり、結果も少し変わる。そのため速度の変更（`SetSimSpeed`）もコマンドとして記録する。
- 画面の範囲はコマンドにしない。見ている人ごとに範囲が違っても、同じ記録から同じ街を再現できるようにするためである。
- 一時停止は tick を進めないだけなので、記録しない。

## 3. 速度に応じた移動計算の切り替え

### 3.1 3 つの計算

| 名前 | 使う場面 | 中身 |
|---|---|---|
| 細かい計算 | 120 tick/秒まで（等速〜24 倍、1 日 1 分まで） | 移動体が車線を走る。追従、信号、横断歩道、渋滞を 1 tick ごとに解く |
| 区間の計算 | 中速（120 tick/秒を超え 360 tick/秒まで、1 日 20 秒まで） | 移動体を作らない。移動の主体はリンクの待ち行列に入り、見積もった所要時間が過ぎたら次のリンクへ移る |
| 一括の計算 | 最高速（360 tick/秒を超える速度） | 出発の時点で経路の各リンクの所要時間を足し、到着 tick を決める |

区間の計算は、リンクを待ち行列とみなす MATSim の手法にならう（事実 F3）。リンクには流せる台数（1 tick あたり）と溜められる台数を持たせ、溜まりきったら手前のリンクで待たせる。これで、渋滞が手前へ伸びる様子を粗い計算でも再現する。

速度の境目は、倍率ではなく 1 秒あたりの tick 数（120 tick/秒と 360 tick/秒）で決める。重さは 1 秒に解く tick の数で決まるので、等速の tick 数を変えても境目は動かさずに済む。境目は定数にし、ベンチマークを見て決め直す。

### 3.2 計算の選び方と中速の描画

どの計算で回すかは速度だけで決め、街全体に同じ計算を使う。画面の範囲は計算の選び方に関わらない。

移動の主体（`Trip`）は、いまどの計算で動いているかを持つ。

```rust
pub enum TripState {
    Micro { lane: LaneId, offset: LaneOffset, speed: MmPerTick, entered_at: Tick },
    Queued { link: LinkId, entered_at: Tick, exit_at: Tick },        // 区間の計算
    Scheduled { arrive_at: Tick, entered: Vec<(LinkId, Tick)> },     // 一括の計算
}
```

中速の画面に映る移動体は、`Queued` の主体から描画のためだけに作る。リンク上の位置は `(いまの tick − entered_at) ÷ (exit_at − entered_at)` でリンクの長さを按分して求める。出る tick を過ぎても先のリンクが詰まって待っている主体は、リンクの終わりから待ち行列の順に車 1 台ぶんずつ下げて並べる。どの車線に描くかは `TripId` から決める。この移動体は中核の状態に入らず、状態ハッシュにも影響しない。

### 3.3 速度の境目をまたぐときの移り変わり

- 細かい → 区間：移動体をすべて消し、いまのリンクで `Queued` にする。`entered_at` はそのリンクに実際に入った tick を引き継ぎ、`exit_at` は「いまの tick ＋残りの距離 ÷ そのリンクの平均の速さ」とする。
- 区間 → 細かい：`Queued` の主体を、3.2 と同じ按分で求めた位置に移動体として置く。前の車と重なるときは、前の車の後ろの空いた位置まで下げる。リンクの始点まで下げても空きがなければ、空きができるまで `Queued` のまま待たせる。
- 区間 → 一括：`Queued` の主体を、残りの経路について一括で見積もり直し、`Scheduled` にする。
- 一括 → 区間：`entered` から、いまいるはずのリンクと入った tick を求めて `Queued` に戻す。
- 細かい計算と一括の計算のあいだを 1 度に飛ぶときは、同じ tick の中で区間の計算を経由する。
- 移り変わりはすべて tick の頭で、`TripId` の順に処理する。

### 3.4 数字をずらさないための所要時間の表

3 つの計算は、所要時間を **リンクごとの表 `LinkStats` 1 つ** から読む。細かい計算が測った値を書き、粗い計算はそれを読むだけにする。

- 1 日を 96 の時間帯（ゲーム内 15 分、75 tick）に分け、リンク × 時間帯ごとに「測った平均の所要時間 T」と「そのときの交通量 V」を持つ。
- 細かい計算でリンクを通り抜けた移動体は、入った tick と出た tick を記録する。時間帯の終わりに集計し、過去の値と指数移動平均で混ぜる（重みは 1/4）。中速と最高速では測らないので、最後に細かい計算で測った値をそのまま使う。
- 粗い計算での見積もりは、BPR 関数（事実 F6）の比で補正する。

  ```text
  見積もり = T × BPR(いまの交通量) ÷ BPR(V)     ※測った値がないリンクは自由走行の時間 × BPR(いまの交通量)
  BPR(v) = 1 + 0.15 × (v / 容量)^4              ※整数の表引きで計算する
  ```

- 見積もりは自由走行の時間の 1〜10 倍に収める。信号の待ち時間は、測った値がないうちは周期の赤の割合 × 周期 ÷ 2 を足す。
- 区間の計算と一括の計算も、リンクに入った台数を「いまの交通量」として数える。こうすると、最高速で回しているあいだも渋滞の度合いが所要時間に反映される。
- ずれていないかは、同じ街を 3 つの計算でそれぞれ数日回し、平均の通勤時間、リンクの交通量、収入を比べるテストで確かめる（8 章）。

### 3.5 細かい計算の中身

- 車線ごとに移動体を前から順に並べた配列を持つ。追従は SUMO の既定と同じ Krauss 型の安全速度（事実 F5）を整数で解く。
- 車線の選び方は、リンクに入るときに次の曲がり方から決める。MVP では追い越しをしない。
- 1 tick の更新は 2 段に分ける。
  1. 車線ごとに、前の tick の状態だけを読んで新しい位置を求める（rayon で並列）。
  2. ノードをまたぐ移動を、ノード ID の順に 1 つずつ確定する。行き先の車線に空きがなければ止める。
- 3 本以上の区間が集まるノード（交差点）では、車は停止線で止まる。停止線の位置は画面と同じで、道路の端、横断歩道、すき間、停止線の幅に、描く車の長さの半分を足しただけノードの中心から手前にある。停止線からノードの中心を通り、出ていく腕の横断歩道を描く車の後ろの端が抜ける所までが、交差点の中の通り抜けの区間で、中核の車もこの道のりを進む。停止線を越えた車は、そのときに次のリンクで入る車線を決め、ノードを越えるまで持つ。1 マスのリンクのように、停止線が手前の交差点の通り抜けの区間の中になるときは、その区間を抜けた所で待つ。ただし、そこが先の交差点の車道の四角にかかるときは、四角の縁で待つ。譲るかを決める前に、交わる車の通る四角へ入らないためである。2 つの交差点の四角が重なるときは、待つ車は手前の交差点の四角にかかる。また、どの車も、次のリンクの終わりの交差点の停止線で止まれる速さまでしか出さない。次のリンクが短いと、ノードを越えたとたんに止まりきれない車になり、譲るかを確かめずに先の四角へ入るためである。停止線を越える前に先の四角にかかる車がいれば、交差点の中の車に数える。
- 交差点では、1. の前に、前の tick の状態だけを読んで、停止線で止める車をノード ID の順に決める。交差点の手前まで来た車線の先頭の車を優先の順に見て、交差点の中の車や先に通すと決めた車と道筋が交わるか、同じ車線へ合流するなら止める。道筋が交わるのは交差点の車道の四角の中だけなので、交差点の中の車とは、停止線を越えた車と、ノードを越えて描く車の後ろの端がまだ四角を抜けていない車である。そのうち、いまの速さのまま進んで四角を抜けるのが、手前の車がこの tick に出しうるいちばん速い速さで四角に入るより先の車は、待たない。ただし、中の車の先に、前の車や停止線のように止まりうる所が近く、四角を抜けるまでに速さを落としうるときは、この見込みを使わずに待つ。出口が詰まって中の車が速さを落とすと、見込みが外れて、交わる車が四角に同時に入るためである。同じリンクでも車線が違えば合流しない。ただし、出ていく車線の並びが入ってくる向きの並びと逆なら、道筋が交わるものとして止める。交差点の先の車線は、選べる車線が 2 本以上あるとき、左側通行に合わせて、左へ曲がる車は道路の端の車線、右へ曲がる車は中央寄りの車線にし、直進は車の少ない車線にする。2 車線から 2 車線へ曲がるときのように、入る車線が 1 本に決まるときはその車線に入る。曲がる先の車線に交差点を抜けきるだけの空きがなければ、直進と同じく車の少ない車線にする。こうすると、片側 2 車線の道路へ左と右から曲がって入る車は、別の車線へ同時に入れる。優先の順は、止まりきれない車、長く待ちすぎた車、格の高い道路の車、右折より直進と左折、待った長さの順とする。全順序なので、譲り合って誰も動かない行き詰まりは起きない。止めた車も、先の車線に空きがあれば道筋を押さえ、後の順番の車を割り込ませない。ただし、横断歩道の人だけのために止めた車は、人が渡り終えるまで交差点に入らないので道筋を押さえず、その道筋と交わる後の車を先に通す。交差点の中で止まる車を出さないよう、出ていく車線に通り抜けの区間を抜けきるだけの空きがなければ、止まりきれる車には停止線を越えさせない。停止線を越えてその車線へ向かう車も、車線の最後尾として数える。出ていく車線の詰まりが輪になって誰も動けなくなったときは、交差点の手前で 300 tick より長く待った車を行き先に着いたことにして、輪をほどく。
- 建物の駐車場から出る車は、駐車場の出入りの位置で空いた車線に置く。前の車と重なるなら、その後ろの空いた位置まで下げる。ただし、交差点の手前まで来た車線の先頭の車が交差点の先で入りうる車線では、自分の位置から車 2 台ぶんより後ろへは下げず、空くまで駐車場の中で待つ。後ろへ下げて入れると、列が進んでリンクの入口にできた空きを駐車場から出る車が先に取り、交差点の先頭の車が空きを待ち続けて、詰まりの輪ができるためである。先頭の車は先の車線のうち車の少ない車線か、曲がる向きの車線を選ぶので、駐車場から出る車を置くと選ぶ車線が変わりうる。そのため、選ぶ 1 本だけでなく、選びうる車線をすべて守る。
- 横断歩道と、道路を勝手に横切る歩行者は **衝突区間** で表す。衝突区間は毎 tick、歩行者の位置から作り直し、状態には持たない。
  - 歩行者は、どちらの向きに歩いても建物の側の歩道を歩く。交差点で側を変えるときは、交差点のまわりを渡る腕の少ない向きに回り、通る腕の横断歩道を順に渡る。高速道路の腕は渡らずに回る。
  - プレイヤーは、交差点の腕ごとに横断歩道を外せる。外した腕は、腕の向きの印としてノードに持つので、区間を分けても種類を変えても残り、腕を取り壊すと消える。歩行者は、外した腕も高速道路の腕と同じく渡らずに回り、次の交差点で外した腕を避けられる側へ先に移っておく。どちらに回っても越えるときだけ、横断歩道があるときと同じく車を止めて渡る。高速道路の腕を車を止めずに越えるのは、外した腕を渡っても回れないときだけである。交差点で渡り始めた人の道のりは、渡り終えるまで変えない。経路を選ぶときは、そうして越える腕 1 本ごとに 100m の固定の費用を足すので、ほかの交差点を回る遠回りがそれより短ければその交差点を避ける。外した腕を渡るのは回れない人だけになるので、そこを通る車は、ほとんど止まらなくなる。
  - 車は、交差点で入る腕か出る腕の横断歩道に人がいれば、停止線で止まる。停止線を越えた車と、ノードを越えて出ていく腕の横断歩道をまだ抜けていない車は、交差点の中にいるとみなす。区間の途中の衝突区間では、その手前で止まる。止まりきれない車は止まらない。
  - 歩行者は、止まりきれない車が来ているあいだと、交差点の中に車がいるあいだは渡り始めない。信号のない交差点では、手前まで来た車を先に通す。信号のある交差点では、歩行者も信号に従い、そのうえで手前まで来た腕が青の車を先に通す。渡ってよい横断歩道へ来るのは、青の軸から曲がってくる車である。曲がる車が渡り続ける人に止められると、同じ車線の後ろの直進まで青を使えなくなるためである。先の車線の最後尾が止まっていて交差点を抜けきる空きがない車は、動く見込みがないので先に通さない。信号のある交差点の歩行者も、次の項の順番の決まりで先に渡る。待った長さには、赤を待った tick と、渡ってよいあいだに車を待った tick を合わせて数える。
  - 人と車は、待った長さで順番を回す。渡り始めるのを 40 tick 以上待った歩行者がいる横断歩道では、止まりきれる車を止め、待っていた歩行者をまとめて渡らせる。ただし、横断歩道の人に譲ってその歩行者より長く待った車がいれば、その車を先に通す。交差点の中で止まった車がいるあいだは歩行者が渡れないので、手前の車を止めない。止めると、先の詰まりと輪になりうる。車の待ちは、横断歩道の人のために止まった tick 数で数える。人に譲るあいだに先に通した交わる車を待つ tick も数える。ほかの車や先の車線の空きだけを待つ tick は数えないが、それまでに数えた待ちは、交差点の手前で止められているあいだ残す。人に譲ったことのない車は歩行者を止めない。こうして、車が途切れない交差点でも歩行者はいつか渡れ、歩行者が途切れない交差点でも車はいつか進める。
  - 区間の途中で横切る歩行者も、40 tick より長く待てば、止まっている車のすぐ前を横切る。横切る所に車がかかっていなければ、止まりきれる車にその前を空けさせる。かかっている所で空けさせないのは、空けさせた所どうしが互いを待ち続けないためである。
  - 区間の途中で横切るのは、出発と行き先が同じリンクの上にあり、建物が道路の反対の側どうしのときだけである。経路を選ぶときは横切りに 100m の固定の費用を足すので、近くの横断歩道までの遠回りがそれより短ければ横断歩道を使う。
- 信号は感応式とする。骨組みは固定の周期で、どの軸の段階にいるかは `(tick + ノードごとのずらし) mod 周期` で決める。そのうえで、tick を進める前の車と歩く人の位置から、青を渡す先を決める。段階の軸の手前に車が来ていなければ、車の来ている次の軸へ青を渡すので、段階の青の長さ（30 tick）は上限になる。ほかの軸の腕を渡ろうと待つ人がいるあいだは渡さない。止まりきれない車のいる軸は、どの段階でもその tick は黄にし、青はその車が抜けてからほかの軸へ移す。信号は状態を持たず、灯火はいまの tick と移動の主体の位置だけで決まる。画面に出す灯火は、移動の主体の表が控えた、直前の tick に効いた様子から求める。
- 駐車は、建物の駐車場の台数だけを持つ。満車なら近くの別の建物の駐車場へ回り、そこから歩く。路上駐車は MVP では入れない。駐車場の台数、出入り、描き方は 3.6 に書く。

### 3.6 建物の駐車場

人間のフィードバック（#210）から起こした設計である。車を、建物の敷地の中の駐車場に停め、路肩には停めないようにする。地図では、敷地を切り欠いた駐車場と、停まっている車を描く。

#### 今の作り

中核には、建物ごとの駐車場がすでにある（`movement/parking.rs`）。

- 建物ごとに、停めてある台数と、向かっている車のために押さえた台数（`Lot`）を持つ。台数の上限は `Building::parking_spaces` で、`Building::parking_layout` の平面と建物の中の台数の和である。決め方は後述の「台数の決め方」にある。4×4 マスの段階 5 の住宅なら 20 台（平面 14 台、建物の中 6 台）、オフィスなら 40 台になる。
- 行き先の駐車場は出発のときに決めて押さえる。満車なら、行き先から 16 マス（`PARK_RADIUS`）の中で空きのある、いちばん近い建物の駐車場にする。どこも満車なら車では行かず、歩く。
- 住民ごとに、車を停めた駐車場を覚える（`Commuters::cars`）。
- 世帯ごとに、車を置く枠（`CarPlaces`）を持つ。住宅の駐車場に停められるのは、その建物の自宅の枠を持つ世帯の車だけである（3.7 の 3）。
- 遊ぶ人が置く共同の駐車場もある（3.7）。駐車場は `LotId` で指し、建物の駐車場（`Building`）、共同の駐車場の外来の枠（`Shared`）、世帯が借りた枠（`Rented`）を分ける。共同の駐車場は占める範囲の最小の角のマスで指す。

敷地の切り欠きの形（`Building::parking_layout` と `lot_end`）、車の出入り（`lot_spot`）、停まっている車の描画は、すでに作ってある。

- 着く車は駐車場の出入りの位置から入り、車線の上では止まらない。出る車は駐車場の中で待ち、空いた車線に入る。
- 地図には、切り欠いた駐車場の面と枠、停まっている車を描く。
- 建物の中の駐車場に停めてある台数は、寄りと細部の段で、建物の中心に「P」と数字で出す。

足りないのは、検査の欄に平面と建物の中の台数を出すことである。これは別の Issue で扱う。

#### CS2 の作りと、chizu で取るもの

| CS2 の作り | chizu の扱い | 理由 |
|---|---|---|
| 行き先の建物の駐車場に停めるのが、いちばん快適な選び方である。停められなければ、ほかの駐車場か、ほかの手段を選ぶ（事実 F11） | 取る。今の作りのとおり、行き先、近くの駐車場、歩きの順にする | CS2 に近づける |
| 駐車場が足りないと、住民はその場所での活動を避けるようになる（事実 F11） | 今は取らない。行き先を選び直す仕組みが chizu にはまだないので、歩きへの切り替えで代える | 行き先の選び方を変える大きな変更になる |
| 路肩の駐車。地区ごとに路肩の駐車料金を決められる（事実 F11）。路肩の駐車枠の多い道路もある（事実 F12） | 今は取らない。路肩には誰も停めない。宅配と送り迎えの短い停車は、後で別に足す（#214） | 日本の街の慣習に合わせる（後述）。路肩で止まる車は詰まりの元でもある |
| 駐車場と建物ごとの駐車料金。料金は経路の費用に入り、料金が高いと豊かな住民だけが停める（事実 F11） | 今は取らない。後で別に足す（#215） | 経路の費用に、お金の重みをまだ入れていないため（5.1）。入れるときに、駐車料金も一緒に入れる |
| 置いて使う駐車場と、駐車場ビル（立体駐車場）。駐車場ビルは増築で 300 台まで増える（事実 F12） | 今は取らない。施設として置けるようにするのは、後で別に足す（#216、設計は 3.7） | 建物ごとの駐車場が先にないと、足りない場所が分からない |
| 建物の地下や立体の駐車場 | 取る。大きい建物は、切り欠いた平面の駐車場に入りきらない台数を、建物の中に持つ | 描けない台数を数字で出す形と合う |

日本の街の慣習も入れる。

- 車を持つには、道路の外に保管場所（車庫）が要る。道路を車庫の代わりに使うことと、同じ場所に長く停めておくことは、法律で禁じられている（事実 F13）。そのため、自家用車は駐車場に停めるのが普通である。
- 路肩に停まるのは、宅配の車と、短い一時停車だけである。
- 大きい建物には、条例で駐車場を付けることが義務づけられている地域が多い（事実 F13）。

chizu には、宅配の車も一時停車もまだない。そのため、路肩の駐車は今は作らない。宅配の車や送り迎えを足すときに、「路肩の短い停車」として足す（#214）。そのときは、#100 の合流と #192 の停止線との関係を測ってから決める。

「歩く人の多い街」の前提（CS2 より歩く人が多い）にも合わせる。駐車場は、CS2 のように足りなくなるまで車を呼び込むものにはしない。建物の大きさに見合った台数にとどめ、あふれた車の分は歩く人に回す。

#### 台数の決め方

台数は、建物の種類、マスの数、段階から決まる純粋な関数にする（`Building::parking_layout`）。状態には持たない。

まず、要る台数 N を決める。

| 種類 | 要る台数 N | 考え方 |
|---|---|---|
| 低密度の住宅（段階 1〜2） | 世帯の数 × 1。1〜2 マスの家の 3 軒に 1 軒は 0 | 戸建て。1 世帯に 1 台の車庫。持たない家は 3.7 の 1 |
| 高密度の住宅（段階 1〜5） | 世帯の数 × 0.5（切り上げ） | 集合住宅。段階を問わない。足りない世帯は共同の駐車場を借りる（3.7 の 1） |
| 商業 | 職場の数 × 1 | 働く人と客の分 |
| オフィス | 職場の数 × 0.5（切り上げ） | 街中のオフィスは、歩いて来る人が多い前提にする |
| 工業 | 職場の数 × 1 | 郊外の工場は、車で通う人が多い |

職場の数は `Building::workplaces`（税で減らす前）を使う。税率で台数が変わると、停めてある車が上限を超えるためである。

次に、N を敷地の平面の駐車場と、建物の中の駐車場に分ける。

- 平面の駐車場は、1 マスに 3 台とする。駐車の枠は 2.5m × 5m（事実 F14）で、8m の幅に 3 つ並ぶ。
- 平面に使えるマスは、建物のマスの 1/3（切り捨て）までにする。建物の本体を敷地の 2/3 より小さくしない。ただし、1〜2 マスの建物は、道路に面した側の奥行き 5m の帯を使える（後述の「前面の帯」）。
- 平面に入りきらない分は、建物の中（地下か立体）に持つ。ただし、戸建て（低密度の住宅）は建物の中に持たない。入りきらない分は切り捨てる。
- 集合住宅（高密度の住宅）も、平面に入る分を先に平面に置く。高密度の段階 1〜2 も同じである。区画に建つ大きさ（1 辺 4 マスまで）で縦か横の道路に面していれば、どれも平面に収まる。
- 斜めの道路に面した建物は、切り欠かない。台数はすべて建物の中に持つ。戸建ても同じで、建物の中の車庫として、ほかの戸建てと同じ 1 世帯 1 台を持つ。自宅の駐車場を持たない家（3.7 の 1）は、斜めの道路に面していても車庫を持たない。

集合住宅の台数は、はじめ世帯の数 × 0.7 にしていた。車を持つ世帯の割合（`CAR_OWNERSHIP_PERCENT`、70%）に合わせたものである。ところが、車を持たない世帯も 500m 以上なら車で向かう（後述の「車の持ち方」）ので、世帯の車は世帯の数だけある。住宅の駐車場はその建物の住民だけが使うので、近くに建物を足しても直らない。遊ぶ人に打つ手がないまま、駐車場の足りない建物の上位を集合住宅が占めていた（#258）。

そこで、集合住宅も世帯に 1 台にし、増やした分を建物の中（地下）に持った（#264）。そのあと、共同の駐車場（3.7）が打つ手になったので、集合住宅の台数を世帯の数 × 0.5 に減らし、建物の中の分をなくした（3.7 の「既存の作りから移る道」）。

- 段階は上がるだけで、下がらない。台数は世帯の数とともに増える。
- 戸建てか集合住宅かは密度で決まり、段階が上がっても変わらない（低密度は段階 2 で止まる）。そのため、台数が段階の上昇で減ることはない（3.9 の 5）。

#### 敷地の切り欠き方

切り欠く形は、建物の大きさで 2 つに分ける。

| 形 | 使う建物 | 形 | 出入りの位置 |
|---|---|---|---|
| 前面の帯 | マスが 1〜2 の建物 | 道路に面した辺に沿った、奥行き 5m（0.625 マス）の帯。長さは要る枠の数だけにする。枠は道路に直角に並べる。帯のある所だけ、建物の本体が奥に下がる | 帯の真ん中 |
| 脇の駐車場 | マスが 3 以上の建物 | 間口の端の 1 列を、道路の側から奥へ必要なマスだけ切り欠く。1 列の幅 8m を、枠の奥行き 5m と通路 3m に分け、枠を通路に沿って並べる | 切り欠いた列の、道路に面した辺の真ん中 |

- 脇の駐車場の列の数は、平面に使えるマスに収まるだけにする。1 列の奥行きで足りなければ、隣の列も使う。
- どちらの端の列を切り欠くかは、面した道路の、近い交差点から遠い側にする。同じなら座標の大きい側にする。出入りの位置を、交差点の手前の停止線（#192）と、描画で歩く人の位置を写し替える窓（#204、10m）から離すためである。
- 前面の帯も、同じ決まりで間口の端に寄せる。帯は端の外側の辺から内へ枠の数だけ延び、出入りの位置はその真ん中になる。
- 交差点は 3 本以上の区間の集まるノードとし、出入りの位置のある車のリンクの両端のノードだけを見る。曲がり角やつなぎ目のノードの先へは見に行かない。両端とも交差点でなければ、座標の大きい側にする。
- 出入りの位置が道路の上に取れないとき（行き止まりの端のマスで、帯の真ん中が道路の外に出るときなど）は、端のマスの真ん中にする。それも取れなければ、建物の出入口にする。
- 間口は、隣り合うだけでつながっていない 2 本の道路にまたがりうる。出入りの位置は、出入口の区間と同じ区間か、端のノードでつながる区間に取る。出入口から歩道で届かなければ、出入口にする。
- 切り欠きは描き方と出入りの位置を決めるだけで、建物の占めるマス（`area`）は変えない。世帯の数と職場の数も変えない。建物は、残りの敷地で上へ伸びると見なす（「決めたこと」の 1）。

#### 中核の状態の持ち方

停めてある車は、今と同じく建物ごとの台数だけで持つ。1 台ずつの車は持たない。

- 停めてある車の位置と色は、描画の側が台数から決める。枠は出入りの位置に近い順に埋める。色は、建物の正面のマスと枠の番号から決める。誰の車かは描かない。
- 駐車場の配置（形、枠の数、建物の中の台数、出入りの位置）は `Building` から計算で求め、状態にも状態ハッシュにも入れない。

出入りの位置を、建物の出入口の前から、駐車場の出入りの位置へ移す。

- `Then::Drive` の `park_at` を、出入りの位置の車のリンクの上の点にする。降りた人は、そこから歩道を歩いて建物の出入口へ向かう。前面の帯なら同じマスの中なので、数 m 歩くだけになる。
- 出る車も、出発の建物の駐車場の出入りの位置から出す。乗る人は、建物の出入口から出入りの位置まで歩道を歩いてから車に乗る。自分で停めた車が別の建物に停めてあるとき（満車で近くに停めたときなど）は、今と同じく出発の建物から出す（今の作りの簡略をそのまま残す）。
- 平面の駐車場のない建物（斜めの道路に面した建物）は、建物の中の駐車場に出入口から出入りする。

着く車は、車線の上で止まらずに駐車場へ入る。

- 経路の最後のリンクでは、出入りの位置へ「入る速さ」（時速 7.2km、2,000 mm/tick）まで落とし、出入りの位置に届いたら車線から外れて停める。今のように速さ 0 まで落として車線をふさがない。後ろの車は、入る車の減速にだけ付き合えばよい。
- 減速は、減速の上限（`CAR_DECEL`）の内で行う。出入りの位置が最後のリンクの始まりに近いときに間に合うよう、手前のリンクを走っているあいだも、出入りの位置までの距離を見て落とす。
- 道路の反対の側の駐車場に入る車（左側通行で右に折れて入る車）も、今は同じ扱いにする。対向の車線を横切る判断は入れない。

出る車は、駐車場の中で待ち、空いた車線に入る。

- 今の `waiting` の車を、そのまま「駐車場の中で出る順番を待つ車」とする。待っているあいだは車線の外にいて、流れを止めない。
- 車線に入るときの決まりは、#206 の路肩からの入り方とそろえる。空いた車線に置き、前の車と重なるなら後ろへ下げる。交差点の手前まで来た車線の先頭の車が交差点の先で入る車線では、車 2 台ぶんより後ろへは下げず、駐車場の中で待つ。待ち続けたら歩きに切り替える（今の救済のまま）。
- 置く位置は、出入りの位置にする。建物の出入口の位置ではない。

駐車場がいっぱいなときは、次の順に試す。

1. 行き先の建物の駐車場。
2. 行き先から 16 マスの中の、ほかの建物の駐車場を近い順に。住宅の駐車場は、その建物の自宅の枠を持つ世帯の車だけが使える（「決めたこと」の 2 と、3.7 の 3）。商業、オフィス、工業の駐車場は誰でも使える。
3. どこも満車なら、車では行かずに歩く（今のまま）。

住宅の駐車場の決まりは、行き先と近くの候補の両方に効く。店や職場に車で来た人は、行き先の近くの住宅の駐車場に停めない。住民は、行き先が自分の家か、自分の家が行き先の近くにあるときに、自分の家の駐車場に停める。

路肩には停めない。歩きに切り替わった数と、近くへ回った数は、`rescues` と同じく読み取り用に数える。

#### 車の持ち方

車は世帯ごとに 1 台にする。世帯の中で同時に車を使えるのは 1 人だけで、ほかの人は歩く。公共交通を足したら、そちらにも回す。

- もとは、車を住民 1 人ごとに持っていた。一方、住宅の台数は世帯の数で決めている（1 世帯に 1 台）。車を持つ世帯の働く人がみな自分の車で帰るので、住宅の駐車場が毎晩ほぼ満車になっていた。
- 台数を住民の数に合わせて増やす案（住宅の台数を 2 倍）も測った。止まっている車と救済が main より増え、目安（1.05 倍）を外れた。
- 世帯に 1 台は、日本の世帯の車の持ち方に近く、「歩く人の多い街」の前提にも合う。

世帯の車のいる所を、世帯ごとに覚える（`Commuters::cars`、`HouseholdCar`）。

- 停めてあるときは、駐車場と、停めた住民を覚える。移動が使っているときは、その移動を覚える。
- 車を使えるのは、家に停めてある車に家から乗るときか、自分で停めた車のときである。家に停めてある車は、家から出る世帯の誰でも使える。職場など家でない所に停めた車は、同じ職場で働く世帯の人がいても、停めた本人だけが使える。
- ほかの住民が乗っているときや、離れた所に停めてあるときは、車がないものとして歩く。この数を読み取り用に数える（`ParkingTally::no_car`）。
- 同じ tick に同じ世帯の住民が出るときは、出発の依頼の順で先の住民が車を使う。
- 車で走っているあいだに、車を停めずに移動が終わったとき（歩きへの切り替え、救済、行き先の建物が消えたときなど）は、車はどこにもないものとする。次に車で出る住民の出発の建物から車が現れる。世帯の車がまだどこにもない街の始まりも同じである。
- 車を持たない世帯（`CAR_OWNERSHIP_PERCENT` の外の 30%）も、500m 以上なら今のまま車で向かう。これも世帯に 1 台として数える。公共交通がないあいだの代わりである。
- 住民の職場が変わるかなくなったら、その住民が家でない所に停めた車は、どこにもないものに戻す。車で向かっているあいだに変わったときは、着いて移動が終わったときに、着いた所に停めた車を戻す。前の職場に停めたまま残すと、本人はもうそこへ行かず、世帯のほかの人も車を使えないままになるためである。
- 世帯が街を出ると、停めてある車も駐車場から外す。

保存データとゴールデンは次のように扱う。

- 状態の形は、進める順の 1 で読み取り用の数を足したときと、3 で車を世帯ごとに持つように変えたときに変わった。どちらの PR でも `SNAPSHOT_VERSION` を上げた。
- 記録の形式は変えない。コマンドを足さないので、`FORMAT_VERSION` も変えない。
- 台数の式と、着く車の速さが変わるので、シミュレーションの結果が変わる。ゴールデンを `CHIZU_UPDATE_GOLDEN=1` で書き直し、同じ PR に含める。
- 前の版で保存した街は、記録を再生すると別の街になる。読み込んだときに、保存したハッシュと食い違うことを画面に示す（今の仕組みのまま）。

#### 地図の描き方

地図の見た目の決まり（[map-style.md](map-style.md)）の総描の考え方に合わせる。引くほどまとめ、寄るほど 1 台ずつの生活を見せる。

| 段 | 描くもの |
|---|---|
| 引き | 描かない。街区の面に含める |
| 標準 | 切り欠いた所を、駐車場の淡い面で塗る。枠と車は描かない。建物のまとまりの中の、建物の建っていない所として見える |
| 寄り | 駐車場の面に、枠の白線と、停まっている車を描く。駐車場の中で出る順番を待つ車も、空いた枠か出入りの位置に描く。建物の中の台数は数字で出す |
| 細部 | 停まっている車に、走る車と同じ窓と屋根を描き足す |

- 枠と停まっている車は、車と人が現れるのと同じ倍率 12〜16 で溶け込ませる。倍率 12 では 1 つの枠の幅が 3.75px しかなく、枠の白線は描き分けられないためである。
- 停まっている車は、走る車と同じ角丸の長方形を、枠に合わせて向きを変えて描く。色は移動体の色の表から選ぶ。
- 出る車と着く車は、駐車場の出入りの位置と車線のあいだで、描くずれを移す。歩道の上で止まって見える車はなくなる。
- 数字は、寄りと細部の段で、建物の中に停めてある車がある建物の、敷地の中心に出す。日本の駐車場の案内と同じく、青い角丸の盾に白い字で「P」と、建物の中に停めてある台数を出す（例：`P 12`）。建物の中の台数は、平面の枠を先に埋めるものとして、停めてある台数から平面の台数を引いた分である。ラベルの重なりの優先は、地区（寄り）より低い最後にする。
- 平面の駐車場だけの建物は、車そのものが台数を伝えるので、数字を出さない。

| もの | 色 |
|---|---|
| 駐車場の面 | `#e3e1dc` |
| 駐車場の縁 | `#c9c4b9`（1px） |
| 枠の白線 | `#ffffff`（1px） |
| 「P」の四角 | `#1a73e8` に白の字 |

駐車場の面の色は、地面（`#f4f2ec`）と歩道（`#e6e2d8`）の両方と見分けられるよう、少し暗くした。見本を作って確かめ、合わなければ描画の PR で選び直す。

描画に渡すものは次のとおりである。

- 駐車場の配置は、建物の静的データ（チャンクの版番号で送る）に足す。建物が建つか、段階が変わるときだけ変わる。
- 停めてある台数は、見えているチャンクの建物の分だけを、1 秒に 1 回ほど送る。毎 tick 変わる値ではないので、三重バッファには入れない。状態は変えない。

`chizu-cli agent` は、observe に駐車場の埋まり具合（種類ごとの台数と停めてある台数、満車の建物の数、近くへ回った数、駐車場がなくて歩いた数）を足す。map の凡例には、切り欠いた駐車場のマスの文字を足す。

#### 駐車場が足りないことの知らせ

満車で車をやめた数は、行き先の建物ごとにも数える（`Trips::lot_misses`、`LotMisses`）。近くへ回った数も同じである。

- 数えるのは、`ParkingTally` の `lots_full` と `parked_elsewhere` を増やす所である。行き先にした建物に、ゲーム内の今日と前の日の 2 日ぶんだけを持つ。日が 2 つ以上空いたら捨てる。
- `ParkingTally` と同じく、状態ハッシュには入れず、スナップショットには入れる（`SNAPSHOT_VERSION` を上げた）。読み取りだけで済む作りは取れなかった。やめた移動は残らず、あとから建物ごとに数え直せないためである。
- 駐車場が足りない建物は、今日と前の日の満車で車をやめた数の和が `SHORTAGE_LOTS_FULL`（3）以上のものとする。前の日までを入れるのは、日の変わり目で知らせが消えたり出たりしないようにするためである。
- 画面は、その建物を種類ごとに数えて「駐車場が足りない建物がある（商業 3 棟）」と知らせ、押すたびに次の建物へ寄る。ほかの区画や施設の知らせ（#217）と同じ通知センターに並べる。
- observe の `parking.shortages` は、満車で車をやめた数の多い順に上位 10 件を出す。`byZone` には、押さえた分を含まない `parkedPermille` を足した。
- 需要や幸福度には響かせない。それは #236 と合わせて決める。

2. 道路の反対の側の駐車場へ入る車と、そこから出る車に、対向の車線を横切る判断を入れるか。今は入れない。

### 3.7 共同の駐車場

人間の方針（#216）から起こした設計である。駐車場の不足を遊びの要素にする。自宅に駐車場のない世帯が、近くの共同の駐車場（月極）の枠を借りて車を持つ。遊ぶ人は、共同の駐車場を施設として置いて、不足を埋める。

人間の方針では、幸福度に関わるのは次の 3 つである。

- 駐車場が足りず、車を持てない。歩くか、公共交通を使うしかない。
- 駐車場が自宅から遠い。
- 駐車場が高い。

各項目の判断には、次の印を付ける。

- 【マネージャー】：要件、人間の方針、「CS2 に近づける」の範囲で、マネージャーが決めてよい。
- 【マネージャー：決定】：この基準だけでは決められないか、要件に触れる項目である。人間から任され、マネージャーが決めた。

理由は、人間の方針、CS2 に近づける、歩く人の多い街が楽しいか、決定論と整数で作れるか、の 4 つで書く。CS2 にない形は、日本の街らしさとして人間が求めたもの（自宅に駐車場のない家と、月極の駐車場）に限る。

#### 今の作りとの違い

3.6 の作りでは、どの建物も自分の駐車場を持ち、住宅の駐車場は世帯に 1 台ある（#264）。住宅の駐車場は早い者勝ちで、満車ならその住民は車で帰れない。遊ぶ人が駐車場を足す手はない。

この節では、次の 3 つを変える。

1. 世帯ごとに、車を置く枠（自宅の枠か、共同の駐車場の枠）を結び付ける。枠のない世帯は車を持たない。
2. 遊ぶ人が、共同の駐車場（平面と立体）を施設として置ける。
3. 一部の家は、自宅の枠を持たない。持たない世帯が共同の駐車場を借りる。

#### 1. 自宅の枠を持たない家

| 住宅 | 自宅の枠 | 切り欠き |
|---|---|---|
| 戸建て（低密度）で、1〜2 マス | 3 軒に 1 軒は持たない。ほかは 1 台 | 持たない家は前面の帯を切り欠かず、建物が道路の際まで出る |
| 戸建て（低密度）で、3 マス以上 | 世帯の数 × 1（今のまま） | 今のまま |
| 私道の敷地（3.8） | 家ごとに 1 台（今のまま） | 今のまま |
| 集合住宅（高密度。段階を問わない） | 世帯の数 × 0.5（切り上げ） | 平面に入る分を先に平面に置き、入らない分だけ建物の中に持つ |
| 商業、オフィス、工業 | 今のまま | 今のまま |

- 持たない戸建ては、種と建物の正面のマスを混ぜた値（`rng(seed, 用途, 正面のマス)`）で決める。建物の ID で決めると、建て直したときに同じ場所の家の性質が変わるためである。状態には持たず、`Building::parking_layout` の純粋な関数のままにする。
- 自宅の枠は、`parking_layout` の台数（平面と建物の中の和）とする。住宅の駐車場は、その建物の自宅の枠を持つ世帯の車だけが使う。
- 段階が上がって世帯が増えると、自宅の枠の足りない世帯が出る。街が育つほど共同の駐車場が要るようになり、不足は少しずつ現れる。

理由：

- 人間の方針：日本の家には、自宅の駐車場がない家も多い。狭い敷地の戸建てと、駐車場の設置台数が世帯の数より少ない集合住宅が、その典型である。
- 遊びの面：始めたばかりの戸建ての街で、不足を一度に出さない。密度が上がるにつれて手を打つ場面が増えるので、打つ手（共同の駐車場）と不足の大きさが釣り合う。
- 見た目（#270）：切り欠きの多くは、1〜2 マスの戸建ての前面の帯と、集合住宅の脇の駐車場である。どちらも減るので、地図の駐車場の面も減る。
- 決定論：割合は整数の比（1/3、5/10）で、乱数は種と位置だけから引く。

判断：

- 持たない家の種類（狭い戸建てと集合住宅）【マネージャー】。人間の方針の「自宅の駐車場がない家」を、日本の街の典型に当てはめた。
- 割合の初期値（戸建て 1/3、集合住宅 0.5）【マネージャー】。3.6 の係数と同じく、測った数字を見て決め直す。

作る順の 4 で決めた細部：

- 持たない家の乱数の用途は `RngPurpose::HomeParking` で、混ぜる値は正面のマスの x と y である。混ぜた値が 3 で割り切れる家が持たない。1〜2 マスの戸建てなら、斜めの道路に面した家も同じ決まりで持たない（車庫も持たない）。
- 私道の敷地は 3 マス以上の戸建てなので、家ごとに 1 台の枠を持つままにした（3.8 の「私道、家、枠の置き方」）。
- 戸建てが段階 3 に上がって集合住宅になると、自宅の枠が減りうる（4×4 マスなら 8 台から 6 台）として作った。枠の数を超えた世帯は ID の大きい世帯から枠を返し（3 の 1）、停めてある車は駐車場から外す。家へ向かっている車は、着いても停めずに押さえた空きを返す。戸建てを密度で決めるようにした（3.9 の 5）あとは、この場面は起きない。枠を返す仕組みは、枠の数が減る別の場面（駐車場を壊したときなど）のために残す。
- 種は `World` が持つ。`Building::parking_layout` は種を引数に取り、建物の表（`Buildings`）は種を写して持つ。写しは書き出しに入れず、読み戻したときに `World` の種から写し直すので、状態の形は変わらない。
- 割合は初期値のまま（戸建て 1/3、集合住宅 0.5）にした。測った数字（下の「測り方」の窓、少しずらした版 5 本の平均）では、(a) 共同の駐車場を置かなくても人口は main の 0.99〜1.01 倍で、需要と税収も大きくは動かなかった。家のある世帯の 36〜46% が車を持てなくなり、通勤の車の割合は 44〜50% から 26〜29% に下がった。車が減るので、止まっている車は main の 0.04〜0.27 倍、救済は 0〜0.25 倍になった（車の少ない種 311 と種 512 は main でもほぼ 0）。
- (b) の手順は、`parking.carlessAreas` の上位 10 件の区切りごとに、車を持てない世帯 12 世帯に 1 つ（4 つまで）の平面の駐車場を、区切りの真ん中から近い順（24 マスまで）に置ける所へ置き、60 tick 進めて借りさせる。これを、車を持てない世帯が 1 割を切るか、1 つも置けなくなるまで繰り返す。区画を塗ったマス（とその 2 マスのまわり）には置かない。育った街では区画を塗っていない空き地がほとんどなく、置けたのは 0〜23 か所で、車を持てない世帯は 29〜45% に残った。止まっている車と救済は main の 0.42 倍以下で、人口は 0.98〜1.01 倍だった。区画を塗った空きマスにも置く手順を 1 本ずつ試すと、置けた数は増えたが、建物の建つ土地が減って人口が main の 0.79〜0.98 倍に下がった。

#### 2. 共同の駐車場の形

置く施設は 2 種類にする。`ServiceKind` に足し、発電所と浄水場と同じく `PlaceBuilding` で置く。

| 種類 | 大きさ | 台数 | 建設費 | 維持費（1 日） | 1 台あたり |
|---|---|---|---|---|---|
| 平面の駐車場 | 2×2 マス | 12 台（1 マスに 3 台） | 3,000 | 96 | 建設 250、維持 8 |
| 駐車場ビル | 4×4 マス | 240 台（1 マスに 3 台 × 5 層） | 72,000 | 2,880 | 建設 300、維持 12 |

- 台数は、3.6 の平面の駐車場と同じ 1 マス 3 台（枠 2.5m × 5m と通路）から決める。駐車場ビルは 5 層とする。
- 1 台あたりの費用は駐車場ビルのほうが高く、そのかわり 1 マスあたりの台数は 5 倍になる。土地の狭い所では駐車場ビル、広い所では平面、という選び方が生まれる。CS2 でも、駐車場ビルは土地を節約する手段である。
- 比べる値は発電所（建設費 60,000、維持費 1,200）と、住民 1 人の住宅の税（基準の税率で 1 日 10〜18）である。駐車場ビル 1 つは発電所と同じくらいの重さの決断にした。
- 出入りの位置は、3.6 の脇の駐車場と同じ決まりで、面した道路の、近い交差点から遠い側の端にする。
- 電気と水道の需要は持たない。供給の判定（`service::evaluate_supply`）では数えない。
- 増築（CS2 の駐車場ビルは 300 台まで増える）は今は入れない。施設を増築する仕組みが chizu にまだないためである。

料金：

- 料金は、借りた枠 1 つあたりの 1 日の額で、街で 1 つにする。遊ぶ人が税率と同じように決める（新しいコマンド `SetParkingFee`）。初期値は 10、範囲は 0〜50 にする。
- 初期値の 10 では、平面の駐車場は満車でやや黒字（収入 120、維持費 96）、駐車場ビルは満車でも赤字（収入 2,400、維持費 2,880）になる。駐車場ビルを黒字にするには料金を 12 以上に上げる必要があり、上げると借りる世帯が減る（後述）。財政と幸福度の取引になる。
- 料金は街の所持金に入る。収支（`World::finances`）の収入に「駐車場の料金」、支出に「駐車場の維持費」の行を足す。
- 世帯の蓄えからは引かない。世帯の蓄えは越してきたときに決まり、出入りの流れがまだないためである。料金の重さは、借りるかどうか（3）と幸福度（4）で効かせる。

理由：

- CS2 に近づける：置いて使う駐車場と駐車場ビル（事実 F12）。
- 歩く人の多い街：駐車場は、不足を埋める分だけ置く施設にする。置いた分だけ車が増えるので、置かずに歩く街を選ぶこともできる。
- 決定論：台数、費用、料金はどれも整数である。

判断：

- 2 種類の大きさ、台数、費用【マネージャー】。測って決め直す。
- 増築を入れない【マネージャー】。
- 料金を世帯の蓄えから引かない【マネージャー】。家計の流れを足すときに決め直す。
- 料金を街で 1 つにし、遊ぶ人が決める【マネージャー：決定】。まず遊ぶ人が 1 つの手で釣り合いを試せることを優先した。CS2 は駐車場と建物ごとに料金を決める（事実 F11、#215）。駐車場ごとにすると、検査の欄から 1 つずつ料金を変える操作が要り、借りる世帯は料金と距離を比べて選ぶことになる。街で 1 つなら、操作は税率の欄と同じで済む。駐車場ごとの料金は、#215 で経路の費用にお金の重みを入れるときに合わせて足す。

作る順の 5 で決めた細部：

- 料金は `World` の欄 `parking_fee`（`u16`）に持ち、状態ハッシュにも入れる。`SetParkingFee` は記録の種類 11 で、中身は料金の `u16` である。範囲（0〜50）の外は `InvalidCommand::ParkingFeeTooHigh` で断る。
- 料金を変えても、その場では枠を返させない。上限を超えた世帯は、1 日 1 回の見直し（`SHARED_LOT_REVIEW_TICK`）で枠を返す。新しく借りる世帯は、変えたあとの料金で決める。
- 料金の収入に数えるのは、借りている世帯のうち、いまの料金が払える上限（`fee_cap`）以下の世帯の分だけである。上限を超えた世帯は、次の見直しで枠を返すまで料金を払わない。見直しの直後に料金を上げ、直前に戻しても、そのあいだ高い料金は入らない。
- 料金の収入は、借りられた枠の数 × 料金で、収支の収入の行「駐車場の料金」に入れ、ほかの収入と同じく 1 時間ごとに所持金へ足す。
- 画面は、財政の欄の税率の並びの最後に料金の行を置き、1 ずつ上げ下げする。欄が高くなって検査の欄と知らせに重ならないよう、見出しを分けずに 1 行だけ足した。車を持てない世帯の知らせは、理由に「料金が高い」があれば料金を下げるよう促す。
- 初期値 10 と範囲 0〜50 は変えなかった。測った数字（「測り方」の窓、少しずらした版 5 本の平均。共同の駐車場は自宅の枠を減らす PR の (b) の手順で置いた。停止線の変更（#280）を取り込む前に測った）は次のとおりである。
  - 料金 10 で借りる世帯は、料金 0 と同じだった。払える上限はどの世帯も 10 以上なので、初期値で借りる世帯は減らない。
  - 料金 15 では、上限の届かない世帯が「料金が上限を超える」になった。満車の街では、空いた枠を払える世帯が借りるので、借りる世帯の数はほとんど減らず、満車の世帯が料金の世帯に替わった。満車で待つ世帯の少ない街（city.rec）では、払える世帯だけでは埋まらず、借りる世帯が 2 割ほど減った。
  - 料金 20 以上では、どの街でも借りる世帯が 0 になった。上限が 20 に届くのは蓄えが `SAVINGS_FOR_FULL_BONUS` 以上の世帯だけで、測った街にはいなかった。21〜50 は、借りる世帯を 0 にする点で 20 と同じである。
  - 人口と税収は、窓の数日のあいだ料金によらず同じだった。料金の重さを幸福度に効かせるのは作る順の 6 である。
- 範囲の上のほう（20〜50）が同じ結果になることは、作る順の 6 で高さの点を入れるときに、上限の式と合わせて決め直す候補とする。作る順の 6 で、上限を 10〜50 に広げた（4 の「作る順の 6 で決めた細部」）。

#### 3. 世帯と駐車場の結び付け

世帯ごとに、車を置く枠（`CarPlace`）を状態に持つ。

```rust
pub enum CarPlace {
    Home,               // 自宅の枠
    Shared(TilePos),    // 共同の駐車場の枠。駐車場の占める範囲の最小の角で指す
}
// 世帯ごとの枠。枠のない世帯は持たない。
pub struct CarPlaces { by_household: BTreeMap<HouseholdId, CarPlace> }
```

- 共同の駐車場は、占める範囲の最小の角のマスで指す。施設の並び（`Vec<Facility>`）は取り壊すと詰まるので、添え字では指せないためである。同じマスに 2 つの施設は建たないので、角のマスで一意に決まる。
- 共同の駐車場ごとに、借りられた枠の数と、借りた世帯の車が停まっている台数、借りていない車（外来）の停めた台数と押さえた台数を持つ。
- 枠を借りた世帯の車は、乗っていないあいだ、その枠に停まる。借りた枠は車がいないあいだも空かず、外来の車は使えない。日本の月極の駐車場と同じである。

結び付けの決め方：

1. 自宅の枠を先に配る。建物の世帯を ID の順に並べ、自宅の枠の数まで `Home` にする。段階が上がって枠が増えたときも、同じ順で配り直す。
   - すでに枠を持つ世帯からは、同じ建物に住むかぎり取り上げない。空いた枠だけを、枠のない世帯に ID の順に配る。ID は使い回すので、小さい ID の世帯があとから越してくることがある。そのたびに枠を取り上げると、取り上げた世帯の停めてある車が、停めてよい台数を超えて残るためである。
   - 配り直すのは、世帯が越してきた tick、家をなくしたとき（建物を取り壊したとき）、住宅の段階が上がったとき、世帯が街を出たときである。枠をなくした世帯の停めてある車は、駐車場から外す。
2. 自宅の枠のない世帯は、家の出入口から直線で 32 マス（256m、`SHARED_LOT_RADIUS`）の中の共同の駐車場を、近い順に試す。空きがあり、料金が世帯の払える上限以下なら借りる。
3. どこも空きがないか、払えなければ、枠を持たない。枠を持たない世帯は車を持たず、どの移動も歩く。
4. 払える上限は、基準の料金（10）＋ 40 × 世帯の蓄えの割合 ÷ 100 とする（`fee_cap`）。蓄えの割合は、蓄えを `SAVINGS_FOR_FULL_BONUS` で割った百分率（0〜100）である。上限は 10〜50 になり、料金を 10 上げるごとに、蓄えの少ないほうから 4 分の 1 ずつの世帯が借りなくなる。CS2 で料金が高いと豊かな住民だけが停める（事実 F11）のと同じ向きである。最初は基準の料金 ×（100 ＋ 蓄えの割合）÷ 100（10〜20）だったが、作る順の 6 で決め直した（4 の「作る順の 6 で決めた細部」）。

決め直す時：

- 越してきた世帯は、越してきた tick に決める。
- 自宅の枠を配り直すとき（1 の時機）にも、続けて自宅の枠のない世帯に貸す。自宅の枠に空きができたら、枠のない世帯に先に配り、余れば借りている世帯に配る。自宅の枠に移った世帯は借りた枠を返し、停めてあった車も外す。
- ゲーム内の 1 日に 1 回、職場の割り当てと重ならない決まった tick に、枠のない世帯と、料金が上限を超えた世帯を世帯の ID の順に決め直す。料金が上限を超えた世帯は枠を返す。借りている世帯は、より近い駐車場ができても移らない。毎日移ると、置いた順で結果が揺れ、遊ぶ人に読めないためである。
- 共同の駐車場を取り壊すと、借りていた世帯は枠をなくし、停まっていた車も消える（建物の駐車場が消えたときと同じ）。次の決め直しで、ほかの駐車場を探す。
- 面した道路をなくした共同の駐車場は、新しくは貸さない。借りている世帯は、取り壊すまで枠を持ち続ける。
- 世帯が街を出ると、枠を返す。

車の動き：

- 枠のある世帯の車は、3.6 の「世帯の車」の決まりで動く。違うのは、車の帰る所が自宅の駐車場ではなく、借りた枠になることである。
- 家から車で出るときは、家の出入口から借りた駐車場の出入りの位置まで歩き、そこから車に乗る。家に帰るときは、借りた駐車場に停めて、家まで歩く。どちらも `Then::Drive` の 3 区切りのままで、最初と最後の歩く区切りが長くなるだけである。
- 借りた枠はいつも空いているので、家に帰る車が満車で車をやめることはない。
- 枠を持たない世帯は、`CAR_OWNERSHIP_PERCENT` の外の世帯が 500m 以上で車を使う決まり（公共交通の代わり）も使わない。
- 共同の駐車場の外来の空き（台数 − 借りられた枠 − 外来の停めた台数と押さえた台数）は、店や職場に来た車が、満車のときに `PARK_RADIUS` の中で探す候補に入る。候補の順は、建物の駐車場と同じく距離の近い順で、同じなら建物を先にする。

理由：

- 人間の方針：自宅に駐車場のない世帯が、共同の駐車場を借りる。空きがなければ車を持てず、遠いほど、高いほど借りにくい。
- 歩く人の多い街：車を持てない世帯は歩く。歩く人が増えるのは、3.6 の「決めたこと」の 3 と同じく方針に合う。
- 決定論：世帯の ID の順、距離の近い順、角のマスの順に決め、`BTreeMap` で持つ。料金の上限は整数の掛け算と割り算で求める。
- 範囲を 32 マスにしたのは、時間の圧縮のためである。歩く速さは 1,389 mm/tick なので、256m は約 184 tick かかる。通勤の点の満点の境目は 300 tick（1.6）なので、それより遠い駐車場を借りると、歩くだけで通勤の点が下がりはじめる。日本の車庫法の保管場所は使用の本拠から 2km 以内（事実 F15）だが、chizu では歩く時間が重く効くので、狭くした。

判断：

- 世帯ごとの枠を状態に持ち、月極として借りた枠を空けない【マネージャー】。人間の方針の「買ったり借りたり」に当たる形である。
- 範囲 32 マス、払える上限の式、決め直す時【マネージャー】。測って決め直す。
- 借りている世帯は近い駐車場ができても移らない【マネージャー】。
- 枠を持たない世帯は、遠い行き先にも歩く【マネージャー：決定】。人間の方針に「車を持てないので、歩いたり公共交通を使ったりせざるを得ない」とあるためである。今は車を持たない世帯も 500m 以上なら車を使い、これを公共交通の代わりにしている（3.6 の「車の持ち方」）。枠を持たない世帯にもこの代わりを残すと、不足の効きがほとんどなくなる。残さないと、公共交通が入るまで、枠のない世帯の通勤は長い歩きになる。そのため、自宅の枠を減らす PR（作る順の 4）では、人口と需要が大きく崩れないことも確かめる。崩れるなら、公共交通が入るまで、自宅の枠を減らす割合を小さくして調整する。

#### 4. 幸福度の駐車場の点

住民の点数に、通勤、生活サービス、暮らし向きと並ぶ 4 つ目の「駐車場」を足す（`HappinessParts::parking`）。世帯の全員が同じ点になる。

| 世帯の状態 | 点 |
|---|---|
| 自宅の枠がある | 100 |
| 共同の駐車場を借りている | 100 − 遠さ − 高さ |
| 借りたいのに枠がない（車を持てない） | 30 |

- 遠さ：家の出入口から駐車場の出入りの位置までの直線で、8 マスまでは 0、32 マスで 40 になるまで一様に増やす。
- 高さ：料金が基準の料金以下なら 0、世帯の払える上限で 30 になるまで一様に増やす。
- 車を持てない世帯の点を 0 にしないのは、歩くことで通勤の点がすでに下がるためである。通勤の点と二重に下げすぎないようにする。
- 整数で求め、組ごとの更新（1.5）で書き直す。

理由：

- 人間の方針：「車を持てない」「遠い」「高い」を、通勤の点と並ぶ項目として入れる。
- 遊びの面：共同の駐車場を置くと、車を持てない世帯の点が 30 から 60 以上に上がる。置いた手の効きが幸福度に見える。

判断：

- 点の式と値【マネージャー】。測って決め直す。
- 4 つ目の項目を足すことと、その重み【マネージャー：決定】。人間の方針で、幸福度に関わるものとして不足、遠さ、高さの 3 つが挙がっているので、要件の幸福度の表と最初の版の表にも「駐車場」を足した。重みは通勤と同じ 1 から始め、暮らし向きを 3 から 4 に上げる（通勤 1、生活サービス 1、駐車場 1、暮らし向き 4）。税率は遊ぶ人のいちばん大事な手なので、駐車場を足してもその効きを弱めないよう、暮らし向きの割合を前の 5 分の 3 に近い 7 分の 4 に保つ。#132 と同じく、交通の手が効くようになってから、測って決め直す。こうすると、駐車場だけで幸福度は最大 70 ÷ 7 ≒ 10 点下がる。

作る順の 6 で決めた細部：

- 点の値は表のとおりにした。車を持てない世帯は 30（`PARKING_CARLESS`）、遠さは 8 マス（`PARKING_NEAR_TILES`）までは 0 で、借りる範囲の端の 32 マスで 40（`PARKING_FAR_PENALTY`）、高さは料金が基準の料金（10）以下なら 0 で、世帯の払える上限で 30（`PARKING_FEE_PENALTY`）である。範囲の端で上限の料金を払う世帯は 30 点になり、車を持てない世帯と同じになる。
- 遠さは、借りる探し方と同じく、家の正面のマスから駐車場の正面のマスまでの直線で測る。マスの数は整数の平方根で切り捨てる。
- 「借りたいのに枠がない」は、家のある世帯のうち枠を持たない世帯（`carless_households` と同じ）とする。理由（範囲に駐車場がない、満車、料金が上限を超える、待っている、道路に面していない）は問わない。家のない世帯は車を持てない世帯に数えないので、駐車場の点は満点にする。家のない住民は幸福度の平均にも入らない。
- 料金を上げて上限を超えた世帯は、1 日 1 回の見直しで枠を返すまで、料金の下げ幅を上限（30）まで取る。枠を返すと車を持てない世帯と同じ 30 に下がる。前後で点が同じなのは遠さが 40 のときだけで、駐車場が近い世帯は見直しのときに一度に下がる。
- 移住する人の見込みの幸福度（`newcomer_happiness`）は、自宅の枠がある人として駐車場を満点にする。通勤を満点とするのと同じ扱いである。
- 状態の形は `HappinessParts` に欄が増えるので、`SNAPSHOT_VERSION` を 17 に上げ、ゴールデンを書き直した。
- 画面は、人口の欄の内訳（通勤、生活サービス、駐車場、暮らし向き）と、住宅の検査の欄に駐車場の点を出す。chizu-wasm の `overview` では、あとから足した値なので、ほかの値の位置を変えないよう固定の並びの最後に置いた。chizu-cli の observe は `population.happinessParts.parking` を出し、`sinceLastObserve` にも載せる。

#### 既存の作りから移る道

住宅の建物の中の駐車場（#264）：

- 集合住宅の自宅の枠を世帯の数 × 0.5 にすると、ほとんどの集合住宅は平面だけで足り、建物の中の台数は 0 になる。たとえば 4×4 マスで段階 5 の 20 世帯は、平面 14 台と建物の中 6 台から、平面 10 台と建物の中 0 台になる。平面に入りきらない形の集合住宅（斜めの道路に面した建物など）だけが、入りきらない分を建物の中に持つ。
- #264 で増やした分（世帯の数 × 0.7 を超える分）は、共同の駐車場で借りる分に置き換わる。#264 の理由は「遊ぶ人に打つ手がない」ことだった。共同の駐車場が打つ手になるので、建物の中に持たせる理由はなくなる。
- 商業、オフィス、工業の建物の中の駐車場は変えない。外来の車の駐車場で、世帯の枠とは別だからである。

家ごとの切り欠き（#232）：

- 1〜2 マスの戸建て（低密度）の 3 軒に 1 軒は、前面の帯を切り欠かない。
- 集合住宅の脇の駐車場は、世帯の数 × 0.7 から 0.5 に減るので、切り欠くマスが約 3 割減る。
- 3 マス以上の戸建て（低密度）と、商業、オフィス、工業の切り欠きは変えない。#270 の「見た目だけを変えるのか、台数の持ち方も変えるのか」には、住宅だけ台数の持ち方も変えると答える。
- 減らしすぎると、店や職場に来た車の行き場がなくなる。非住宅の台数は、駐車場の面の割合を測ってから別に決める。

私道の奥の一軒家（#271）：

- 私道の設計（3.8）は、私道の脇に家ごとの枠を置くと決めた。私道の敷地の家は自宅の枠を持つ（1 の表）。

#### 決めきれない点

人間から任され、マネージャーが決めたこと：

1. 料金を街で 1 つにし、遊ぶ人が決める。CS2 の駐車場ごとの料金は #215 に回す。
2. 枠を持たない世帯は、公共交通がないあいだも遠い行き先へ歩く（500m 以上で車を使う代わりを残さない）。
3. 幸福度に 4 つ目の項目「駐車場」を足し、要件にも足す。重みは通勤と同じ 1 から始め、交通の手が効くようになってから決め直す。

測った数字を見て、マネージャーが決めること：

1. 自宅の枠の割合（戸建て 1/3、集合住宅 0.5）。
2. 共同の駐車場の大きさ、台数、建設費、維持費、料金の初期値と範囲。
3. 借りる範囲（32 マス）、払える上限の式、駐車場の点の式。
4. 暮らし向きの重み【マネージャー：決定】。駐車場を重み 1 で足すと、暮らし向きを 3 のままにすれば割合が 5 分の 3 から 2 分の 1 に下がり、税率の効きが弱まる（税を上限の 300‰ にしても、ほかの要素が満点の世帯の幸福度は 50 で、出ていく境目の 52 をわずかに下回るだけになる）。税率は遊ぶ人のいちばん大事な手なので、暮らし向きを 4 にし、割合を 7 分の 4 に保った。税を上限にした世帯の幸福度は 42、税率 200‰ で越してくる人の見込みは 54 で、前（40 と 52）に近い。#132 で重みを決め直すときに、あらためて測る。

別の Issue で扱うこと：

1. 越してくる人の見込み（`newcomer_happiness`）は駐車場を満点にするので、車を持てない世帯が出ていき、越してくる人で埋まる入れ替わりが起きる（転出は 2〜4 倍になるが人口は保たれる）。見込みの点を、街の住宅の世帯の分かれ方（自宅の枠、借りている、車を持てない）の平均から求めれば、車を持てない世帯の多い街に人が来にくくなり、CS2 に近づく。

### 3.8 私道の奥の家

人間のフィードバック（#271）から起こした設計である。いまの住宅は、どれも通りに面した 1 つの棟で、区画の奥行きいっぱいに建つ。そのため、低い段階の住宅もアパートに見える。日本の住宅地によくある形にならい、行き止まりの私道の脇に一軒家を並べた敷地を足す。

#### 決まっていること

- 私道は車が通れてよい。私道の先や脇に駐車場があってもよい（人間の判断）。
- 私道は通り抜けられない行き止まりにする。その住宅と行き来するためだけの道で、ほかの車や歩く人の経路には使わない（人間の判断）。
- 私道は、プレイヤーが引く道路ではなく、建物の敷地の一部として持つ。区画の奥行き（6 マス）の中に収める。
- 中核の経路探索の網には、私道を足さない。
- 区画を塗れる範囲（#250）は変えない。

#### 敷地の形

共有の私道の形から始める。1 本の行き止まりの私道の脇に、世帯の数だけ一軒家を並べる。旗竿地（細い通路の奥に家が 1 軒）は今は作らない。

- 中核の建物 1 つは、何世帯かを持つ。共有の私道なら、建物 1 つを「私道を共有する家の並び」と見なし、1 世帯を 1 軒にできる。建物の数も、世帯と職場の数の式も変えずに済む。
- 旗竿地にすると、通りに面した家と奥の家を、別の建物に分けることになる。建物の数と並びが変わり、育ち方の比べ方が崩れる。
- 共有の私道でも、通りに面した 1 軒の奥に家が続くので、奥まった家は見える。

#### どの建物が奥になるか

次の条件をすべて満たす建物の一部を、私道の敷地にする。

| 条件 | 理由 |
|---|---|
| 住宅で、段階 1〜2 | 戸建ての段階である（3.6 の「台数の決め方」）。私道の敷地は段階 2 で止め、段階 3 以上の集合住宅にはならない |
| 縦か横の道路に面している | 斜めの道路沿いの建物は 1 辺 2 マスまでの正方形で、奥行きがない |
| 間口が 2 マス | 1 マス（8m）は、私道の 3m を除くと家の幅が 5m しか残らない。3〜4 マスは、家を 1 列に並べると幅が広すぎて、また集合住宅に見える |
| 奥行きが 4 マス以上 | 奥に 1 軒以上の家を並べるためである。奥行き 4 マスの段階 1 で 2 軒になる |

- 3.9 の 4 で、私道の敷地は低密度の住宅区画にだけ建つようにし、以下の割合（`LANE_PERCENT`）と段階の上限（`LANE_MAX_LEVEL`）、奥行きの下限（`LANE_PERCENT_MIN_DEPTH`）はなくした。この節の以下は、高密度に建てていたときの決め方と、その測りの記録である。
- 選ぶのは建物が建つときで、建物の大きさを決めたあとに、建てる試みごとの乱数（`RngPurpose::BuildingGrowth`）からもう 1 つ引く。引いた値が `LANE_PERCENT`（25%）より小さければ私道の敷地にする。試みごとの乱数は、大きさを決めたあとに使わないので、ほかの建物の位置と大きさは変わらない。
- 選んだ結果は `Building::form`（`LotForm::Street` か `LotForm::Lane`）として持つ。状態ハッシュとスナップショットに入る。
- 私道の敷地は、段階 2（`LANE_MAX_LEVEL`）より上に上がらない。`grow_buildings` が、`form` が `Lane` の建物の段階を上げない。CS2 には集合住宅にならない低密度の住宅区画がある。chizu は住宅区画が 1 種類で段階に応じて育つが、私道の敷地だけは低密度として扱い、育ちきった街にも一軒家の住宅地が残るようにする（#276）。
- 割合は 25% にした。私道の敷地にできる大きさの住宅は、段階 1〜2 の住宅の 2 割ほどである。段階 3 以上に上がらなくなると、私道の敷地は低い段階のまま人口の少ない家になるので、割合が高いほど人口が減る。main と少しずらした版の組（5 本）の平均で比べた（#276）。70% では、育ちきった街（city.rec の 63〜68 日目、種 0 の 96〜101 日目）で人口が約 10% 減った。割合を 40%、25% と下げると、同じ 2 つの街で 6% 台から 3〜4% 台へ減り方が小さくなった（ずらしなしの 1 本ずつ）。5 本の平均では、25% で人口が main の 0.95（city.rec）と 0.96（種 0）になり、育ち始めの街（種 311、種 512、種 101）は 0.99〜1.00 だった。30% は city.rec で 0.93 になり、目安の 5% を超えた。割合を変えると私道の敷地になる建物が入れ替わるので、減り方は割合に比例せず、1〜2% の幅で揺れる。25% は、5% の目安に収まる中で多いほうである。
- 育ちきった街で残る私道の敷地は、25% で city.rec の 68 日目が 8 棟（住宅 162 棟のうち）、種 0 の 101 日目が 14 棟（住宅 290 棟のうち）である。段階 3 に上がると戻っていた前の版（70%）では 0 棟だった。70% のまま段階を止めると 22 棟と 39 棟だが、人口が減りすぎる。
- 止まっている車と救済は、5 つの街のうち 4 つで main の 1.05 倍以内か、それより少なかった。超えたのは、種 101 の止まっている車（1.08 倍）と種 0 の救済（1.32 倍、1 日 2.2 件から 2.9 件）で、どちらも幅が main と重なり、揺れの内である。平均の移動時間は main の 0.99〜1.01 倍だった。

#### 私道、家、枠の置き方

形は建物の種類、大きさ、段階、`form` から決まる純粋な関数にし（`Building::lane_plan`）、状態には持たない。間口の座標 u は、私道のある端の外側の辺を 0 として内へ増え、奥行きの座標 v は、道路に面した辺を 0 として奥へ増える。単位は mm である。

| もの | 置く所 |
|---|---|
| 私道 | u が 0〜3,000。v は 0 から、いちばん奥の枠の奥の端まで。そこで行き止まりにする |
| 区切り | 奥行きを世帯の数 n で等分する（切り捨て）。道路の側から 0 番、1 番と数える |
| 家 | 区切りごとに 1 軒。u は 8,600〜15,400（2 列めのマスから、まわりに 600 ずつ空ける）。v は区切りの始まりから 600 空けて、奥行き `min(区切り − 1,200, 10,000)` |
| 枠 | 区切りごとに 1 台。u は 3,000〜8,000（私道に面した奥行き 5m）、幅 2.5m。v は家の真ん中にそろえる。車は私道の側から入る |

- 私道の幅 3m は、脇の駐車場の通路（3.6）と同じである。車 1 台が通れる幅にした。
- 私道のある端は、脇の駐車場と同じく `lot_end`（面した道路の、近い交差点から遠い側）で選ぶ。#232 の切り欠きと同じ決まりで、出入りの位置を停止線から離す。
- 台数は今と同じく世帯の数で、すべて平面に持つ。切り欠きの形は `ParkingCut::Lane { houses }` とする。間口 2 マスで奥行き 4 マス以上の戸建ては、脇の駐車場でも世帯の数だけ持てるので、台数は変わらない。3.7 の「自宅の枠を持たない家」でも、3 マス以上の戸建ては世帯の数 × 1 の枠を持つので、私道の敷地（8 マス以上）は家ごとに 1 台の枠を持つままでよい。
- 占めるマス（`area`）、世帯の数、職場の数は変えない。私道と枠と庭は、建物の敷地の中にある。

奥行き 6 マスの段階 1（3 世帯）なら、区切りは 16m で、家は 6.8m × 10m になる。段階 2（6 世帯）なら、区切りは 8m で、家は 6.8m 四方になる。

#### 間口の使い方と、ほかの建物との並び

- 私道は間口 2 マスのうち、端の列の外側の 3m を使う。残りの 13m に枠と家を置く。
- 隣の建物との並びは今と同じで、建物の敷地の外は変えない。私道の敷地が隣り合うと、私道と家の列が交互に並ぶことも、私道が 2 本並ぶこともある。どちらも、日本の住宅地の分譲地に見られる並びである。
- 私道は区画の奥の端まで届かない。奥の区画の建物とは、敷地の中で行き来しない。

#### 交通への効かせ方

建物の出入口と駐車場の出入りの位置を、どちらも私道の入口にする。私道の入口は、私道の真ん中の線（u = 1,500）が道路に面した辺と交わる所を、道路の上に写した点である。

- 駐車場の出入りの位置（`lot_spot`）は、脇の駐車場と同じ決まりで、端の列の外側の辺から 1,500 内に入った点にする。脇の駐車場は 4,000（列の真ん中）である。
- 歩く人の出入口（`building_spot`）も、同じ点にする。住民は、家から私道を通って通りに出る。降りた人も乗る人も、私道の入口で車と乗り降りする。
- 中核の `Building::entrance` と `entrance_at` は変えない。電気と水道の届き方の道のり（`service`）は、今のまま `entrance_at` で測る。
- 私道の入口が道路の上に取れない端（行き止まりの端など）には、私道を通さない。両方の端を試し、取れた端のうち交差点から遠いほうを選ぶ（`lot_end` が返す端も同じ）。脇の駐車場は、取れないとマスの真ん中や出入口に寄せるが、私道は入口がマスの真ん中に落ちると私道の外の脇の枠の上になるので、寄せない。
- 両方の端で取れないときだけ、出入口にする。この場合は入口が私道の外に出うる。端の入口の点は、外隣のマスも同じ区間の線の上にあるときしか取れないので、起きるのは次の 2 つの場合である。
  - 建つとき：間口の下の道路がちょうど 2 マスの真っすぐな区間で、両側が曲がり角か行き止まりのとき。
  - 建ったあと：道路を剥がして、敷地が残ったとき。

私道の道のりは、歩く時間にも車の出入りの時間にも足さない。

- 私道はいちばん長くても 45m ほどで、歩いて 35 秒ほどである。通勤の所要時間（分の単位）に比べて小さい。
- 脇の駐車場の中を歩く道のりも、今は足していない。私道だけに足すと、ほかの建物と釣り合わない。
- 足すと、私道の入口で人と車が止まって見える時間ができる。地図に私道の上を動く人と車を描かないうちは、足さないほうが見た目と合う。

#### 地図の描き方

地図の見た目の決まり（[map-style.md](map-style.md)）の総描の考え方に合わせる。私道は細い淡い線、奥の家は小さい棟にする。

| 段 | 私道 | 家 | 枠 |
|---|---|---|---|
| 引き | 描かない。街区の面に含める | 描かない。街区の面に含める | 描かない |
| 標準 | 淡い面。幅 3m なので、倍率 4〜12 で 1.5〜4.5px の細い線に見える | 1 軒ずつの小さい棟（縁なし） | 駐車場の淡い面 |
| 寄り | 淡い面に、敷地の外周に接する辺と、家の側の辺の縁 | 1 軒ずつ、縁と影 | 枠の白線と、停まっている車 |
| 細部 | 寄りと同じ | 1 軒ずつ寄棟の屋根の線 | 停まっている車の窓と屋根 |

- 私道の面と縁は、駐車場の面と同じ倍率で溶け込む（面は 3〜5、縁は 10〜14）。
- 家は、ほかの建物と同じ区画の色で塗る。家の形は中核の決めた長方形をそのまま使い、画面の側で縮めない。
- 停まっている車は、ほかの駐車場と同じく、枠の並びの順に埋める。枠の並びは道路の側の家から並べる。

| もの | 色 |
|---|---|
| 私道の面 | `#fbfaf6` |
| 私道の縁 | `#d6d0c4`（1px） |

私道の面の色は、住宅の地面（`#eef4e6`）と駐車場の面（`#e3e1dc`）の両方と見分けられるよう、白に近くした。道路の白（`#ffffff`）より少し暗くし、縁を道路より淡くして、プレイヤーの引いた道路と取り違えないようにする。

描画に渡すものは次のとおりである。

- chizu-wasm の `lots` に、私道の長方形と家の長方形を足す。見出しに、私道の数と家の数を足す。枠は、今の枠の並びに 1 台ずつの並びとして入れる。
- 建物の静的データと同じく、建物が建つか、段階が変わるか、網が変わるときだけ送る。

#### chizu-cli

- `agent map` は、私道の通るマスを `=` で出す。駐車場（`p`）と建物より先に出す。私道の脇の枠は、私道のマスに含める。
- `agent observe` の `buildings.lanes` に、私道の敷地の数（`lots`）と、その家の数（`houses`）を出す。

#### 状態と記録

- `Building` に `form` を足すので、状態の形が変わる。`SNAPSHOT_VERSION` を 11 から 12 に上げる。
- 記録の形式は変えない。コマンドを足さないので、`FORMAT_VERSION` も変えない。
- 出入口と駐車場の出入りの位置が変わるので、シミュレーションの結果が変わる。ゴールデンを書き直す。

#### 測り方

3.6 の「測り方」と同じ窓（種 0、種 101、種 311、種 512、city.rec）で、main と比べる。交通の数字はわずかな違いで大きく揺れるので、それぞれ少しずらした版の組（5 本）の平均と幅で比べる。

- 止まっている車と救済は、組の平均で main の 1.05 倍以内にする。
- 人口と建物の数が大きく変わらないことを確かめる。建物の位置と大きさは変わらないので、変わるのは交通を通した分だけである。
- 平均の移動時間と駐車場の数字（満車で近くへ回った数、駐車場がなくて歩いた数）も並べる。

#### 決めきれない点

見た目と数字を見て、マネージャーが決める。

1. 私道の敷地にする割合（`LANE_PERCENT`、25%）。3.9 で、私道の敷地は低密度の住宅区画にだけ建つようにし、この割合はなくす。
2. 遊ぶ人が一軒家の住宅地を選んで作れるか。3.9 で、低密度の住宅区画を塗れるようにすると決めた。
3. 旗竿地と、間口 3〜4 マスの敷地（私道の両側に家を並べる形など）は、後で足すかを決める。

### 3.9 低密度の住宅区画

人間のフィードバック（#271）から起こした設計である（#281）。3.8 で私道の一軒家を入れたが、住宅区画が 1 種類で、段階が上がると集合住宅になる。そのため、育ちきった街には一軒家がほとんど残らない。CS2 にならい、住宅区画を低密度と高密度の 2 つに分ける。遊ぶ人は、塗るときにどちらかを選ぶ。

#### 決まっていること

マネージャーが #281 で決めた。

- 低密度の住宅は、段階 1〜2 で止まる。一軒家と私道の敷地（3.8）が建つ。
- 高密度の住宅は、今の住宅区画と同じで、段階 5 まで上がる。
- 要件の表には、住宅の中の密度の違いとして足す。

各項目の判断の理由は、人間の要望（#271）、CS2 に近づける、歩く人の多い街が楽しいか、決定論と整数で作れるか、の 4 つで書く。

#### 1. 区画の種類の持ち方

`ZoneKind`（住宅、商業、工業、オフィスの 4 つ）は、税率、需要、職場の数、街の数字の表の添え字として残す。新しく、塗る区画の種類 `Zone` を足し、マスと建物はこちらで持つ。

```rust
#[repr(u8)]
pub enum Zone {
    Residential = 1,     // 高密度の住宅。今の住宅区画
    Commercial = 2,
    Industrial = 3,
    Office = 4,
    ResidentialLow = 5,  // 低密度の住宅
}
impl Zone {
    pub fn kind(self) -> ZoneKind;     // 住宅の 2 つは ZoneKind::Residential
    pub fn density(self) -> Density;   // 低密度の住宅だけ Density::Low
    pub fn max_level(self) -> u8;      // 低密度の住宅は 2、ほかは MAX_LEVEL
}
pub enum Density { Low, High }
```

- `LayerTiles.zone`、`LotFronts`、`Building::zone`、`PaintZone` の区画は `Zone` にする。税率、需要の内訳、`CityStats`、`ZoneTotals`、`job_slots` は `ZoneKind` のままにする。
- 番号と並びは今の `ZoneKind` と同じにし、低密度を最後の 5 に足す。今の住宅区画は高密度（番号 1）になり、状態ハッシュとスナップショットのバイト列は、低密度を塗らない街では変わらない。
- 区画の塗り方（1.4）の「別の種類の区画」は `Zone` で比べる。低密度と高密度は別の種類で、塗りの範囲の外の高密度のマスを通って低密度の奥のマスへは続かない。建物のあるマスに塗れないのは今のままなので、建った建物の密度は変わらない。密度を変えるには、建物を取り壊してから塗り直す。

理由：

- CS2 に近づける：CS2 も、住宅、商業、工業、オフィスの大きな種類の中に、密度の違う区画を持つ（事実 F16）。商業にも低密度と高密度があるので、後で商業を分けるときも `Zone` に足すだけで済む。
- `ZoneKind` に 5 つ目を足す案は取らない。区画の種類ごとの表（税率、需要、職場、街の数字の並び、画面の受け渡しの JSON）がすべて 5 つになり、住宅の 2 つで同じ税率と需要を持ち合う決まりを表ごとに書くことになる。
- 決定論：`Zone` は番号の決まった列挙で、反復の順も変わらない。chizu-cli の、ワイルドカードのない match がコンパイルで止まるので、直し漏れがない。

判断：`Zone` を足し、`ZoneKind` を残す【マネージャー】。

#### 2. 需要の分け方

住宅の需要は 1 つのままにし、低密度と高密度で分けない。

- 新しく建つ住宅は、今と同じく住宅の需要が正のときに、住宅の間口の候補（`LotFronts` の住宅の並び。低密度と高密度の両方を含む）から乱数で選ぶ。建つ密度は、空いている間口の数の比になる。
- 段階を上げる条件（`grow_buildings` の `wanted`）も、住宅の需要 1 つで見る。低密度は段階 2 で止まる。
- 需要の内訳（`demand_factors`）と、画面の受け渡しの需要の要因の表は変えない。

理由：

- 人間の要望：一軒家の住宅地を、遊ぶ人が選んで作れることが芯である。需要が 1 つなら、塗ったとおりの密度で街が育つ。
- CS2 に近づける：CS2 は世帯の種類（家族、1 人、学生、高齢）から密度ごとの需要を出す（事実 F16、F17）。chizu の世帯にはその属性がないので、分けても根拠のない割合になる。要件の「重みは世帯の属性で変える」を入れて世帯の種類ができたときに、密度ごとに分け直す。
- 歩く人の多い街：街の密度を遊ぶ人が決められる。職場の近くを高密度にして歩く街にするか、郊外を低密度にして車の街にするかが、塗り方の判断になる。
- 決定論：今の式をそのまま使う。

判断：住宅の需要を 1 つのままにする【マネージャー】。世帯の種類を足すときに決め直す。

#### 3. 建物の大きさと世帯の数

世帯の数の式（4 マスあたり段階ぶん、切り上げ）は変えない。低密度は段階 2 で止まるので、1 マスあたりおよそ 0.5 世帯になる（1〜3 マスの家は切り上げで少し多い）。高密度は 1.25 世帯までである。

低密度の敷地は、一軒家が並ぶ形だけにする。

| 敷地 | 形 | 世帯の数（段階 1 → 2） |
|---|---|---|
| 間口 2、奥行き 3〜6 | 私道の敷地（3.8）。必ず私道にする | 2〜3 → 3〜6 |
| 間口 1〜2、奥行き 1〜2 | 通りに面した家。1 世帯を 1 軒として、間口に沿って並べる | 1 → 1〜2 |
| 斜めの道路沿い（1 辺 1〜2 の正方形） | 通りに面した家 | 1 → 1〜2 |

- 建てる大きさは、高密度のように間口を乱数で引かず、間口 2 を先に試す。試す順は、私道の敷地の (2, 6)、(2, 5)、(2, 4)、(2, 3)、通りに面した家の (2, 2)、(2, 1)、(1, 2)、(1, 1) である。収まる中で最初のものに建てる。電気と水道の余りに収まらない大きさを飛ばすのは、今と同じである。
- 間口 1 の深い敷地（1 × 3 以上）は作らない。1 列に 2〜3 世帯が並ぶと、通りから入れない家ができるか、また 1 つの棟に見えるためである。そのため、塗った間口の端数が 1 マスのときは、奥のマスが空き地として残る。残るのは、次の置き方で出る端数の列だけである。
- 間口の位置は乱数で選ばず、並びの端から 2 マスずつ詰める（#285）。建てる試みの乱数が引いた間口のマスを、そのマスを含む並びの端から数えて 2 マスずつの組の頭にそろえる。並びは、同じ低密度の区画で、同じ向きの道路に面した空きの間口が途切れずに続くマスである。建物や施設、別の区画で途切れた並びは、そこから数え直す。引いた位置を使わないと、私道の敷地のあいだに幅 1 マスの隙間ができ、そこに間口 1 の家が建って奥が空いたままになる。並びの長さが 2 で割り切れないときは、端数の 1 列だけが残り、そこには通りに面した間口 1 の家が建つ（奥は空く）。斜めの道路沿いは今のままである。高密度の間口の選び方は変えない。
- 私道の敷地の奥行きの下限（`LANE_MIN_DEPTH`）を 4 から 3 に下げる。奥行き 3 の段階 1 は 2 軒（区切り 12m、家 6.8m × 10m）、段階 2 は 3 軒（区切り 8m、家 6.8m 四方）で、奥行き 6 の段階 2 と同じ大きさの家が入る。下げないと、奥行き 3 の列は通りに面した家（奥行き 2）になり、奥に 1 マスが残る。
- 段階の上限は `Zone::max_level` で決める。`LANE_MAX_LEVEL` はこれに置き換える。私道の敷地は低密度にしか建たないので、私道の敷地が段階 2 で止まる決まりも、低密度の上限に含まれる。
- 通りに面した家を 1 世帯 1 軒で描くのは画面の仕事で、中核の状態は変えない。家の大きさと並べ方は、私道の家（3.8）と同じく `Building` から決まる純粋な関数にし、描画の PR で決める。

理由：

- 人間の要望：通りに面した家も私道の奥の家も、1 軒ずつに見える。区画の奥行き 6 マスの列は、間口 2 ずつの私道の敷地で埋まり、日本の分譲地の形になる。
- CS2 に近づける：低密度の建物は 1 世帯である（事実 F16）。chizu では、建物 1 つを家の並びと見なし、1 世帯を 1 軒にする。
- 決定論：大きさを試す順は決まった並びで、乱数は今と同じ建てる試みの乱数だけを使う。

判断：

- 世帯の数の式を変えない【マネージャー】。人口と需要の比べ方を崩さないためである。
- 試す順、間口 1 の深い敷地を作らないこと、`LANE_MIN_DEPTH` を 3 にすること【マネージャー】。
- 私道の敷地を並びの端から詰めること、旗竿地を足さないこと【マネージャー】。古い記録の住宅の塗りをすべて低密度に書き換えた街で、低密度の塗ったマスの空きは 0.7〜2.6% になった（乱数で間口を選んでいたときは 15〜18%）。

#### 4. 私道の敷地の割合

私道の敷地は、低密度の住宅区画にだけ建てる。低密度では、間口 2、奥行き 3 以上の敷地は必ず私道の敷地にする。高密度には建てない。`LANE_PERCENT` はなくす。

理由：

- 3.8 の 25% は、私道の敷地が段階 2 で止まって人口が減るのを、5% の目安に収めるための値だった（#276）。密度を遊ぶ人が選ぶので、高密度で人口を削る理由はなくなる。
- 高密度を「今の住宅区画と同じで、段階 5 まで上がる」にそろえる。高密度に私道の敷地を残すと、その建物だけ段階 2 で止まり、決まっていることと食い違う。
- CS2 の高密度にも、一軒家は建たない。
- 低密度で割合を 100% にしないと、間口 2 の深い列が 1 つの棟（通りに面した、奥行き 6 の建物）になり、集合住宅に見える。

古い保存データの扱い：すでに建っている高密度の私道の敷地（`LotForm::Lane`）は、そのまま残す。`lane_plan` は低密度の住宅にしか効かないので、この建物は通りに面した建物として振る舞い、駐車場の台数もふつうの建物と同じになり、段階 5 まで上がれる。状態の形は変わらないので `SNAPSHOT_VERSION` は上げない。

#### 5. 駐車場との関わり

3.6 と 3.7 の「戸建て」と「集合住宅」は、今は段階（1〜2 か 3〜5）で分けている。これを密度で分ける。

| 住宅 | 今 | 変えたあと |
|---|---|---|
| 低密度（段階 1〜2） | 戸建て | 戸建て。今と同じ |
| 高密度の段階 1〜2 | 戸建て | 集合住宅。自宅の枠は世帯の数 × 0.5（切り上げ）で、平面に入る分を先に平面に置き、残りを建物の中に持つ |
| 高密度の段階 3〜5 | 集合住宅 | 集合住宅。今と同じ |

- 私道の敷地は、今と同じく家ごとに 1 台の枠を私道の脇に持つ。
- 通りに面した低密度の家（1〜2 マス）は、前面の帯に世帯の数だけの枠を持つ。今の段階 1〜2 の 1〜2 マスの住宅と同じである。
- 3.7 の「自宅の枠を持たない家」の表の「戸建て」も、密度で読む。1〜2 マスの低密度の家の 3 軒に 1 軒が枠を持たず、高密度は段階を問わず世帯の数 × 0.5 になる。3.7 の作る順の 4 がこの節の作る順の 5 より後に入るときは、その PR で密度の決まりを使う。先に入るときは、この節の 5 の PR で 3.7 の表を書き直す。
- 低密度の住宅地は、どの家も自宅の枠を持ちやすく（私道の家はすべて持つ）、車の街になる。高密度は、3.7 の 4 が入ると枠が世帯の半分になり、共同の駐車場か歩きに頼る。

理由：

- CS2 に近づける：CS2 の区画は密度で建物の形が決まり、高密度の建物は段階 1 でも集合住宅である。
- 歩く人の多い街：高密度の街は歩く人と共同の駐車場の街に、低密度の街は自宅の車の街になる。遊ぶ人が密度を選ぶことが、交通の手を選ぶことにもなる。
- 決定論：台数は今と同じく、`Building` から決まる純粋な関数である。

判断：戸建ての判定を密度で決める【マネージャー】。高密度の段階 1〜2 の台数は世帯の数 × 1 から × 0.5 に減るので、3.7 の作る順の 4 のあとの別の PR にして前後を測る。

作る順の 5 で決めた細部：

- 戸建ては `Zone::ResidentialLow` だけで決める。台数の式（`parking_needed`）、建物の中に持たない決まり（`parking_layout`）、自宅の駐車場を持たない家（`has_home_lot`）のどれも、段階を見ない。
- 台数が変わるのは、高密度の段階 1〜2 である。世帯の数 × 1（3 軒に 1 軒は 0）から、世帯の数 × 0.5 になる。低密度は変わらない。
- 低密度は段階 2 で止まるので、戸建てが集合住宅に上がって台数が減る場面はなくなった。
- 状態の形は変わらないので `SNAPSHOT_VERSION` は上げない。ゴールデンは書き直した。
- 測った結果：#291 までを取り込んだ main と比べた。着く判定を 0、25、50、75、100mm ずらした版 5 本の平均と最小・最大である（種 101 と種 311 と種 512 と種 0 と city.rec の古い記録、始めの所持金は同じだけ足した）。止まっている車と救済は、どの街も main 以下だった（種 101 は 0.54 倍と 0.65 倍、city.rec は 0.78 倍と 0.81 倍）。人口は 1.00 倍、税収は 1.00 倍、歩きに切り替えた数は 0.40〜0.83 倍、車を持てない世帯の数は 0.91〜1.01 倍だった。

#### 6. 画面と chizu-cli

画面：

- 区画の道具の住宅を、「住宅（低密度）」と「住宅（高密度）」の 2 つのボタンにする。CS2 と同じく、同じ住宅の組の中に並べる。
- 区画の地面は、どちらも住宅の緑の系統にする。低密度の空きの区画は、寄りの段の模様で高密度と分ける。色と模様は描画の PR で決め、[map-style.md](map-style.md) も同じ PR で直す。
- 通りに面した低密度の家は、1 世帯を 1 軒の小さい棟として描く。私道の敷地は今の描き方のままである。
- チャンクの静的データのマスの区画の番号（3 ビット）に、5 を足す。建物の静的データの区画を `Zone` の番号で送るのは、作る順の 3 である（`detail.ts` の屋根と `roads.ts` の建物の色が番号 1 を前提にしているので、建物の描き分けと一緒に変える）。
- 検査の欄に、建物の密度を出す。需要の欄は住宅 1 つのままである。

chizu-cli：

- act の `paintZone` の区画に、`residentialLow` を足す。`residential` は高密度のままにし、今の遊び方とセッションの指示をそのまま使えるようにする。`setTaxRate` の区画は 4 つのままで、`residentialLow` は断る。
- observe の `buildings` に、密度ごとの建物の数、世帯の数の上限、住んでいる世帯の数を足す。`zones` の塗ったマスの数も密度ごとに分ける。
- map は、低密度の建物を `D`、空きの低密度の区画を `d` で出す（`L` は平面の駐車場に使っている）。凡例に足す。

判断：画面と chizu-cli の中身【マネージャー】。

#### 決めきれない点

測った数字を見て、マネージャーが決める。

1. 住宅の需要を密度ごとに分けるか。世帯の種類を足すときに決め直す。
2. 中密度（長屋と低層の集合住宅）を足すか。家賃を足すときに、高密度との違いが出るかを見て決める。

人間に回すことはない。要件の表に足すのは住宅の中の密度の違いで、要件の区画の種類（住宅、商業、工業、オフィス）は変えない。

### 3.10 鉄道

人間の方針（#311）から起こした設計である。公共交通の最初の手段として、地上の鉄道を入れる。

ねらいは次の 3 つである。

- 車を持てない世帯の遠い移動を、「500m 以上なら車を使う」という仮の扱い（3.6 の「車の持ち方」）から、鉄道に移す。
- 駐車場の不足に対して、遊ぶ人が打てる手を増やす。駅を置くか、共同の駐車場（3.7）を置くかを選べるようにする。
- 要件の 1 行目にある「鉄道」を作る。

各項目の判断には、3.7 と同じ印を付ける。

- 【マネージャー】：要件、人間の方針、「CS2 に近づける」の範囲で、マネージャーが決めてよい。測って決め直す値もこれに入れる。
- 【マネージャー：決定】：この基準だけでは決めにくいが、遊びの方向を変えない項目である。マネージャーが決めた。
- 【人間に聞く】：遊びの方向そのものに関わるか、要件の文を変える項目である。末尾の「人間に聞くこと」にまとめる。

理由は、人間の方針、CS2 に近づける、歩く人の多い街が楽しいか、決定論と整数で作れるか、の 4 つで書く。

#### 決まっていること

- 公共交通は鉄道から入れる。バスはその後にする（人間の方針、#311）。
- 貨物列車は、物の流れ（要件の「まだ決めていないこと」）と一緒に後で決める。この節では旅客だけを扱う（人間の方針、#311）。
- 線路は地上の層に置く。高架と地下は、要件のとおり層を足すときに加える。データの持ち方は、最初から層を前提にする（1.2、1.3）。
- 線路は道路と同じく、マス目の 8 方向に引ける（要件の「道路と線路は 45 度の斜めも引ける」）。
- 住民は、所要時間と費用を比べて手段と経路を選ぶ。手段を乗り継いでもよい（要件の「交通」）。

#### 今の作り

- 手段は歩きと車の 2 つで、出発の建物と行き先の建物の正面のマスの直線の距離だけで決める（`movement/commute.rs`）。車を持つ世帯は 150m（`OWNER_DRIVE_MIN_MM`）以上、車を持たない世帯（`CAR_OWNERSHIP_PERCENT` の外の 30%）は 500m（`DRIVE_MIN_MM`）以上で車に乗る。車を置く枠のない世帯は、遠くても歩く（3.7 の 3）。
- 5.1 の「徒歩と自家用車の費用を比べて安いほうを選ぶ」は、まだ作っていない。費用で手段を比べるのは、この節が初めてになる。
- 3.1 の区間の計算と一括の計算（`LinkStats` も含む）は、まだ作っていない。今はどの速さでも細かい計算で回す。
- 移住する世帯は、道路で外の世界とつながった住宅に現れる。外から移動してくるわけではない。
- 網（`Network`）は道路と歩道だけを持つ。区間の種類は道路と高速道路（`SegmentKind`）、車線の使い手は車と歩道（`LaneMode`）である。

#### CS2 の作りと、chizu で取るもの

| CS2 の作り | chizu の扱い | 理由 |
|---|---|---|
| 線路に、双方向の単線、複線、一方通行がある。高架、橋、トンネル、掘割もある（事実 F20） | 複線の 1 種類だけを取る。高架と地下は層を足すときにする | 単線は行き違いの信号と待ち合わせが要り、詰まりの元になる。一方通行は環状の路線を作る手だが、複線で足りる。種類を絞って、最初の PR を小さくする |
| 列車は前にも後ろにも走れ、終点で折り返す。駅には線路が付いていて、つなぐと分岐が自動でできる（事実 F20） | 取る。駅を置くと駅の中の線路もできる。終点では折り返す | CS2 に近づける。駅の線路を遊ぶ人が別に引かずに済む |
| 駅は大きさ別に数種類あり、ホームの数（2〜14）と快適さが違う。ホームを増築できる（事実 F20、F21） | 1 種類（相対式ホームの 2 面 2 線）だけを取る。大きい駅と増築は後で足す | 乗り換えの多い駅を作るのは、まず路線と乗る人が動いてからでよい |
| 車両基地（Rail Yard）が列車を出して整備する。基地ごとに持てる台数が決まっている（事実 F19、F21） | 今は取らない。列車は路線の最初の駅に現れる | 基地まで線路をつなぐ手間は、遊ぶ人の判断をあまり増やさない。本数の上限は路線ごとに持つ |
| 路線は、駅を順に選んで引く。同じ駅を複数の路線が使える。路線ごとに運賃、台数、運行時間（昼、夜、両方）を決める（事実 F19） | 路線の引き方と台数は取る。運賃は街で 1 つにする。運行時間は取らない | 運賃を街で 1 つにする理由は 3.7 の駐車場の料金と同じである（後述の「お金」）。運行時間は、夜の移動がまだ少ないので効かない |
| 台数を増やすと待ち時間が短くなる。運賃は経路の計算に入る（事実 F19） | 取る | 本数と運賃が、遊ぶ人の主な手になる |
| 住民は時間、快適さ、お金、振る舞いで手段と経路を選ぶ。快適さには降りる停留所を見つけることが入り、お金には歩くことも比べる（事実 F1、F22） | 時間とお金だけを取る | 5.1 と同じく、MVP は時間とお金だけを入れる |
| 道路と線路が同じ高さで交わる所は踏切になる。遊ぶ人が置く鉄道の信号はなく、列車が自分で先の線路を押さえる（事実 F24） | 取る。踏切を作り、閉塞は中核が自動で扱う。信号は置かせない | 地上の層しかないうちは、道路と線路を交わらせるには踏切しかない。踏切で車が止まるのは、日本の街らしい詰まりでもある |
| 鉄道は開発の点で解く（事実 F23） | 今は取らない。初めから置ける | chizu にはまだ開発の点の仕組みがない。人口の節目で解くかは、節目の仕組みをそろえるときに決める |
| 外の街とつながる幹線の鉄道が、旅行者と移住者を運ぶ | 今は取らない（後述） | 移住する世帯は外から移動してこない。要件の幹線鉄道は、物の流れと一緒に入れる |

判断：

- 複線の 1 種類、駅の 1 種類、運行時間を取らないこと、開発の点を取らないこと【マネージャー】。
- 車両基地を取らないこと【マネージャー：決定】。CS2 では基地が台数の上限を決めるが、chizu では路線ごとの上限（16 本）で代える。基地を足すときは、基地から路線の最初の駅まで線路でつながっていることを、列車を出す条件にする。
- 踏切を取ること【マネージャー：決定】。踏切を作らないと、地上の層だけでは線路が道路で区切られた街の中に引けない。立体交差は高架の層を足すときに加える。

#### 1. 線路の網

線路は、道路の網（`Network`）とは別の網 `Rail` として持つ。

```rust
pub struct Rail {
    nodes: Slots<RailNode>,       // 世代つきの ID（1.3 と同じ）
    tracks: Slots<Track>,         // ノードとノードを結ぶ直線の線路。上りと下りの 2 本を持つ
    crossings: Vec<Crossing>,     // 踏切。線路と道路の区間の交わるマス
    stations: Slots<Station>,
    lines: Slots<RailLine>,
    trains: Slots<Train>,
}
pub struct Track { pub a: RailNodeId, pub b: RailNodeId, pub line: Line, pub layer: Layer }
pub struct Crossing { pub track: TrackId, pub at: TilePos, pub segment: SegmentId }
```

- 道路の網の中に区間の種類として足す案は取らない。網に線路を入れると、3 本以上の区間が集まるノードに横断歩道と交差点の決まり（3.5）が付き、車と歩く人の経路のグラフ（5.1）も作り直しになる。線路を引くたびに、覚えた経路を捨てることにもなる。別の網にすれば、道路の経路探索とその覚えた結果は、線路を引いても変わらない。
- 1 マスに置けるのは、道路か線路のどちらか 1 つである。ただし、踏切のマスだけは両方が通る。マスの使い道（`TileUse`）に線路を足す。
- 線路は 8 方向の直線を、1 回に 1,024 マス（`MAX_ROAD_TILES` と同じ）まで引ける（`BuildRail { from, to }`）。線路の端が既存の線路のノードに当たればつなぐ。途中のマスで既存の線路に当たれば、そこで両方を分けてノードを置く（分岐）。
- ノードで向きを変えられるのは、45 度までとする。90 度以上の曲がりは断る（`DenyReason::RailTooSharp`）。曲線は道路と同じく入れない。45 度の曲がりと分岐では、列車は時速 40km まで落とす。
- 1 つのノードに集まる線路は 3 本までにする（分岐 1 つ）。
- 道路のマスを横切る線路は、次をすべて満たすときだけ踏切にする。満たさなければ断る。
  - 道路のノード（交差点、曲がり角、つなぎ目）のマスではない。区間の途中のマスである。
  - 高速道路ではない（`DenyReason::HighwayCrossing`）。
  - 線路と道路が平行ではない（縦と横、斜めと縦横など）。
  - 両隣のマスに別の踏切がない。
- 道路を線路の上に引いても、同じ決まりで踏切になる。
- 取り壊し（`Bulldoze`）は、範囲にかかる線路のマスを道路と同じく外す。線路の上にいる列車は、後述の「途中で消えたとき」のとおりに扱う。
- 線路の網は、つながりごとに別の路線を持てる。つながっていない 2 つの線路の網は、それぞれ別の鉄道として動く。

理由：

- 人間の方針：鉄道を公共交通の最初の手段にする。
- CS2 に近づける：踏切があり、線路は道路とつながらない別の網である（事実 F20、F24）。
- 決定論：ID は世代つきの添え字で、使い回しの順も 1.3 と同じにする。

判断：別の網にすること、1 マスに道路か線路の 1 つ、45 度まで、分岐 1 つ、踏切の条件【マネージャー】。

#### 2. 駅

駅は、遊ぶ人が置く施設の 1 種類（`ServiceKind::Station`）にする。発電所と同じく `PlaceBuilding { kind, at, rotation }` で置く。

| 項目 | 値 |
|---|---|
| 大きさ | 間口 10 マス（80m）× 奥行き 3 マス（24m） |
| 中の形 | 道路の側から、駅舎とホーム（1 列）、複線の線路（1 列）、ホーム（1 列） |
| 駅の線路 | 真ん中の列の 10 マス。両端に線路のノードを置き、駅の外の線路とつなぐ |
| 出入口 | 面した道路の、間口の真ん中の歩道の点（施設の出入口と同じ決まり） |
| ホームの長さ | 80m。4 両の列車（後述）がちょうど入る |

- 駅の線路は道路と平行に走る。駅の両端から外へ線路を引いてつなぐ。CS2 の駅と同じく、駅を置けば駅の中の線路もできる（事実 F20）。
- 歩く人は駅の出入口から入り、ホームの間は跨線橋でつながるものとして、上りと下りのどちらのホームにも歩かずに行ける。駅の中を歩く時間は足さない（3.8 の私道と同じ考え）。
- 1 つの駅に止まれる列車は、向きごとに 1 本である（ホームが向きごとに 1 つ）。後ろの列車は、駅の手前の閉塞で待つ。
- 名前は、ほかの施設と同じく「{地区の名前}{施設の種類}」で「港町駅」とする（map-style.md の名前の付け方）。

駅まで歩く範囲は 64 マス（512m、`STATION_WALK_RADIUS`）にする。

- 日本の都市計画では、鉄道駅の徒歩圏を 800m とすることが多い（事実 F25）。chizu では歩く時間が重く効くので、狭くする。歩く速さは 1,389 mm/tick なので、512m は約 369 tick かかり、通勤の点の満点の境目（300 tick、1.6）を少し越える。
- この範囲は、乗る駅を探す候補の範囲と、画面で見せる駅の円にだけ使う。範囲の中のどの駅を使うかは、所要時間の見積もりで決める（後述の 4）。
- 3.7 の共同の駐車場を借りる範囲（32 マス）の 2 倍になる。駐車場は家ごとに要るが、駅は街に少しだけ置くものなので、広めにした。

判断：

- 駅を 1 種類、10 × 3 マスにし、`PlaceBuilding` で置くこと【マネージャー】。
- 駅まで歩く範囲 64 マス【マネージャー】。測って決め直す。

#### 3. 路線と列車

路線は、駅を順に選んで引く。CS2 の路線の道具と同じく、駅を 1 つずつ足していく。

| コマンド | 中身 |
|---|---|
| `CreateLine { from, to }` | 駅 `from` から駅 `to` への路線を作る。駅は占める範囲の最小の角のマスで指す |
| `ExtendLine { line, station }` | 路線の終点の先に駅を 1 つ足す。最初の駅を指せば環状の路線になる |
| `RemoveLine { line }` | 路線をなくす。走っている列車と、待っている人は後述の「途中で消えたとき」のとおりに扱う |
| `SetLineTrains { line, trains }` | 路線を走らせる列車の本数を決める。0〜16 |

- コマンドの中身は決まった大きさにする。`Command` は `Copy` で、記録も種類ごとに決まった大きさの中身で持つ（`record.rs`）。駅の並びを 1 つのコマンドに入れると、可変長の中身が初めて記録に入るので、足していく形にした。
- 駅と駅のあいだの線路は、線路の網の上の最短の道のりを、決まった順（ノードの ID の順）で選ぶ。路線は駅の並びと、そのあいだの線路の並びを持つ。線路を変えたら、路線ごとに線路の並びを選び直す。選べない区間ができた路線は止まり、列車は前の駅で止まって待つ。
- 環状でない路線は往復する。列車は終点の駅で、反対の線路へ移って折り返す。折り返しのあいだ（30 tick、`TURNBACK_TICKS`）は、終点の駅の両方のホームを押さえる。
- 路線は途中の駅を通り過ぎてよい。止まるのは、路線に入れた駅だけである。
- 路線の数は街で 64 まで、1 つの路線の駅は 32 までにする。

列車：

| 項目 | 値 | 理由 |
|---|---|---|
| 編成 | 4 両、1 両 20m、全長 80m | 日本の通勤電車の 1 両の長さ（事実 F26）。駅のホームの長さと合わせる |
| 定員 | 1 両 150 人、編成 600 人 | 日本の通勤電車の 1 両の定員（事実 F26） |
| 最高の速さ | 時速 90km（25,000 mm/tick） | 道路の大（時速 60km）より速く、高速道路（時速 100km）より遅い。駅の間が短い街の中の路線に合わせる |
| 加速と減速 | 800 mm/tick² と 1,000 mm/tick² | 通勤電車の加速（時速 3km/秒前後）に近い値 |
| 止まる時間 | 20 tick。乗り降りが多ければ、1 tick に 20 人ずつで延ばす | 4 両 × 片側 4 扉で、1 扉 1 秒に 1 人ほど |

- 列車は `Train { line, track, dir, offset, speed, next_stop, riders, dwell }` で持つ。位置は先頭の線路と線路の上の距離で、尾は全長ぶん後ろにある。
- 本数を増やすと、新しい列車は路線の最初の駅に、前の列車が出たあとで現れる。本数を減らすと、次に終点で折り返す列車から、乗っている人を降ろして消える。
- 列車はダンゴにならないよう、駅で間を空ける。駅を出るのは、同じ路線の同じ向きの前の列車がその駅を出てから、少なくとも「1 周の見込みの時間 ÷ 本数」の半分がたったあとにする。1 周の見込みは、線路の長さと速さ、止まる時間から求める。

閉塞（列車どうしをぶつけない決まり）：

- 線路の向きごとに、ノードとノードのあいだを 1 つの閉塞とする。駅の線路、分岐のノード、踏切の前後もノードで区切るので、閉塞は長くても数百 m になる。
- 列車は、先の閉塞が空いているときだけ入る。入れる見込みがなければ、閉塞の端で止まれる速さまで落とす。中核が自動で扱い、遊ぶ人は信号を置かない。
- 分岐のノードは、上りと下りをまとめて 1 つの閉塞にする。複数の列車が同じ tick に入ろうとしたら、待った長さの長い順、同じなら列車の ID の順に入れる。全順序なので、譲り合って誰も動かない行き詰まりは起きない。
- 1 つの路線は、上りと下りの線路を向きどおりに使うので、向かい合う列車が同じ閉塞を取り合うのは、分岐と終点の折り返しのときだけになる。終点の折り返しは、両方のホームが空いたときだけ駅に入るので、輪にならない。

踏切：

- 列車の先頭が踏切の手前 400m（約 16 tick ぶん）に来てから、尾が踏切を抜けるまで、踏切を閉じる。
- 閉じた踏切は、道路の側では区間の途中の衝突区間（3.5 の横切りと同じ仕組み）として扱う。車は止まりきれるなら手前で止まり、歩く人は渡り始めない。
- 踏切の中で止まる車を出さないよう、交差点と同じく、踏切の先に車 1 台が抜けきる空きがなければ、車は踏切に入らない。
- それでも踏切の中に車か人がいれば、列車は踏切の手前の閉塞で止まる。列車は車に譲るが、閉じたあとに新しく入る車はいないので、待ちは短い。
- 踏切で止まった車の延べ tick を、読み取り用に数える（`RailTally::crossing_wait`）。

速さによる計算の細かさ：

- 列車は、どの速さでも 1 tick ずつ動かす。列車は多くて数百本で、乗る人は列車の中の並びとして持つだけなので、1 tick の重さは移動体 2 万に比べて小さい。3.1 の区間の計算と一括の計算が入っても、粗くなるのは駅まで歩く区切りと車だけで、列車と乗り降りは同じ規則で動く。
- そのため、運賃の収入、乗った人の数、待ち時間は、どの速さで回してもずれない。8.2 のずれのテストには、鉄道の数字も足す。

判断：

- 駅を 1 つずつ足すコマンドの形、往復と環状、止まる駅を選ぶこと【マネージャー】。
- 編成、定員、速さ、止まる時間、本数の上限 16、間を空ける決まり【マネージャー】。測って決め直す。
- 閉塞を中核が自動で扱い、信号を置かせないこと【マネージャー：決定】。CS2 にも鉄道の信号の道具はない（事実 F24）。遊ぶ人の判断は、線路の引き方、駅の位置、本数に絞る。
- 列車をどの速さでも 1 tick ずつ動かすこと【マネージャー：決定】。要件の「最高速では移動体を作らない」と食い違うので、要件の直しを提案する（「要件との食い違い」）。

#### 4. 移動の選び方

鉄道が入ると、手段は歩き、車、鉄道の 3 つになる。鉄道の移動は「歩く → 待つ → 乗る → 歩く」の区切りで、乗り換えるときは「降りる → 待つ → 乗る」が 1 回増える。

候補の作り方：

1. 出発の建物の正面のマスから 64 マス以内の駅を近い順に 3 つ、行き先の建物から 64 マス以内の駅を近い順に 3 つ選ぶ。駅の空間索引は、チャンクごとの駅の一覧で持つ。
2. 9 つの組のそれぞれで、駅から駅への所要時間を、駅の組の表（後述）から引く。乗り換えは 1 回までにする。
3. いちばん費用の小さい組を、鉄道の候補にする。どちらかの側に駅がないか、駅の組がつながっていなければ、鉄道の候補はない。

費用は、所要時間の見積もり（移動の秒）に、運賃を秒に直した値を足す。

| 手段 | 見積もり |
|---|---|
| 歩き | 直線の距離 × 13 ÷ 10 ÷ 歩く速さ |
| 車 | 直線の距離 ÷ 1,000 mm/秒（1.6 の `STRAIGHT_LINE_MM_PER_SECOND`。駐車場まで歩く時間と詰まりを含めて測った値） |
| 鉄道 | 駅まで歩く（直線 × 13 ÷ 10 ÷ 歩く速さ）＋待ち ＋乗る ＋乗り換えの待ち ＋駅から歩く ＋運賃 × `FARE_SECONDS`（1 円 20 秒） |

- 歩きの 13 ÷ 10 は、碁盤の目の街で直線より遠回りする分である。測って決め直す。
- 待ちは、路線の運転間隔（1 周の見込みの時間 ÷ 走っている本数）の半分にする。直前に乗りきれずに残った人がいた駅と向きでは、間隔をもう 1 つ足す。
- 乗る時間は、駅の組の表から引く。表は、路線ごとに駅から駅までの時間を、線路の長さ、速さ、止まる時間から求め、列車が走ったら測った値を 1/4 の重みで混ぜる（3.4 の考えと同じ）。乗り換えの時間には、乗り換える路線の待ちを足す。表は路線か線路が変わったときと、時間帯ごとに作り直す。駅が S 個なら表は S² で、駅が 200 でも 4 万の値で済む。
- 車の見積もりは、鉄道とは違って運賃のようなお金を含まない。燃料代と駐車料金をお金の重みで足すのは、#215 で経路の費用にお金を入れるときにする。それまでは、鉄道がお金の分だけ不利になる。

選び方：

| 世帯 | 候補 | 選び方 |
|---|---|---|
| 車を持ち、車を使える | 歩き、車、鉄道 | 150m 未満は今と同じく歩く。それより遠ければ、3 つの費用のいちばん小さいもの |
| 車を持つが、車を使えない（ほかの人が乗っている、離れた所にある） | 歩き、鉄道 | 費用の小さいほう |
| 車を持たない（`CAR_OWNERSHIP_PERCENT` の外）で、枠がある | 歩き、鉄道。鉄道の候補がないときだけ、今の仮の扱い（500m 以上は車） | 費用の小さいほう |
| 枠がない（車を持てない） | 歩き、鉄道 | 費用の小さいほう |

- 鉄道の候補がある移動では、車を持たない世帯の「500m 以上なら車」の仮の扱いを使わない。鉄道が届く範囲では、仮の扱いを鉄道に置き換える【マネージャー：決定】。人間の方針（#311 のねらい）そのものである。
- 鉄道の候補がない移動で仮の扱いをいつ外すかは、遊びの方向に関わるので人間に聞く【人間に聞く】（「人間に聞くこと」の 1）。外すまでは、今の街の数字は変わらない。
- 帰りも同じ決まりで選ぶ。行きに鉄道を使った人の車は、家に停めたままである。行きと帰りで手段が違ってもよい（車で行った人は、停めた車に乗って帰る今の決まりを優先する）。
- 買い物の移動（`errand`）も同じ決まりで選ぶ。
- 見積もりで選んだ手段の、実際にかかった時間は、1.6 の通勤の時間としてそのまま測る。待ちと乗り換えも含む。

乗る人の持ち方：

- 駅まで歩く区切りは、今の歩く移動（`Trip`）のまま歩道を歩く。駅の出入口に着いたら、移動は歩道から外れ、駅の待ち行列に入る。`parking::Then` に `Ride { board, alight, line, dir, then }` を足し、乗り換えは `then` で次の乗車をつなぐ。
- 駅の待ち行列は、（駅、路線、向き）ごとに、着いた順の `TripId` の並び（`VecDeque`）で持つ。同じ tick に着いた人は ID の順に並べる。
- 列車は、乗っている人を（降りる駅の順、`TripId`）の順に並べて持つ。駅に着いたら、先に降りる人を降ろし、次に待ち行列の先頭から定員まで乗せる。
- 降りた人は、駅の出入口から行き先へ、新しい歩く区切りを始める。出発の tick は引き継ぐ。
- 乗る人は、列車の上でも駅でも、移動体を作らない。画面には列車だけを描き、乗っている人数を列車の混み具合として見せる。
- 待ち行列の先頭に 600 tick（`RAIL_GIVE_UP`）より長くいる人は、歩きに切り替えて行き先へ向かう。数を読み取り用に数える（`RailTally::gave_up`）。

途中で消えたとき：

- 路線をなくしたか、駅を取り壊したときは、その駅で待っていた人は歩きに切り替える。乗っていた人は、列車が次に止まる駅（なければ今いる線路にいちばん近い駅）で降りたことにして、そこから歩く。駅が 1 つもなければ、3.6 の救済と同じく行き先に着いたことにする。
- 線路を取り壊して、その上の列車が消えたときも同じにする。

理由：

- 人間の方針：車を持てない世帯の遠い移動を鉄道に移す。
- CS2 に近づける：時間とお金の費用で手段を比べる（事実 F1、F22）。待ち時間が本数で短くなる（事実 F19）。
- 歩く人の多い街：駅まで歩く人が増える。駅のまわりの歩道と横断歩道が、歩く人の多い所になる。
- 決定論：候補の駅は距離の近い順、同じなら駅の ID の順に選ぶ。費用は整数の秒で、同じなら歩き、鉄道、車の順に選ぶ。待ち行列と列車の中の並びは、着いた tick と ID の順で決まる。

判断：

- 費用を時間とお金にすること、見積もりの式、乗り換え 1 回まで【マネージャー】。
- 候補の駅を両側 3 つずつにすること【マネージャー】。性能（後述）を見て決め直す。
- 乗る人に移動体を作らないこと【マネージャー：決定】。要件の「移動層：家を出た時点で移動体になり、道路や線路の上を動く」は、列車が線路の上を動き、乗る人はその中にいるものと読む。

#### 5. お金

| 項目 | 値 | 比べる値 |
|---|---|---|
| 線路の建設費 | 1 マス 1,500。斜めは長さに比例 | 道路の大は 750 |
| 線路の維持費 | 道路と同じく、建設費の 1%（1 日） | `ROAD_UPKEEP_PERMILLE_PER_DAY` |
| 踏切 | 線路の建設費に含める | |
| 駅の建設費 | 40,000 | 発電所 60,000、駐車場ビル 72,000 |
| 駅の維持費 | 800（1 日） | 発電所 1,200 |
| 列車の維持費 | 1 本 600（1 日）。走らせている本数で数える | |
| 運賃 | 1 回の乗車ごとに街で 1 つの額。乗り換えても 1 回分。初期値 5、範囲 0〜20（`SetFare`） | 住民 1 人の住宅の税（1 日 10〜18） |

- 駅 4 つ、線路 40 マス、列車 4 本の路線は、建設に約 22 万、維持に 1 日約 6,200 かかる。1 日に 1,300 回乗られれば、初期値の運賃 5 で釣り合う。始めの所持金（50 万）で 1 本は引けるが、もう 1 本は税収を貯めてからになる。
- 運賃は街の所持金に入る。収支（`World::finances`）の収入に「運賃」、支出に「鉄道の維持費」の行を足す。
- 運賃は世帯の蓄えからは引かない。3.7 の駐車場の料金と同じく、世帯の蓄えに出入りの流れがまだないためである。運賃の重さは、手段の選び方（費用）で効かせる。
- 運賃を 0 にすれば、時間だけで選ばれる。上げると、駅から遠い人と、乗る時間の短い人から鉄道をやめる。収入と利用の取引になる。

理由：

- CS2 に近づける：鉄道は初めの費用が重く、乗る人が多いと元が取れる（事実 F19）。運賃は経路の費用に入る。
- 運賃を街で 1 つにする：3.7 の 2 と同じく、まず遊ぶ人が 1 つの手で釣り合いを試せるようにする。路線ごとの運賃は、#215 で経路の費用にお金の重みを入れるときに合わせて足す。

判断：

- 費用、運賃の初期値と範囲、`FARE_SECONDS`【マネージャー】。測って決め直す。
- 運賃を街で 1 つにすること、世帯の蓄えから引かないこと【マネージャー：決定】。3.7 の料金と同じ扱いにそろえる。

#### 6. 幸福度、需要、駐車場、転出への効き

#### 7. 決定論と性能

決定論：

- 線路、駅、路線、列車の ID は世代つきの添え字にし、`BTreeMap` か ID で引く `Vec` で持つ。反復はすべて ID の順にする。
- 列車の 1 tick は、道路の移動体と同じ 2 段に分ける。1. 前の tick の状態だけを読んで、列車ごとに新しい速さと位置を求める（並列にしてよい）。2. 閉塞の出入りと駅の乗り降りを、列車の ID の順に 1 本ずつ確定する。
- 踏切の開け閉めは、tick の頭に列車の位置だけから決める。状態に持たない（信号と同じ）。
- 駅の組の表と運転間隔の見込みは、線路と路線と測った値から作り直せる。測った値は状態に入れ、表そのものは入れない。
- 状態ハッシュには、線路、駅、路線、列車（位置、速さ、乗っている人の並び）、駅の待ち行列、運賃、測った値を入れる。読み取り用の数（`RailTally`）は入れない。

性能（10 万人規模）：

- 人口 10 万人が 1 日に 25 万回移動し、その 2 割が鉄道に乗ると、1 日に 5 万回の乗車になる。乗る人は待ち行列と列車の並びの中の ID で、毎 tick 触るのは駅に止まった列車の分だけである。
- 手段を選ぶ計算は、1 回の移動で、駅の空間索引を 2 回引き、表を 9 回引くだけである。道路の経路探索（5.2）は、選んだ手段の歩く区切りと車の区切りにしか回さない。駅まで歩く区切りは行き先が駅に集まるので、5.2 の覚えた結果がよく当たる見込みである。
- 線路の網は経路探索のグラフに入れない。路線の線路の並びを選ぶ探索は、路線か線路が変わったときだけ回す。
- 6.2 の `perf` に `rail_100k` を足す。`city_grid_100k` に路線 4 本と列車 32 本を置き、1 日を回す。`day_100k` に対する増分を 1 割以内にする。

判断：測る項目と目安【マネージャー】。

- act は、`buildRail { from, to }`、`placeBuilding` の `station`、`createLine { from, to }`、`extendLine { line, station }`、`removeLine { line }`、`setLineTrains { line, trains }`、`setFare { fare }` を受ける。断る理由（`RailTooSharp`、`HighwayCrossing` など）も、ほかのコマンドと同じく出す。

#### 測り方

鉄道のない街は変わらないので、比べるのは「同じ土地に線路と駅を置き、列車を走らせない街」と「走らせる街」である。走らせない街は、鉄道のない街と同じ移動になる。線路と駅が土地を使う分の違いを、比べる両方にそろえるためである。

- 街：3.7 の「測り方」と同じ 6 つの窓（種 77、種 311、種 512、種 101、city.rec、種 0）。
- 置き方：記録の決まった tick（窓の始まりの 3 日前）に、決まった手順で 1 本の路線を置く記録を足す。手順は、observe の住宅の世帯が多い 8 × 8 マスの区切りと、職場の多い区切りの真ん中を結ぶ直線の近くに、取り壊してでも駅 4 つと線路を置く、とする。手順は小さな関数にして測る PR にテストの補助として置き、誰が回しても同じ記録になるようにする。
- 前の版の記録は、所持金が少し違うと建てる操作が断られて別の街になる。1.6 と同じく、比べる両方に始めの所持金を同じだけ足す。
- 交通の数字は小さな違いで大きく揺れる。3.9 と同じく、着く判定を少しずつずらした版 5 本（揺れやすい街は 10 本）の組の平均と最小・最大で比べる。

|---|---|---|
| 手段の割合 | その日に着いた移動の、歩き、車、鉄道の割合 | 上限は設けない。PR に出す |
| 乗った人と乗車率 | 路線ごとの 1 日の乗車、いちばん混んだ区間の乗車率、乗りきれずに残った人、待ちきれずに歩いた人 | 乗車率が 1 日を通して 100% なら定員か本数の初期値が低すぎる |

| 踏切 | 踏切で止まった車の延べ tick | PR に出す |

- 運賃を 0、5、10、20 にした版も、同じ時点から運賃だけ変えて回し、乗った人と収入を並べる（3.7 の料金ごとの表と同じ形）。

#### 要件との食い違い

要件の文は変えない。次の直しを提案する。どれも要件の文を変えるので、人間の了承を得てから直す（「人間に聞くこと」の 3）。

1. 「交通」の表の鉄道の「ダイヤと定員がある」を、「本数（運転間隔）と定員がある」にする。CS2 は時刻表ではなく、路線ごとの台数で間隔を決める（事実 F19）。chizu も本数で決め、時刻表は持たない。
2. 「最初の版のあとに足すもの」の「バスと鉄道」を「鉄道、バスの順」にする。人間の方針（#311）に合わせる。
3. 「時間」の表の最高速の「移動体を作らない」に、「列車は数が少ないので、どの速さでも 1 本ずつ動かす」を添える。
4. 「住民」の移動層の「道路や線路の上を動く」に、「列車に乗っている人は、列車の中の人数として持つ」を添える。

#### 決めきれない点

人間から任され、マネージャーが決めたこと【マネージャー：決定】：

1. 線路を道路の網と分けた別の網にする。
2. 踏切を作る。立体交差は高架の層を足すときにする。
3. 車両基地を作らず、路線ごとの本数の上限で代える。
4. 閉塞を中核が自動で扱い、鉄道の信号を置かせない。
5. 列車はどの速さでも 1 tick ずつ動かし、乗る人に移動体を作らない。
6. 運賃を街で 1 つにし、世帯の蓄えから引かない。
7. 鉄道の候補がある移動では、車を持たない世帯の 500m の仮の扱いを使わない。
8. 幹線鉄道（外部接続）は、物の流れと一緒に入れる。移住する世帯は外から移動してこないので、今の幹線鉄道は、つながっていることを示すだけになるためである。

測った数字を見て、マネージャーが決めること【マネージャー】：

1. 駅まで歩く範囲（64 マス）、候補の駅の数（両側 3 つ）。
2. 編成、定員、速さ、止まる時間、本数の上限。
3. 建設費、維持費、運賃の初期値と範囲、`FARE_SECONDS`。
4. 見積もりの式（歩きの遠回り 13 ÷ 10、車の 1,000 mm/秒）。
5. 踏切を閉じる距離（400m）。

#### 人間に聞くこと

1. 鉄道の届かない所で、車を持たない世帯の「500m 以上なら車を使う」仮の扱いをいつ外すか。外すと、駅のない所の車を持たない世帯（3 割）の遠い移動はすべて歩きになり、通勤が延び、幸福度が下がる。鉄道を引く理由は強くなるが、鉄道を引くまで街が苦しくなる。案は 3 つある。(a) 鉄道を入れても残す。(b) 作る順の 6 の後に外す。(c) 外すのは、バスも入れて、どこでも公共交通が届く手が遊ぶ人にそろってからにする。マネージャーの案は (c) である。
2. 家の近く（64 マス）に路線の止まる駅がある、車を持てない世帯の駐車場の点を上げるか。上げないと、駅を置いても駐車場の点は 30 のままで、駅は通勤の点にしか効かない。#311 のねらいの「駅を置くか駐車場を置くかを選べる」は、幸福度の上では弱くなる。上げると、要件の幸福度の駐車場（「自宅か近くに車を置けるか、遠さ、料金」）の意味が「車がなくても困らないか」に広がるので、要件の文を変えることになる。マネージャーの案は、上げて 70 点（共同の駐車場を中くらいの遠さで借りた世帯と同じ）にし、要件の駐車場の行に「車を置けなくても、近くに駅があれば点の下がりを和らげる」を足すことである。
3. 「要件との食い違い」の 4 つの直しを入れてよいか。

## 4. 決定論の守り方

| 項目 | 方法 |
|---|---|
| 数値 | 1.1 の整数の型だけを使う。`f32` と `f64` を `disallowed_types` で禁じ、浮動小数点のリテラルも `scripts/check-no-float.sh` で禁じる |
| 乱数 | 自前の小さな生成器（SplitMix64 で種を混ぜ、PCG32 で引く）。外部クレートを使わないのは、版が上がって乱数の列が変わるのを避けるため |
| 乱数の流れ | 共有の生成器を持たない。`rng(seed, 用途, 対象の ID, tick)` で毎回その場で作る。並列に回しても引く順番に左右されない |
| 集合 | `HashMap` と `HashSet` を clippy の `disallowed_types` で禁じる。`BTreeMap`、ID で引く `Vec`、挿入順を保つ表のどれかを使う |
| 並列 | rayon で並列に回すのは「入力を読み、出力を自分の枠に書く」処理だけにする。添え字つきの並列反復を `collect` すれば元の順番が保たれる（事実 F8）。他の表への書き込みは、命令の列として集め、ID 順に並べてから 1 本のスレッドで適用する |
| 集計 | 整数の足し算だけで行う。足す順番が変わっても結果は変わらない |
| 経路探索 | 時間帯の初めに重みの写しを作り、その時間帯の探索はすべて写しを読む。結果は依頼の順に並べて適用する |
| 状態ハッシュ | `World::state_hash()` が、表を ID 順になめて決まった順番でバイト列を作り、xxh3 にかける。`std::hash::Hash` の既定の仕組みは使わない |

## 5. 経路探索

### 5.1 グラフ

- 車のグラフは、リンクを頂点、ノードでの曲がり方（`Connector` をリンク単位にまとめたもの）を辺にする。曲がり方を辺にすると、右折禁止や信号の待ちを辺の重みに乗せられる。
- 歩行者のグラフは、歩道のリンクを頂点にし、ノードでのつながりを辺にする。歩道のリンクは歩く向きを表し、どちらの側の歩道を歩くかは移動の主体が持つ（3.5 節）。横断歩道を渡る時間は経路の費用に入れない。区間の途中での横切りの費用（100m の固定）は、グラフの辺ではなく、出発と行き先の組を選ぶときに足す。
- 自家用車の移動は「歩く → 車 → 歩く」の 3 区切りで探す。家の駐車場から車に乗り、行き先の建物の駐車場（満車の見込みなら近くの駐車場）で降りる。
- 費用は、所要時間に、燃料代と駐車料をお金の重みで換算して足したものにする。CS2 の時間・快適さ・お金・振る舞いの 4 つ（事実 F1）のうち、MVP は時間とお金だけを入れる。
- 住民は家を出るときに、徒歩と自家用車の両方の費用を比べて安いほうを選ぶ。

### 5.2 10 万人規模で回すための方式

10 万人が 1 日に約 2.5 回移動すると、1 日に 25 万回の探索が要る。最高速で 1 日 5 秒なら、毎秒 5 万回になる。素朴な A* で 1 回に数 ms かかると、4 スレッドでも間に合わない。

段階を踏んで速くする。

1. **A* ＋結果の再利用（最初の実装）**：`(出発のリンク, 着くリンク, 手段, 時間帯)` を鍵にして結果を覚えておく。網か時間帯の重みが変わったら捨てる。住民の行き先は職場や店に集まるので、覚えた結果を使い回せる場面が多いと見込んでいる。
2. **出発地の束ね**：同じ tick に同じ建物群から出る探索を、1 回の一対多の探索にまとめる。
3. **CCH（必要になったら）**：Customizable Contraction Hierarchies は、網の形だけを使う重い前処理と、重みを入れる軽い処理を分ける手法である（事実 F9）。時間帯ごとに重みだけを入れ直せばよく、渋滞の反映と相性が良い。道路を引くたびに前処理をやり直すので、建設中は 1. に戻すといった工夫が要る。既存の RoutingKit は C++ なので、使うなら Rust で書き直す。

探索は `Router` という trait の裏に隠し、1.〜3. を差し替えられるようにする。探索の依頼は tick ごとに集めて rayon で並列に解き、依頼の順に適用する。

### 5.3 渋滞の反映と経路の見直し

辺の重みには、3.4 の `LinkStats` の見積もりを時間帯の初めに写したものを使う。所要時間の情報源を 1 つにすることで、細かい計算と粗い計算で経路の選び方がずれない。

いまは `LinkStats` を入れる前の仮の形として、車線に並んでいる車の台数から遅れを見積もる。

- 時間帯（75 tick）ごとに 1 回、職場の割り当てなどの重い処理と重ならない時間帯の真ん中の tick に、時速 7.2km より遅い車をリンクごとに数え、1 台あたり 4 秒をリンクの車線の数で割った長さを遅れにする。交差する流れのある交差点や信号では、車線の先頭から 4 tick に 1 台ほど抜けるためである。
- 車のリンクの費用は、自由に走れたときの所要時間にこの遅れを足したものにする。次に見積もるまでの探索はすべて同じ遅れを読む。遅れが変わったら、覚えた車の経路を捨てる。
- 時間帯の途中で書き出した街を読み戻しても同じ経路を選ぶよう、遅れは街の状態に入れる。
- 費用の同じ経路が並ぶ碁盤の目でも、混んだ道を避けて並行の道へ分かれる。

碁盤の目には、費用の同じ最短経路がたくさんある。1 つの決まりで 1 本を選ぶと、遅れが見積もられるまで、同じ向きの車がみな同じ道に集まる。そこで、費用の同じ経路を次のように散らす。

- 車の経路は、1 回の探索から、費用の同じ経路を 8 本の候補として取り出す。候補 k では、出発のリンクから進むたびに、最短経路を続けられる辺のうち、行き先のリンクの順がいちばん小さいものを選ぶ。順は、候補の番号と、リンクの通る直線（向きと位置）を混ぜた値である。同じ直線の上では順が変わらないので、まっすぐ進む経路が選ばれやすい。
- どの候補を使うかは、出発と行き先の位置を混ぜた値で決める。同じ 2 点のあいだはいつも同じ経路を通り、同じ道に面した隣の家からは別の経路に分かれる。
- 費用は変えないので、ヒューリスティックは下限のままである。結果は `(出発のリンク, 着くリンク, 手段, 時間帯)` ごとに 8 本の候補をまとめて覚えるので、探す回数は変わらない。鍵あたりの大きさが鍵によって大きく違うので、覚える量の上限は鍵の数ではなく、持っている経路のリンクの数の和で決める。
- 歩く経路は散らさない。

経路は出発のときに決め、途中では変えない。ただし、通る予定の区間が消されたときと、細かい計算で同じ場所に一定の時間以上止まったときだけ、いまの位置から探し直す。

## 6. 性能の目標と測り方

### 6.1 目標

| 場面 | 規模 | 目標 |
|---|---|---|
| 細かい計算（6 倍、30 tick/秒） | 人口 10 万、移動体 2 万 | 1 tick の計算が 10ms 以内（30 tick/秒に対して 3 割の余裕）。描画は 60fps |
| 中速（48 倍、240 tick/秒） | 人口 10 万、街全体を区間の計算で回し、画面内の約 2 千体を補間して描く | 240 tick/秒を保つ |
| 最高速 | 人口 10 万 | 1 日（7,200 tick）を 5〜10 秒で回す |
| 将来 | 人口 100 万 | 最高速で 1 日 60 秒以内。表の作りを変えずに届くかを見るためだけに測る |

すべて 4 スレッドの WASM（Chrome、M1 程度の機械）を基準にする。ネイティブの値は参考にとどめる。

### 6.2 測り方

- `chizu-scenario` クレートに、種から格子状の街を決定論的に作る関数を置く。住民の表は `synthetic_population`、道路の格子は `grid_network` と `city_grid_100k`、区画を塗って建物が建つ街は `zoned_grid_city`、通勤の依頼は `commute_requests` で作る。テストとベンチマークはこれを共有する。
- ネイティブのベンチマークは `crates/chizu-scenario/benches/` に置き、`mise run bench` で回す。
  - `citizen_bucket`：住民の表の 1 組の更新（10 万人と 100 万人）
  - `route_batch`：経路の一括探索（1,000 件と 10 万件、束ねるかどうか、職場の集まり方）
  - `growth`：建物が建つ街の 1 日と、最悪の 1 tick
- ブラウザとネイティブを同じ条件で並べる測定は `chizu-scenario` の `perf` モジュールにまとめ、`mise run bench:wasm` で回す。
  - 1 tick は、`zoned_grid_city` の `World::step` と、住民の表の 1 組の更新である。住民の処理には、乱数を引いて幸福度と出発の予定を書き戻す仮の中身（`perf::rng_write`）を使う。住民の表は `World` の外に持つ。
  - `day_100k` と `day_1m`：住民 10 万人で 1 日（7,200 tick）、100 万人で 1/10 日を回し、1 tick の平均と最悪を出す。`day_ns` は 1 tick の平均から見積もった 1 日の時間である。道路を引いたあとの最初の `World::step` は経路のグラフを作り直すので、1 回進めてから測る。
  - `movers_20k`：`city_grid_100k` で、歩く人と車を 1 万ずつ出して 300 tick 進め、1 tick の平均と最悪を出す。6.1 の細かい計算の場面の目安である。
  - `route_batch_1k` と `route_batch_100k`：`city_grid_100k` で、職場が車のリンクの約 1/100 に集まった通勤を、覚えた結果がない状態から解く。
  - `memory_bytes`：始めたとき、`day_100k` のあと、`day_1m` のあとの WASM の線形メモリの大きさ。線形メモリは縮まないので、それまでで最も大きかったときの値になる。
  - 測る前に、どの項目も小さい規模で一度ずつ回す（`perf::warm_up`）。V8 は WASM をまず Liftoff で動かし、よく呼ぶ関数を TurboFan でコンパイルし直すので、その時間を測った値に入れないためである。ネイティブでも同じように回す。
- WASM の側は `chizu-bench-wasm` クレートから `perf` を呼ぶ。画面のアプリの WASM には入れず、`build:bench-wasm` で `build:wasm` と同じ rustflags とプロファイル（`wasm-release`）でビルドする。
  - `bench:wasm` は、COOP/COEP のヘッダーをつけて配る小さなサーバーを立て、ヘッドレスの Chrome で開いた Worker から呼ぶ。
  - rayon のスレッドは 1、4、`navigator.hardwareConcurrency` 本の 3 通りにする。スレッドプールは 1 つのインスタンスで 1 度しか作れないので、スレッド数ごとに Worker を作り直す。
  - 同じ項目を、ネイティブでも同じスレッド数で回す（`CHIZU_PERF_THREADS=4 cargo bench -p chizu-scenario --bench perf`）。WASM がネイティブの何倍かかったかを `ratio` に出す。`CHIZU_PERF_THREADS` がないときは何もしないので、`mise run bench` では回らない。
  - どちらも、測る処理全体を rayon のプールのスレッドの上で回す。ネイティブは `ThreadPool::install` を使い、WASM はプールに `rayon::spawn` で渡して終わるのを待つ。
  - 結果は、標準出力と `target/bench-wasm.json` に JSON で書く。`mise run bench:wasm -- --wasm-only` ならネイティブは回さない。
- 粗い計算が入ったら、6.1 の中速と最高速の場面に合わせて `perf` に項目を足す。
- 共有の CI の機械は速さがぶれるので、CI ではベンチマークをビルドするだけにする。`chizu-bench-wasm` は `lint:wasm` で wasm32 に clippy をかけ、壊れたら落ちるようにする。数字は手元で測り、大きな変更の PR には前後の値を書く。

## 7. リポジトリの構成

```text
Cargo.toml                 # workspace
rust-toolchain.toml        # 日付で固定した nightly、rust-src、clippy、rustfmt、wasm32 のターゲット
crates/
  chizu-core/              # 中核。依存は rayon（feature "parallel"）、smallvec、xxhash-rust だけ
  chizu-scenario/          # テストとベンチマーク用の街の生成
  chizu-wasm/              # wasm-bindgen の受け渡し、スナップショットの書き込み、コマンドの検証
  chizu-cli/               # ネイティブで操作の記録を再生し、状態ハッシュを出す
web/
  package.json  vite.config.ts  tsconfig.json  biome.json
  src/  main.ts  worker.ts  protocol/  render/  ui/
```

中核をさらに網・住民・交通のクレートに分けるのは、ビルド時間が気になってからにする。最初は `chizu-core` の中のモジュールで分ける。

WASM でスレッドを使うには、nightly と `build-std` と `+atomics` が要る（事実 F4）。nightly は `rust-toolchain.toml` で日付ごと固定し、ネイティブのビルドも同じものを使う。stable と nightly を混ぜると、clippy やテストを 2 つのツールチェーンで回すことになるためである。

WASM は `cargo build` のあと `wasm-bindgen --target web` で JS 側のつなぎのコードを作る。wasm-pack は使わない。`wasm-bindgen-cli` は、クレートの wasm-bindgen と同じ版を mise の tools で入れる。

TypeScript 側は Vite でビルドする。wasm-bindgen-rayon は Rollup 系では Vite を勧めている（事実 F4）。Worker の扱いと開発サーバーの COOP/COEP ヘッダーも、Vite なら設定だけで済む。パッケージ管理は pnpm、テストは Vitest、lint と整形は Biome、型の検査は `tsc --noEmit` にする。描画はライブラリを使わず、WebGL2 のインスタンス描画で書く。

node、pnpm、biome は mise の tools で入れる。Vite などの開発用の依存は `package.json` に書き、`pnpm install --frozen-lockfile` で入れる。

### 7.1 mise のタスク

既存の `test` と `lint` を、チェックごとのタスクに分けて束ねる形に変える。

```toml
[tasks."lint:md"]      # 既存
run = "rumdl check ."
[tasks."lint:actions"] # 既存
run = "jactionlint"
[tasks."lint:rust"]
run = ["cargo fmt --all --check", "cargo clippy --workspace --all-targets -- -D warnings"]
[tasks."lint:web"]
dir = "web"
run = ["biome check .", "pnpm exec tsc --noEmit"]
[tasks.lint]
depends = ["lint:md", "lint:actions", "lint:rust", "lint:web"]

[tasks."test:rust"]
run = "cargo test --workspace"
[tasks."test:wasm"]    # WASM で決まった状態ハッシュが出るか
run = "..."
[tasks."test:web"]
dir = "web"
run = "pnpm exec vitest run"
[tasks.test]
depends = ["test:rust", "test:wasm", "test:web"]
```

ほかに `build`（WASM と Web）、`dev`（Vite の開発サーバー）、`bench`、`bench:wasm` を置く。

### 7.2 CI

既存の `test` と `lint` の 2 ジョブを、タスクごとの別ジョブに分ける。matrix は使わず、ジョブを並べて書く。

| ジョブ | 呼ぶタスク |
|---|---|
| lint-md | `mise run lint:md` |
| lint-actions | `mise run lint:actions` |
| lint-rust | `mise run lint:rust` |
| lint-web | `mise run lint:web` |
| test-rust | `mise run test:rust` |
| test-wasm | `mise run test:wasm` |
| test-web | `mise run test:web` |
| build | `mise run build` と `cargo bench --no-run` |

Rust のジョブは `~/.cargo` と `target` をキャッシュする。

### 7.3 WASM のビルドの設定

設定は `bench:wasm` の数字を見て決めた。比べるときは、設定ごとにビルドした WASM を順番を入れ替えながら交互に測り、中央値で比べる。

- `--max-memory` は 2GiB にする。100 万人の街を作ったときの線形メモリは約 140〜160MiB で、これで足りる。
  - 共有メモリは、上限の大きさの仮想アドレスを最初に確保する。
  - iOS の Safari では、上限の大きい共有メモリで `WebAssembly.Memory` が作れなかったという報告がある（WebKit の Bug 255103）。そのため、wasm32 で指せる最大の 4GiB にはしない。報告は上限 2GiB のときのものなので、iOS で動かすときに確かめ、だめなら下げる。
- `target-feature` に `+simd128` を足す。WASM のビルドには専用のプロファイル `wasm-release`（`release` を引き継ぎ、`lto = "fat"` と `codegen-units = 1`）を使い、`build:wasm` と `build:bench-wasm` だけがこれでビルドする。ネイティブの `release` と `bench` は、ビルドが遅くならないように LTO を入れない。`opt-level` は既定の 3 のままにする。
  - 負荷の低いときに測ると、両方を入れた WASM は、どちらも入れないものに比べて 1 tick が 1〜3 割速く、大きさが約 2 割小さかった。経路の一括探索は、4 スレッドでは変わらなかった。
  - simd128 は、主要なブラウザがすべて対応している（Chrome 91、Firefox 89、Safari 16.4 から）。対応していないブラウザでは WASM を読み込めない。スレッドに要る共有メモリは Safari 15.2 から使えるので、Safari 15.2〜16.3 が新たに外れる。

## 8. テストの方針

### 8.1 決定論のテスト

- **再生**：`chizu-scenario` の街に決まった操作の列を与えて N tick 回し、状態ハッシュが記録した値（`tests/golden/*.hash`）と一致するかを見る。シミュレーションを意図して変えたときは、記録した値を同じ PR で更新する。
- **スレッド数**：同じ入力を、rayon のスレッド 1 本と 8 本で回してハッシュを比べる。
- **画面の範囲**：同じ記録を、途中で `movers_in` を違う範囲で呼びながら回し、呼ばない場合とハッシュが同じかを見る。
- **環境**：同じ入力を、ネイティブと WASM（Node で動かす単一スレッド版）で回してハッシュを比べる。
- **保存**：途中で保存して読み直し、続きを回した結果が、通しで回した結果と同じハッシュになるかを見る。
- **計算の切り替え**：速度を変えるコマンドを途中に挟んだ記録を、2 回再生して同じハッシュになるかを見る。

### 8.2 計算の細かさのあいだのずれ

同じ街を、細かい計算だけ、区間の計算だけ、一括の計算だけでそれぞれ 3 日回す。そして、3 日目の平均の通勤時間、交通量の多い上位 50 リンクの交通量、税収を比べる。ずれは細かい計算に対して ±10% 以内を合格とする。この幅は、ベンチマークの街で実際に測ってから見直す。

### 8.3 単体テスト

- 単位の型と丸め、BPR の表引き、乱数の列は、表で値を固定したテストと proptest を使う。
- 網の編集（道路を引く、交差させる、消す）は、ノードと区間とリンクの整合が保たれるかを proptest で確かめる。
- 追従、信号、衝突区間は、車線 1〜2 本の小さな場面を作って、止まる位置や通過の台数を確かめる。
- TypeScript 側は、受け渡しの符号化と、三重バッファの入れ替えを Vitest で確かめる。
